# AI 时代游戏客户端工程研究

以 Unity / C# 商业游戏客户端为实践场景，研究工程师如何定义问题、建立系统模型、做出取舍，并用证据对交付结果负责，而不是积累技术名词或比较代码产量。

先阅读[项目宗旨：从实现代码，到理解系统与承担工程结果](docs/project-manifesto.md)，了解项目为什么存在、核心问题及研究边界。

**当前没有完成独立来源核验或 Unity 实验。** 宗旨附有 7 条外部来源 URL，但本仓库尚未逐条核对。两份原始研究报告仍保留不可追溯的导出引用，原任务书未提供；报告中的案例数字与 AI 效率结论也未独立核验。详见[导入与证据缺口说明](docs/import-notes.md)。

## 核心问题

- 什么可观察的行为与结果，能区分“实现功能”和“对系统负责”？
- 架构、性能、资源所有权与异步生命周期之间如何相互制约？
- AI 可以承担哪些工作，哪些约束、验证与责任必须明确？
- 怎样把观点变成可证伪的问题，再依据结果修订能力判断？

选择 Unity / C#，是为了让研究落在具体的运行时、目标设备、生命周期和生产约束上；不预设结论能直接推广到所有软件领域。

## 怎样开展研究

问题与范围 → 机制模型 → 来源与证据 → 候选方案 → 实验验证 → 结果及局限 → 修订与后续问题。

- 区分来源事实、特定案例、综合推论与待验证假设。
- 官方或项目自述不自动等于性能优越的证据；第三方案例不是本项目实验结果。
- 原始报告中的能力分级是待检验的研究提案，不是项目宗旨、行业标准或认证量表；不合并报告中的不同模型。
- 下一步先恢复关键证据，再考虑“场景切换中异步任务所有权及销毁后的正确性”这一窄问题。

## 本地检查

在仓库根目录执行；检查范围与已记录结果见[变更记录](CHANGELOG.md)。

```bash
python -I -m unittest discover -s tests -p 'test_*.py' -v
python -I scripts/check_docs.py
```

检查通过也只覆盖检查器支持的文档约定，不证明研究事实、Unity 行为、外部来源可信度或页面渲染正确。
