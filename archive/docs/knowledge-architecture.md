# 知识库架构

> **状态**：v0.1（2026-11-15）。本文是仓库自身的结构设计，由 AI 起草，待所有者审阅。编辑源的约定已由所有者决定（见[决策记录](../../docs/decisions.md) D-002），其余设计随本次 PR 审阅。本文不改变任何研究结论的证据状态。

本仓库要成为一个能长期积累、深入展开、从多个维度进入的知识库。本文说明它由哪些层组成，每一层存什么、怎样变化，新知识如何进入，哪些约定由检查器保障，以及哪些结构调整还需要决定。

## 1 定位：一组可证伪的问题，而不是一套结论

**本节结论：仓库积累的是“问题、回答与回答的可信程度”，三者必须一起保存，才能在长期修订中不失真。**

[项目宗旨](../../book/part1-method/1-1-from-code-to-responsibility.md)把研究单位定为“一个可回答、可证伪的问题”。因此这个知识库的基本内容不是一组正确答案，而是：

1. **问题**：要解释什么现象，在什么范围内。
2. **回答**：机制模型、案例、推论和实践建议。
3. **可信程度**：每个回答属于来源事实、案例、推论还是假设，审核与实验进行到哪一步，什么结果会推翻它。

长期知识库最常见的失败，是三者在一次次修订中分离：回答被反复引用，可信程度却留在最初的文件里；或者结论被改写了，引用它的综合和规则却没有跟着变。本架构的目标就是让三者保持绑定。

## 2 设计原则

**本节结论：结构由少量机器可读的数据保障，派生内容自动生成，修订留下痕迹，不为未来预建空框架。**

| 原则 | 含义 | 落在哪里 |
|---|---|---|
| 问题是研究单位 | 一个专题回答一个可证伪的问题，而不是覆盖一个技术领域 | 每个专题的 `meta.json` 必须写明核心问题 |
| 单一编辑源 | 本仓库是全部研究正文唯一的编辑源 | [决策记录](../../docs/decisions.md) D-002 |
| 状态正交且显式 | 编辑、审核、证据、实验各自记录，任一状态不能推出另一状态 | 专题元数据的 `status`；命题的 `type` 与 `status` |
| 结构由数据保障 | 能被检查的约定写成数据并由检查器执行，而不是只写在说明里 | `knowledge/` 与 `scripts/check_docs.py` |
| 派生物自动生成 | 跨专题的地图和索引由数据生成，不手工维护第二份 | [知识地图](../knowledge/README.md) |
| 修订留痕 | 改变观点时保留原判断、新证据与理由；命题编号不复用 | 命题的 `history`、[变更记录](../../CHANGELOG.md) |
| 不预建空框架 | 只在真实研究需要时新增目录、词表取值或模板 | 本文第 9 节的扩展触发条件 |

## 3 五层结构

**本节结论：知识从来源进入专题，被提炼为跨专题命题，再组织成综合与实践；反例和实验结果沿同一条路径反向修订。**

| 层 | 回答什么 | 位置 | 变化节奏 |
|---|---|---|---|
| L0 宗旨与方法 | 为什么研究、怎样算证据、知识库如何组织 | [项目宗旨](../../book/part1-method/1-1-from-code-to-responsibility.md)、[研究方法](../../book/appendix-h-research-method.md)、本文、[术语与分级对照](../../book/appendix-b-glossary.md)、[决策记录](../../docs/decisions.md) | 很少；改动需记录决策 |
| L1 专题 | 一个问题的完整研究：正文、来源、案例、审校 | `research/<专题>/` | 研究推进时 |
| L2 命题 | 跨专题、承重、可被反驳的主张及其证据位置 | [命题登记](../knowledge/claims.json) | 专题修订、新证据或反例出现时 |
| L3 综合与实践 | 阶段性综合与可执行规则 | [阶段性综合](../../book/part1-method/1-4-ownership-evidence-bound.md)、[工程实践指南](../../book/appendix-a-practice-rules.md) | 每个研究阶段 |
| L4 档案 | 原始输入、历史草稿、导出来源记录、变更记录 | [原始深度研究报告](../imports/manifesto.md)、[历史草稿](../imports/deep-research-draft.md)、各专题 `export-manifest.json`、[变更记录](../../CHANGELOG.md) | 只追加，不改写 |

另有一个**导航面**：[知识地图](../knowledge/README.md)。它不保存新内容，只从 L1 与 L2 的数据生成。

```text
来源与实验 ──► L1 专题 ──提炼──► L2 命题 ──组织──► L3 综合与实践
     ▲              ▲                │                    │
     └──── 反例、实验结果、审核意见 ──┴────────────────────┘
                     （沿原路径修订，并在 history 与变更记录中留痕）
```

层与层之间只能**引用**，不能**复制**：综合与指南引用命题编号和专题文件，而不是重述一遍论证。这样一处修订，所有引用处都能被找到。

## 4 维度：同一份知识的多种进入方式

**本节结论：维度用受控词表定义，挂在专题和命题上，由知识地图展开成不同的阅读入口；不为每个维度复制目录。**

| 维度 | 挂在哪里 | 取值来源 | 回答的问题 |
|---|---|---|---|
| 主题领域 | 专题 | `domains` | 我关心异步、性能还是 AI 工作流？ |
| 责任—证据—限度 | 专题与命题 | `axes` | 这条知识帮我判断归属、证据还是边界？ |
| 陈述类型 | 命题 | `claim_type` | 这是来源事实、推论、立场还是假设？ |
| 命题状态 | 命题 | `claim_status` | 它现在有支撑、受质疑还是已被推翻？ |
| 成熟度 | 专题 | `maturity` | 这项研究走到哪一步了？ |
| 编辑、审核、证据、实验 | 专题 | `editorial` 等四项 | 写完、审过、核过、跑过了吗？ |
| 读者 | 专题 | `readers` | 我是一线工程师、负责人、学习者还是研究者？ |

全部取值登记在[受控词表](../knowledge/vocabulary.json)，每个取值写成“短名：说明”。新增取值先改词表并说明含义，检查器拒绝词表以外的值。目录只按专题划分一次；其他维度都通过知识地图进入，避免同一文件因分类不同而出现多份。

“责任—证据—限度”三轴来自[阶段性综合](../../book/part1-method/1-4-ownership-evidence-bound.md)第 5 节，是本仓库的组织框架，不是已验证的理论。若后续研究发现某类知识不适合放进三轴，应先在词表中新增轴并记录决策，而不是硬塞。

## 5 专题契约

**本节结论：每个专题必须有 README、元数据和主文档；成熟度只能按证据前进，检查器阻止“没审先称已审、没跑先称已检验”。**

### 5.1 必备文件

| 文件 | 作用 |
|---|---|
| `README.md` | 专题入口：问题、阅读顺序、状态边界 |
| `meta.json` | 机器可读元数据，字段见下表 |
| 主文档（`meta.json` 的 `entry`） | 开头一段“状态（只在此处说明一次）”；各节以“本节结论”开头 |

推荐但不强制：`sources.md`（来源登记）、`review.md`（审校记录）。专题内部文件超过十余份时，可按 `evidence/`、`history/`、`guides/` 分子目录，参考[代码优美论](../research/code-aesthetics/README.md)的组织方式。

### 5.2 元数据字段

| 字段 | 含义 |
|---|---|
| `id` | 与目录名一致的英文短名，创建后不改 |
| `title`、`question` | 中文标题与一句话核心问题 |
| `entry` | 主文档的相对路径 |
| `maturity` | 成熟度，见 5.3 |
| `status` | `editorial`、`human_review`、`evidence`、`experiment` 四项，彼此独立 |
| `domains`、`axes`、`readers` | 多维索引，取值见受控词表 |
| `related` | 相关专题的 `id` |
| `edit_source` | 当前统一为 `public`：本仓库为唯一编辑源 |
| `provenance` | 来源记录文件（如导出清单）；新专题没有时写 `null` |
| `first_public`、`last_revised` | 首次公开与最近一次实质修订的日期 |

### 5.3 成熟度与门槛

| 成熟度 | 进入条件 | 检查器执行 |
|---|---|---|
| 提出 | 问题与范围已写下 | — |
| 调研 | 已有来源登记或案例 | — |
| 成稿 | 主文档完成，状态说明完整 | — |
| 已审 | 有权限的人完成人工研究审核，并留下记录 | 要求 `human_review` 为 `passed` |
| 已检验 | 至少一项承重主张有实际执行的实验或观测 | 另要求 `experiment` 不为 `not-run` |
| 稳定 | 已审、已检验，近期没有未处理的反证 | 同上 |
| 退役 | 被取代或不再维护；保留文件供追溯 | — |

当前六个专题都处于“成稿”。从“成稿”走到“已审”，是[阶段性综合](../../book/part1-method/1-4-ownership-evidence-bound.md)第 9 节列出的优先事项之一。

## 6 命题登记

**本节结论：命题是跨专题的最小知识单元；它有稳定编号、类型、状态、证据位置和推翻条件，修订只追加历史，不删除。**

### 6.1 什么值得登记为命题

登记**承重**的主张：被多个专题共同使用，被实践规则引用，或者一旦被推翻会改变某个决定。不登记每一句话。第一批 22 条命题提取自六个专题与阶段性综合。

### 6.2 字段

| 字段 | 含义 |
|---|---|
| `id` | `K-` 加三位数字；永不复用，被合并或撤回的编号也保留 |
| `statement` | 一句可被反驳的表述，写清范围 |
| `type` | 来源事实、特定案例、综合推论、逻辑论证、价值或规范立场、概念区分、待验证假设 |
| `status` | 提出、有支撑、受质疑、已推翻、已撤回 |
| `axes`、`topics` | 所属轴与来源专题；第一条轴决定在地图中的归类 |
| `evidence` | 证据所在的仓库文件与定位说明，至少一项 |
| `practice` | 引用它的[实践指南](../../book/appendix-a-practice-rules.md)规则编号 |
| `falsified_by` | 什么结果会推翻或收缩它；立场类可以写 `null` |
| `history` | 带日期的修订记录：改了什么、为什么 |
| `note`（可选） | 证据边界的补充，例如“静态阅读，未运行” |

### 6.3 状态规则

- 类型为“待验证假设”的命题不能标为“有支撑”。要升级，就先用实验结果把类型改成来源事实或案例，并在 `history` 写明依据。
- “有支撑”只表示在所列证据范围内成立，不表示经过人工审核或实验。
- 推翻与撤回不删除条目：改状态，写 `history`，并检查引用它的综合与实践规则。知识地图会把受质疑、仅提出和待验证的命题单独列出。

## 7 知识如何进入与演进

**本节结论：每一种变化都有固定的路径和需要同时更新的文件；改动由检查器把关，结论由人审核。**

| 变化 | 步骤 | 同时更新 |
|---|---|---|
| 新专题 | 写下问题与范围；建目录、README、`meta.json`（成熟度“提出”）；需要时登记来源 | 运行 `--write-index` 重新生成知识地图；变更记录 |
| 新证据或来源 | 登记到专题 `sources.md`；在正文相应位置引用；说明支持还是反对 | 受影响命题的 `evidence` 与 `history` |
| 反例 | 写清条件与推翻的范围；不先改结论 | 命题改为“受质疑”或“已推翻”；必要时收缩表述 |
| 实验结果 | 按[研究方法](../../book/appendix-h-research-method.md)的最低记录要求，存放在所属专题；失败与无收益结果同样记录 | 专题 `experiment` 状态与成熟度；相关命题的类型、状态与 `history` |
| 人工审核 | 审核人留下记录（范围、结论、未覆盖项） | 专题 `human_review` 与成熟度 |
| 修订观点 | 保留原判断、新证据、影响范围和理由 | 命题 `history`；专题 `last_revised`；变更记录 |
| 阶段性综合 | 每个研究阶段一份，文件名带年月，旧版本不改写 | 综合引用命题编号；实践指南的规则与命题对应 |
| 退役 | 专题成熟度改为“退役”，README 指向替代者 | 相关命题改状态或转移到新专题 |

## 8 编辑源与历史快照

**本节结论：本仓库是唯一编辑源；导出清单从此只用于追溯来源，不再要求公开文件与其中的哈希一致。**

所有者于 2026-11-15 决定，公开仓库成为唯一编辑源（[决策记录](../../docs/decisions.md) D-002）。由此：

1. 今后的修订、新专题、命题与综合都直接在本仓库中进行。私有研究稿冻结为历史档案，不再向本仓库导出覆盖。
2. 各专题的 `export-manifest.json` 保留在原位，作为“这些文件最初从哪里来、经过哪些转换”的来源记录（专题元数据的 `provenance`）。其中的 `export_sha256` 与 `public_revision` 只证明当时的文件身份，之后的修订不再更新它们。
3. [发布说明](../research/PUBLICATION.md)中“私有研究版本是编辑源”的条款由 D-002 取代；其中的隐私、排除与授权边界继续有效。
4. 专题正文里保留的“原稿”“导出”等措辞是历史语境，按需在修订时更正，不做批量替换。

## 9 规模化：专题增长几倍后仍然好用

**本节结论：规模扩张靠数据和生成，而不是加目录层级；以下触发条件出现时再调整，不提前建设。**

| 触发条件 | 调整 |
|---|---|
| 专题超过约 15 个 | 知识地图按领域分组展开；首页只列领域入口和最新文章 |
| 某个领域有 4 个以上专题 | 为该领域写一篇领域综述（L3），引用命题而不复述 |
| 命题超过约 150 条 | 命题登记按轴拆成多个文件，编号规则不变 |
| 出现第二份阶段性综合 | 考虑把综合与实践从 `docs/` 移到独立目录（见第 11 节 P2） |
| 实践指南规则大幅增减 | 指南按版本发布，旧版本存档；每条规则注明所依据的命题 |
| 术语对照出现跨专题冲突 | 先在[术语与分级对照](../../book/appendix-b-glossary.md)登记，再决定是否统一用词 |

## 10 检查器保障什么，不保障什么

**本节结论：检查器保障结构一致，不保障内容正确。**

`python -I scripts/check_docs.py` 当前检查：

- 必备文件、首页导航、Markdown 子集、仓库内链接与两份保真导入件的完整性。
- 每个专题都有 README、合法的 `meta.json`、存在的主文档与来源记录，取值都在受控词表中，`related` 指向存在的专题。
- 成熟度门槛：“已审”及以上要求人工审核通过，“已检验”及以上要求实验已执行。
- 命题编号唯一，类型与状态合法，证据文件存在，引用的实践规则编号在指南中存在，待验证假设没有被标为“有支撑”。
- [知识地图](../knowledge/README.md)与当前数据一致；不一致时提示运行 `python -I scripts/check_docs.py --write-index`。

它不检查：命题是否真的被证据支持，定位说明是否准确，专题正文是否与元数据描述相符，外部链接、Unity 行为或任何研究事实。这些仍靠人工审核。

## 12 这个架构可能在哪里失败

**本节结论：如果元数据的维护成本超过它带来的可查找性，就应该收缩它。**

- **登记变成复述**：命题登记如果开始重写专题论证，就违背了“只引用不复制”。信号是命题表述越来越长，或证据栏只指向综合而不指向专题。
- **词表僵化**：如果新研究反复需要词表外的取值，说明分类本身需要修订，而不是继续塞进旧类别。
- **状态失真**：元数据说“有支撑”，正文却已被修订推翻。缓解方法是把命题 `history` 与专题修订放在同一次提交中，由审阅者对照。
- **成本过高**：若一年内知识地图与命题登记很少被使用，也没有帮助发现过冲突或过期结论，应把它们缩减为专题列表，并在决策记录中说明。
