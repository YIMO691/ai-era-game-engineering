# 3.1　迟到的结果：谁拒绝，谁释放

*原题：Unity 场景退出后，谁拒绝旧 Task 结果并释放资源？*

> **本章导读**：第1.2章的界面案例提出了一个问题：旧请求的结果晚到时，它还有权更新界面吗？本章把这个问题放回 Unity 的固定版本源码中，把一次看似简单的 await 拆成三个不能互相推出的问题：在哪里执行、此刻还能不能提交、资源由谁释放。这是全书“责任”一轴最具体的一章。

> **本章证据状态**：源码支持的机制分析与设计提案，不是已运行验证的 Unity 方案。目标为 Unity 6000.0.85f2 的 `System.Threading.Tasks.Task` 与 MonoBehaviour 主线程入口；已读固定版本 C# reference，Unity/.NET 官方网页正文访问受阻；Task 上下文捕获、取消协议与原生销毁时序仍有证据缺口；示意代码未编译、未运行。人工研究审核 pending。来源 ID、定位与访问状态见[共用来源](../../archive/research/unity-task-lifetime/sources.md)。

## 结论

**场景局部的异步结果，应当由业务 owner 决定它现在是否仍有提交资格，由调用方与生产者之间的交接协议决定每个结果由谁释放。** 取消用于请求减少不再需要的工作，但在缺少底层契约时，不能被当作“已停止、不会返回资源、无需清理”的证明。

这是一项有条件的设计判断，不是 Unity 官方替你完成的通用机制。已读的取消入口只看到发出取消信号，主线程队列只处理回调与状态，场景卸载绑定把工作交给原生实现；这些范围内没有出现任意用户 Task 的 owner 或结果释放协议（ER-20261105-unity-task-01、02、04）。“没有在这里看到”不等于完整引擎或某个第三方 API 一定不提供，采用前必须核对具体生产者的成功、取消、异常与资源交接契约。

## 1 三个问题不能合并成一个 await

设一个界面请求加载场景相关数据：

1. 请求 A 启动，携带当时的 owner 与请求代次。
2. 用户离开界面，或同一对象发起请求 B。
3. A 产生结果，等待接收或提交。
4. 接收路径恢复执行。

这里至少有三个独立的判断：

| 判断 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 执行位置 | 当前线程能否调用目标 Unity API？ | 不能证明 A 仍是当前请求 |
| 提交资格 | owner 仍接受结果，且 A 没有被替代吗？ | 不能证明没人需要释放 A 的结果 |
| 资源归属 | 资源此刻归生产者、接收路径还是 owner？ | 不能证明 owner 仍存活 |

**关键反例**：即使对象没有被销毁，请求 B 也能令 A 失效。这个反例不依赖“退出场景后必然发生某个帧回调”的时序假设，所以“对象有效就可以写”不成立。

**关键原则**：即使 A 已经失效，它的结果也可能仍需清理。**“不提交”与“不负责”不是同义词。**

## 2 固定源码建立的四条边界

### 2.1 取消入口只是一个信号入口〔源码〕

ER-20261105-unity-task-01 的 getter 在对象失效时有异常分支，token source 懒创建，`RaiseCancellation` 调用 `Cancel`。由此可推出：需要这个 token 的路径应在对象仍有效时取得它，不要等迟到回调才首次访问已失效 MonoBehaviour 的 getter。

源码没有展示原生何时调用 `RaiseCancellation`，也没有展示任意生产者如何处理 token。因此本文不指定它与 `OnDestroy` 的精确先后，也不宣称它覆盖业务“开始退出”到原生销毁之间的所有窗口。

### 2.2 同步上下文是调度机制，不是业务 owner〔源码〕

ER-20261105-unity-task-02 显示：`Post` 将回调与状态加入队列，`Exec` 取出并调用，初始化时设置 `UnitySynchronizationContext`；`WorkRequest` 保存回调、状态和等待句柄，没有业务 owner 字段。

可得的推论是：**即便某个 continuation 已投递到这个主线程队列，仍需另行判断业务有效性。** 不能反过来推出所有 Task await 都经过这个队列。是否捕获上下文、同步完成、后台入口、`ConfigureAwait(false)` 与实际运行时语义，需要另查契约并在目标环境核对（来源 05、10 未核验）。

内部 `ExecutePendingTasks` 存在超时循环，不代表应用退出时任意任务都能被无限等待或必然清理。本文不提供进程终止或强杀后 `finally` 一定执行的保证。

### 2.3 Unity 对象有效性不等于请求身份〔源码〕

ER-20261105-unity-task-03 的 `CompareBaseObjects` 区分托管引用与原生对象是否存活，所以不能用 CLR 引用仍在来证明 Unity 对象可用。反过来，Unity 对象仍有效也不能证明它仍在展示请求 A：对象池复用、重复打开、同一界面切换目标都会改变业务身份。

### 2.4 场景卸载跨过了原生边界〔源码〕

ER-20261105-unity-task-04 展示的是包装与 extern 绑定，不是完整的原生卸载过程；`Object.Destroy` 也是原生绑定（03）。本研究不能据此确认卸载的所有销毁时点、各类资源的释放方式或任意 Task 的取消行为。

因此正确的措辞不是“场景卸载永远不会释放资源”，而是**“不能只凭已读绑定，假定场景卸载已替你的异步结果履行了具体资源 API 的释放责任”**。持久化 owner、共享缓存和引用计数句柄各有契约，不能把 `IDisposable`、`Object.Destroy`、`Release` 当同义词混用。

## 3 提交资格：由 owner 管理请求身份〔设计〕

- 由 owner 管理一个请求代次或唯一请求标识，在发起新请求、退出界面、归还对象池、同一实例重开时更新。
- 对“关闭后重新打开但复用同一实例”的情形，单一 alive 布尔值区分不了两次会话。
- 唯一性范围与溢出策略由具体工程确定，不能把一个裸 `int` 宣称为无限期身份保证。
- 若业务在切换动作开始时就不再接受结果，应由业务退出入口立即撤销提交资格，而不是等待未经核验的销毁信号时点。
- **先撤销资格或更新身份，再请求取消**，以免取消回调重入时旧请求仍被视为有效。

资格检查至少包含业务有效期与请求身份；token 状态只是其中一个输入。

## 4 资源交接协议〔设计〕

本节是本研究提出的协议模型，不是源码事实。适用前提：一个结果有单一释放责任；接收、资格检查与提交在 owner 规定的同一线程串行执行；检查到接管之间没有 await、没有可重入回调；释放 API 的线程与异常契约已明确。

| 阶段 | 责任方 |
|---|---|
| 生产者返回前 | 生产者负责取消或异常时其内部已分配、尚未交出的资源。调用方看不到的资源，调用方无法补救 |
| 成功返回后、接管前 | 接收路径临时持有；不论取消、过期还是提交前异常，都必须走释放路径 |
| 接管成功后 | owner 负责最终释放；接收路径清空临时引用，避免 `finally` 二次释放 |
| 接管失败 | 保持原归属；不能出现“已存到 owner 后又抛异常，调用方却以为没接管” |

两条延伸要求：

- 若生产者不返回但一直占用资源，下面的 `finally` 不会凭空运行；需要上层服务管理超时、未完成工作与生命周期。
- 若生产者在消费者提前返回后才完成，必须另有路径接收并清理迟到结果。**不要把“停止等待”实现成“无人负责后续结果”。**

取消回调异常、嵌套调用与线程切换不在这个简化模型内，生产实现必须另行设计。

### 接收算法示意（C# 形态，未编译、未运行）

```csharp
// 外部契约均需实现与验证；这不是可直接粘贴的 Unity 脚本。
async Task ReceiveAsync(RequestId id, CancellationToken token)
{
    OwnedResult pending = null;
    try
    {
        pending = await ProduceAsync(token);
        // 前提：此处已处于 owner 线程，ProduceAsync 成功返回非 null。
        if (token.IsCancellationRequested || !IsCurrent(id))
            return;

        AdoptWithoutCallbacks(pending);
        // 契约：Adopt 成功才转移责任；若抛异常则不得已接管。
        pending = null;
    }
    finally
    {
        pending?.Dispose();
    }
}
```

`RequestId`、`OwnedResult`、生产者、`IsCurrent`、`Adopt` 都是待实现的项目契约，不是 Unity API。这里不吸收取消异常，取消与其他异常继续传播，由调用方观察 Task 并按生产者契约归因；只检查本 token 已取消，不能证明异常来自该 token。`Dispose` 假定在当前线程合法且不会掩盖原异常；若不成立，需要专用的清理与异常合并方案。

这段算法**不负责**证明 await 后的线程、实现业务退出入口、清理 owner 已接管的结果，或保证运行时一定执行 `finally`。它只展示责任转移点，删掉这些前提后不能称为“通用安全模板”。

## 5 方案比较

| 方案 | 成本与优势 | 漏洞与适用边界 | 本研究判断 |
|---|---|---|---|
| await 后只判对象有效 | 简单；可拒绝部分已销毁对象的访问 | 对象仍活而请求已替代时无效；未说明资源释放 | 只适合作为一项检查，不是完整协议 |
| 只传销毁 token | 能表达 owner 销毁时的停止意愿；接入成本低 | 原生触发时点和生产者响应需核验；同实例新请求未必销毁；未规定交接 | 不能独立作为完成证明 |
| 请求身份 + 取消 + 明确交接 | 同时回答提交资格与释放责任；能处理迟到成功 | 引入身份与状态管理；要求线程、重入与资源契约；可能与底层库保障重复 | 有条件推荐，需补证和运行验证 |
| 交给跨场景服务 | 长任务不随界面消失；统一管理结果与缓存 | 服务仍要处理订阅失效、资源预算与消费者交接；不是“永久 owner”就免清理 | 工作本身跨场景有价值时更合适 |

**何时不照搬**：目标 API 已提供完整的 owner、取消与释放契约时，直接复用以减少额外状态；结果是无独立释放责任的纯托管不可变值时，可以简化交接部分，但仍要判断是否允许回写；结果是共享或引用计数资源时，独占 `Dispose` 必须换成对应的获取/归还协议。

## 6 失败路径与验证设计（未执行）

| 条件 | 应保持的不变量 | 可能推翻或修订设计的观察 |
|---|---|---|
| 正常成功且当前请求有效 | 只接管一次，最终只释放一次 | 接管失败后 owner 和 `finally` 同时释放 |
| 退出后迟到成功 | 不提交；接收者清理未接管结果 | 没有 continuation 接收结果，或释放线程非法 |
| 同一对象 A/B 请求倒序完成 | A 不覆盖 B | alive 和 token 都正常，但 A 仍通过资格检查 |
| 生产者内部取消或异常 | 生产者清理未交出资源；异常可观察 | 内部资源从未交出却无人释放 |
| 检查后发生重入 | 资格检查与提交不断裂 | Adopt 回调触发退出后仍提交，需要修改交接设计 |
| owner 已接管后退出 | owner 清理已接管结果 | 调用方与 owner 责任重叠或都未释放 |

是否在独立的最小 Unity 工程中执行由仓库所有者决定。执行时应记录 Editor 补丁、运行时与后端、平台、线程 ID、请求 ID、业务失效时点、token 状态，以及结果交出、接管、释放事件与异常，逐条复现并保留原始日志。**计数和顺序才是证据，一次“没报错”不能代替所有权验证。**

## 7 现在能决定什么，不能决定什么

**能决定**：审查异步代码时分别追问线程、提交资格与资源归属；不因写了取消或 await 就默认生命周期问题已解决；提前取得需要的销毁 token；不把主线程队列当业务 owner。

**还不能决定**：目标工程中某套 API 的精确退出顺序、Task continuation 的实际线程保证、某类资源的具体释放方法、性能收益，以及示意代码能否直接上线。补充官方契约后应同步复查本文与[教学文章](../../archive/research/unity-task-lifetime/blog.md)。

## 8 下次看到“await 后更新界面”时问的三个问题

1. **执行位置**：这行 Unity API 调用的线程依据是什么？
2. **提交资格**：对象仍活之外，这是不是当前那次请求？
3. **资源归属**：如果不收这个结果，谁释放它？收下以后又归谁？

## 本章小结

- await 返回后要分别回答执行位置、提交资格、资源归属三个问题。
- 提交资格由业务 owner 管理的请求身份决定；对象仍有效不等于请求仍有效。
- 取消只是请求减少工作，不证明不会再返回资源；“不再需要”不等于“不再负责”。
- 本章的机制来自静态源码阅读，示意代码未编译、未运行。
