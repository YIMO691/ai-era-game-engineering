# 8.1　AI 工作链

*原题：AI时代的高质量代码生成与工程实践体系*

> **本章导读**：第八篇讨论 AI 协作与团队。本章的问题是：让 AI 写出高质量代码，靠的是更强的生成工具，还是更好的工作链？本章对候选工具做了静态源码取证，结论是把项目约束、最小修改、可执行检查、定向审查与反馈接起来，比安装全套插件更值得。

> **本章证据状态**：原稿 2026-11-05，awaiting_review，人工研究审核 pending。这是**静态源码研究与采用设计**，不是工具效果实验：继承旧题指定的七份正文并核对旧快照；读取用户指定候选的 README、定义、关键实现、依赖与许可，并补充四类 C#/Unity 工具；所有仓库固定完整 SHA，来源唯一登记于[sources](../../archive/research/ai-code-quality-workflow/sources.md)。候选安装、插件执行、业务工程修改、Unity 编译与测试、目标设备 Profiling、人工对照均未进行。Claude Code 三份宿主文档及 Unity analyzer 导入文档在访问的安全验证阶段失败（F1/F2），没有正文，因此 Rules 自动匹配、完整 Hooks 语义、用户的 Unity/UTF/Roslyn 版本与发布包兼容仍未知，本题不交付可直接启用的 Hook 配置或已验证的 Unity 测试命令。

## 结论

**最值得采用的不是一个“好代码生成器”，而是把项目约束、最小修改、可执行检查、定向审查和规则反馈接成一条可追溯的工作链。** 对当前 Unity/C# 使用者，推荐保留现有 Claude Code，先复用旧指南和工程已有工具；没有证据支持现在新增 `client-code-quality` Skill、安装全套插件或更换 Agent 平台。

本报告与[能力矩阵](../../archive/research/ai-code-quality-workflow/capability-matrix.md)回答“选什么、为什么”；采用方案、配置设计、Unity 适配和实施指南回答“以后如何小步验证”。

## 1 问题不在于再写一套 Clean Code

**本节结论：新增价值是把已有的质量知识映射到具体决策点，并分清每一层工具能负责什么。**

前置的[第7.1章（客户端代码质量）](../part7-craft/7-1-client-code-quality.md)已经提供质量指南、案例、审查清单和训练路线。本题要回答的是它们在工作流中落在哪里：

1. 开始任务时：读哪些事实，哪些知识按需带入？
2. 改代码时：哪些契约不可动，何时必须停下来确认？
3. 检查时：哪些由程序回答，哪些仍需 AI 或人判断？
4. 审查后：怎样证伪发现、限制修复范围、重新验证？
5. 下次任务：哪些经验值得变成规则，哪些应删掉？

| 层次 | 能做什么 | 不能做什么 |
|---|---|---|
| 知识文档 | 影响模型的输入 | 强制模型遵守 |
| Skill、Agent | 组织调用 | 证明输出正确 |
| 分析器 | 执行指定的语法或语义规则 | 判断业务意图与职责 |
| 测试 | 在具体环境下验证样例 | 证明未覆盖的行为 |
| 人 | 意图、取舍与授权 | 替代运行证据 |

把这几层混称“自动质量系统”，会把建议误当强制、把自评误当证明。

## 2 研究方法与停止理由

**本节结论：按固定源码而非宣传排名比较，跨候选反复出现的风险已足以决定低维护路径。**

访问日期 2026-11-05。本机只读探测得到 Claude Code 2.1.310、gh 2.97.0 及插件相关帮助（C1）。比较依据是固定源码，而不是 Star 或宣传排名；HEAD 不冒充 release，近期 push 不冒充该模块仍在维护。主线程研究官方生态，三个限定取证分别覆盖 ECC、OpenHands、CodeRabbit 与工具，主线程重读决定性段落并整合来源。这种分工是取证方式，不是“多 Agent 更有效”的实验。

判据依次是：与 Unity 问题的语义距离、可验证输出、权限与数据外发、误报与修改边界、维护成本、宿主兼容、撤回成本。没有按“优雅程度”打总分。未读全仓、第三方仓或完整依赖链的缺口保留，不用无限检索掩盖缺乏运行实验。

## 3 成熟项目：采用什么，而不是安装什么

**本节结论：每个候选都有值得借鉴的机制，也都有不能默认整套采用的理由。**

### 3.1 官方四插件：借鉴明确，默认全套不成立（O1）

- **feature-dev**：最值得借鉴的是探索质量——从真实入口追踪调用、数据变化、副作用与既有模式，返回关键文件由主线程亲自读，实现前有批准闸门。完整流程约 7–9 次子 Agent 调用，不适合作为小改的默认；读过的定义里没有可执行的 Unity 验证矩阵。
- **pr-review-toolkit**：提供代码、测试、注释、错误、类型、简化六类角色，允许按风险选择。最适合小范围试验的是代码与测试专项阅读。但错误角色假设 Sentry/Statsig 等 Web 约定，类型角色的 1–10 分是主观框架，简化角色会主动修改，所以它不是纯只读审查器。
- **code-review**：有逐项复核和默认终端输出，`--comment` 才进入对外评论。但实际 command 与 README 不同；实际定义排除了依赖特定输入或状态的问题，且不运行 linter。这与 Unity 停用、销毁、迟到结果等高风险缺陷不匹配，不能因“官方”而默认完整覆盖。
- **code-simplifier**：强调最近修改与行为保持，但只是提示目标，不是等价验证器，且有 React/ES modules 偏置并会主动修改。可借鉴“局部、清晰优先于短小”，不应接在每次编辑后自动运行。

### 3.2 官方 Skills：组织知识，不是质量证明（O2）

渐进加载适合把简短入口与按需指南分开。skill-creator 提供 baseline、断言、人工反馈与可选盲比较的研究思路，但触发率与代码质量是两回事；所读脚本存在 token 缺失时用字符数、前两组按发现顺序比较、固定 3 次元数据等陷阱。当前先用现有能力显式读旧资料，只有稳定的重复摩擦出现，才讨论封装 Skill。

### 3.3 ECC：有实物，但不能整套当 Unity 质量门禁（E1）

实际存在开发流程、TDD、清理及 C# reviewer，可以局部借鉴。但 C# 提示偏 .NET/Web，`ConfigureAwait(false)`、50 行、record、DI 等不能直接成为 Unity 硬规则。**决定性反证**是 quality-gate：没有 `.cs` 分支，strict 只影响部分日志，dispatcher 把退出码归一化为 0。它不是本题需要的阻断式门禁（不能由此推断 ECC 所有 hook 都不阻断）。加上 Stop 时自动格式化与类型检查、未读完整的安装与回滚、可选的跨提供方 diff 外发，结论是不整套安装，只借鉴流程与规则治理。

### 3.4 OpenHands：研究执行边界，不替换现有平台（H1/H2）

当前主仓已是 Agent Canvas，执行、会话与工具在 software-agent-sdk 中。它不是可直接塞进当前 CLI 的小插件，还引入 Node/Python/Server 等维护面。可借鉴三个原则：**保存动作与观察；核对真实终态；恢复时检查外部副作用。** SDK 明示重放的工具调用不幂等；basic 示例在 run 返回后直接写成功，而 local run 可能以 ERROR/STUCK 返回而不抛异常——这是已定位、未复现的静态风险。换平台增加的成本没有对应的证据收益。

### 3.5 CodeRabbit：开源 Skill 不等于离线开源审查（R1）

Skill 调用可信 CLI，经认证把 diff 及所需上下文发送到 CodeRabbit 服务；autofix 另经 gh 交换 PR 数据。结构化输出、区分 heartbeat/skipped/completed、逐项批准最小修复值得借鉴；但 severity 不是修复授权，整文件 staging 也不能保证只提交批准的改动。服务合同、数据保留与费用未核验，当前暂缓。

### 3.6 C#/Unity 工具：确定性规则优先，但兼容与语义仍要验证

- **Microsoft.Unity.Analyzers（U1）**：最贴近当前场景的确定性候选。UNT0012 识别特定未使用的 IEnumerator 调用，serialized suppressor 保护若干序列化字段诊断；两者都不证明业务意图或资产实际引用。先查 IDE 是否已随附，避免重复安装。
- **StyleCop（S1）**：约束团队风格与组织，SA1402 不判断架构设计；最新列出版本是 beta。没有稳定风格需求时无需新增，不全量设为 Error。
- **Roslynator（A1）**：诊断与重构丰富，部分 Unity 回调有条件保护；unused 修复会真正删除节点，无法证明 scene、prefab 或反射可达性。只考虑白名单诊断，不无人值守地 Fix All。
- **NetArchTest（N1）**：对显式程序集与类型的命名空间依赖方向做断言，不自动发现合理架构；HEAD 与 release 陈旧，依赖 Cecil 非公开 API。仅在确有硬边界时试点，配非空、关键类型与故意违约的负例。

## 4 推荐的工程闭环

**本节结论：每个阶段都有一种典型的“假完成”，闭环的作用是把它们挡住。**

| 阶段 | 要做什么 | 要挡住的假完成 |
|---|---|---|
| 编码前：事实简报 | 任务卡记录行为目标与非目标、允许修改范围、入口与调用链、状态 owner、资源交接、错误与取消约定、影响的资产与平台、验证方法与未知项。模型读相关实际文件，给出 file:line 与类似实现，复述不可改变的契约。重要架构冲突先确认 | 读不到的文件被当成“已理解” |
| 编码中：以契约保持清晰 | 先完成一个可验证的最小切片；行为修改与风格清理分开；抽象只服务已知的共同变化原因。新增依赖、公开 API、序列化字段、程序集方向、线程与所有权策略都会扩大范围，应重新确认；简化先给提案和行为不变清单 | “顺手”重构扩大了范围 |
| 验证：确定的交给程序 | 用已有的编译器、格式器、分析器、测试执行明确规则；记录原始命令、版本、退出码、新鲜报告、实际执行的测试集合与未运行项。Unity Editor 编译、PlayMode、Player/IL2CPP 与设备性能是不同的层 | 无相关测试、空的架构选择集、skipped、旧 XML 被当成通过 |
| 审查与修复：角色独立不等于证据独立 | 审阅者先只读 diff、必要周边、约束与验证记录；发现写成“输入或状态 → 路径 → 后果 → 位置 → 最小修复 → 验证方式”，分硬缺陷、设计讨论、可选风格，严重性与确信度分开。作者逐项接受、反驳或待证，不以多票合并；修复后重跑相关验证并保留最终 diff | 审查前的结果覆盖修复后的状态 |
| 反馈：只沉淀重复且已确认的失败 | 单次 AI 意见先不入规则。确认重复后记录规则 owner、适用范围、失败证据、例外、执行器与撤销条件。可程序化的进入测试或分析，意图性约束留短文档，细节案例按需加载；过时或噪声高的规则删除或降级 | 规则无限膨胀，“持续学习”无人维护 |

## 5 八个问题的直接答复

| 问题 | 回答 |
|---|---|
| 最值得采用哪些成熟项目？ | 优先盘点与核验 Unity 分析器；借鉴 feature-dev 的探索与 toolkit 的按风险审查；Skills 只借鉴按需组织。其余依需求而非整套安装 |
| 哪些直接改善代码质量？ | 确定性诊断与测试反馈更可核查；toolkit 等提供审查线索。实际改善程度未知，不能从提示定义推导收益 |
| 编码前如何理解架构约束？ | 任务卡 + 真实调用链、owner 与关键文件 + 相似实现 + 未知项与批准闸门 |
| 编码中如何保持质量？ | 最小可验证切片、行为契约、局部命名与职责、由变更原因驱动的抽象；不按行数或模式数量评分 |
| 怎样独立审查且不过度重构？ | 从一个风险定向的只读角色起步，逐项复核，设计与风格不当作硬缺陷；简化另提案，修复后再验证 |
| 哪些交给程序？ | 编译、选定的格式与诊断、行为回归、显式依赖约束；Unity 资产、生命周期、Player 与设备按对应环境验证 |
| 如何融入旧成果？ | 指南用于编码前选段；案例用于风险与测试设计；清单用于审查分类；训练用于人工修改练习；来源用于证据边界——不复制整套常驻 |
| 最小低维护组合？ | 现有 Claude Code + 短项目契约或任务卡 + 按需旧资料 + 已有的确定性检查链 + 定向审查 + 反馈记录；零新增包也能开始 |

## 6 何时改变推荐

这是与当前约束匹配的设计判断，不是普遍最优。若后续授权试点证明某个单项插件在相同任务与预算下减少人工返工或漏缺陷，且不扩大 diff，可以保留；若它只多输出意见、引入风格噪声或增加权限成本，就不采用。若重复流程无法稳定触发且已有提示确实不足，才比较专用 Skill：先测触发，再测任务效果，两者不能互相替代。

当前证据只允许进入“文稿待人工审核”，不允许宣称方案已部署、代码已验证、质量已提升或发布就绪。最终核验记录见[review](../../archive/research/ai-code-quality-workflow/review.md)。后续综合见 [第8.2章（AI-CQEP）](8-2-ai-cqep-protocol.md)，可执行规则见[附录A（工程实践指南）](../appendix-a-practice-rules.md)第 6、7 章。

## 本章小结

- 价值不在再写一套代码规范，而在把已有质量知识映射到具体决策点。
- 每一层工具只能负责它能负责的部分：文档影响输入，分析器执行规则，测试验证样例。
- 推荐保留现有工具链，先复用已有规范与工程工具，再小步验证。
- 本章是静态研究与采用设计，候选工具未安装、未运行。
