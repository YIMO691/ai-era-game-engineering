# AI时代的高质量代码生成与工程实践体系

> 公开导出说明（2026-11-12）：以下为原稿研究或通用模板，不是实际配置；历史状态、检查与未运行项不因公开授权而升级。来源与排除边界见 [README](README.md) 和 [导出清单](export-manifest.json)。

## 结论与证据边界

**最值得采用的不是一个“好代码生成器”，而是把项目约束、最小修改、可执行检查、定向审查和规则反馈接成一条可追溯的工作链。** 对当前Unity/C#使用者，推荐保留现有Claude Code，先复用旧指南和工程已有工具；没有证据支持现在新增`client-code-quality` Skill、安装全套插件或更换Agent平台。

这是一项**静态源码研究和采用设计**，不是工具效果实验。已继承旧题指定七份正文并核对旧快照；读取用户指定候选的README、定义、关键实现/依赖/许可，并主动补充四类C#/Unity工具。所有仓库固定完整SHA，来源唯一登记于[sources](sources.md)。候选安装、插件执行、业务工程修改、Unity编译/测试、目标设备Profiling和人工对照均未进行。

**显著缺口：** Claude Code三份宿主文档及Unity analyzer导入文档在WebFetch安全验证阶段失败（F1/F2），没有正文；不绕过。Rules自动匹配、完整Hooks schema/阻断语义、用户Unity/UTF/Roslyn版本与发布包兼容仍未知。因此本题不交付可直接启用的Hook JSON或声称已验证的Unity测试CLI。旧题仍为人工pending，其11例未编译/运行，本题不提升该证据强度。

本报告与[能力矩阵](capability-matrix.md)回答“选什么、为什么”；[采用方案](adoption-plan.md)、[配置设计](claude-code-configuration.md)、[Unity适配](unity-csharp-adaptation.md)、[实施指南](implementation-guide.md)回答“以后如何小步验证”。后五份不是已部署记录。

## 1. 问题不在于再写一套Clean Code

旧题B1已经提供质量指南、案例、审查清单和训练路线。本题的新增价值是把它们映射到具体决策点：

1. 开始任务时：读哪些事实，哪些知识需要按需带入？
2. 改代码时：哪些契约不可动，何时必须停下来确认？
3. 检查时：哪些由程序回答，哪些仍需AI/人判断？
4. Review后：怎样证伪发现、限制修复范围，并重新验证？
5. 下次任务：哪些经验值得变规则，哪些应删掉？

知识文档只能影响模型输入；Skill/Agent只能组织调用；分析器执行指定语法/语义规则；测试在具体环境下验证样例；人工负责意图与取舍。把这几层混称“自动质量系统”，会把建议误当强制、把自评误当证明。

## 2. 研究方法与停止理由

访问日期2026-11-05。本机只读探测得到Claude Code 2.1.310、gh 2.97.0及插件相关help（C1）。固定源码而非Star/宣传排名；HEAD不冒充release，近期push不冒充该模块功能维护。主线程研究官方生态，三个限定取证分别覆盖ECC、OpenHands、CodeRabbit/工具；主线程重读决定性段落并整合来源。分工是取证方式，不是多Agent更有效的实验。

判据依次是：与Unity问题的语义距离、可验证输出、权限/外发、误报与修改边界、维护成本、宿主兼容、撤回成本。没有按“优雅程度”给总分。跨候选反复出现的风险已经足以决定低维护路径，故停止扩展仓库；未读全仓、第三仓或完整依赖链的缺口保留，不用无限检索掩盖缺乏运行实验。

## 3. 成熟项目：采用什么，而非安装什么

### 3.1 官方四插件：借鉴明确，默认全套不成立（O1）

**feature-dev**最值得借鉴的是探索质量：从真实入口追踪调用、数据变化、副作用和既有模式，返回关键文件，主线程亲自读；实现前有批准闸门。完整流程包括2–3探索、2–3架构和3审阅子agent，约7–9次调用，不适合作为小改默认。读过的定义没有可执行Unity验证矩阵，工具名映射也未实测。

**pr-review-toolkit**提供代码、测试、注释、错误、类型、简化六类角色，命令允许按风险选择，不要求全部运行。最适合小范围试验的是“代码/测试专项阅读”。但错误角色假设Sentry/Statsig等Web约定，类型角色的1–10分是主观框架；简化角色会修改，所以整个toolkit不是纯只读审查器。

**code-review**有逐项复核和默认终端输出，`--comment`才进入对外评论路径。但实际command与README不同：README的blame/0–100/80阈值不是当前command完整机制。实际定义排除依赖特定输入或state的问题，且不运行linter；这与Unity停用/销毁、迟到结果等高风险缺陷并不匹配。不能因“官方”而默认完整覆盖。

**code-simplifier**强调最近修改和行为保持，却只是提示目标，不是等价验证器。独立版与toolkit版均有React/ES modules等偏置，并要求主动修改。可借鉴“局部、清晰优先于短小”，不应原样接在每次编辑后，更不能由缩短代码推导可维护性提升。

### 3.2 官方Skills：组织知识，不是质量证明（O2）

渐进加载适合把简短入口与按需指南分开。skill-creator提供baseline、断言、人工反馈和可选盲比较的研究思路，但触发率与代码质量是不同问题。所读run_eval写临时commands并启动claude；aggregate存在token缺失用字符数、前两组发现顺序比较、固定3次元数据等陷阱。未运行这些脚本，不把示例数字或模型grader当独立验证。当前先用现有能力显式读旧资料；只有稳定的重复摩擦出现，才讨论封装Skill。

### 3.3 ECC：有实物，但不能整套当Unity质量门禁（E1）

实际存在开发流程、TDD、清理及C# reviewer，可局部借鉴。C#提示偏.NET/Web，ConfigureAwait(false)、50行、record/DI等不能直接成为Unity硬规则。决定性反证是quality-gate：没有.cs分支，strict只影响部分日志；返回原输入字符串后dispatcher归一化exitCode=0。它不是本题需要的阻断合并门禁，也不能由此推断ECC所有hook都不阻断。

当前绑定还包含累积改动后Stop自动格式化/类型检查；旧注释不完全反映新链。未读完整installer/依赖解析/回滚，README有用户级设置和可选跨提供方diff外发。故不整套安装，只借鉴流程和规则治理。

### 3.4 OpenHands：研究执行边界，不替换现有平台（H1/H2）

旧All-Hands入口当前canonical是OpenHands/OpenHands，主仓已是Agent Canvas；执行/会话/工具在software-agent-sdk。它不是可直接塞进当前CLI的小插件，还引入Node/Python/Server等维护面。

可借鉴三个原则：保存动作与观察；核对真实终态；恢复时检查外部副作用。SDK明示rerun工具非幂等；事件保存顺序不保证跨系统exactly-once。basic示例在run返回后直接写成功，而local run可因iteration/stuck以ERROR/STUCK返回不抛异常，这是已定位的静态风险、未复现。PR review实现委托第三仓，本轮未取得其内部实现，不能宣称已验证独立reviewer。对当前题目，换平台增加的成本没有对应证据收益。

### 3.5 CodeRabbit：开源Skill不等于离线开源审查（R1）

Skill调可信CLI，经认证把diff及所需上下文发送到CodeRabbit服务；autofix另经gh交换PR数据。结构化输出、区分heartbeat/skipped/completed、逐项批准最小修复有借鉴价值。severity不是修复授权，build/lint建议不是强制闸门。整文件staging也不能保证只提交批准的改动。

本轮未核验服务合同、保留/训练/子处理者或实际费用，不登录、不上传。不将公开issue中的历史零发现问题写成本次漏报实验。当前暂缓，除非以后确有独立服务需求并获数据外发授权。

### 3.6 C#/Unity工具：确定规则优先，但兼容与语义仍要验证

- **Microsoft.Unity.Analyzers（U1）**：最贴近当前场景的确定性候选。UNT0012识别特定未使用IEnumerator调用，CodeFix包StartCoroutine；serialized suppressor保护若干已识别序列化字段诊断。两者都不证明业务意图或资产实际引用。先查IDE是否随附，避免重复安装；源码开发SDK不等于Unity玩家runtime。
- **StyleCop（S1）**：约束团队风格和组织，SA1402不判断架构设计。最新列出版本是beta；shipping pin链未展开。团队没有稳定风格需求时无需新增，不全量Error化。
- **Roslynator（A1）**：丰富诊断/重构，部分Unity回调保护有条件；发布包变体/完整配置链未核验。unused CodeFix真的删除节点，无法证明scene/prefab/反射可达性。只考虑白名单诊断，不无人值守Fix All。
- **NetArchTest（N1）**：对显式程序集/类型的namespace依赖方向做断言，而非自动发现合理架构。HEAD和release陈旧，TypeParser依赖Cecil非公开API。仅在确有硬边界时试点，配非空、关键类型和故意违约负例；不替代资产关系检查。

## 4. 推荐的工程闭环

### 编码前：事实简报，而不是让AI背完整指南

任务卡记录行为目标/非目标、允许修改范围、入口和调用链、状态owner、资源交接、错误/取消约定、影响资产/平台、验证方法与未知项。模型必须读相关实际文件，提供file:line和类似实现，再复述不可改变的契约。读不到的文件不是“已理解”。重要架构冲突先确认，不为微小命名选择反复打断。

### 编码中：以契约和任务保持清晰

先完成一个可验证的最小切片；行为修改与可选风格清理分开。抽象必须服务已知共同变化原因，不按相似行数触发。新增依赖、公开API、序列化字段、程序集方向和线程/所有权策略都可能扩大范围，应重新确认。需要简化时先给提案和行为不变清单，不自动拉大重构。

### 验证：把能确定的判断交给程序

用已有编译器/格式器/分析器/测试执行明确规则；输出原始命令、版本、退出码、新鲜报告、实际执行测试集合和未运行项。无相关测试执行、空架构选择集、skipped、旧XML都不能当通过。Unity Editor编译、PlayMode、Player/IL2CPP和设备性能是不同层；普通.NET构建不替代它们。性能数字必须有目标设备和基线，本题无数字。

### 审查与修复：角色独立不等于证据独立

审阅者先只读diff、必要周边、约束和验证记录；输出“具体输入/状态→路径→后果→位置→最小修复→验证方式”，分硬缺陷/设计讨论/可选风格，严重性和确信程度分开。作者逐项接受/反驳/待证，不以多票合并。变更后重新跑相关验证，并保留最终diff快照；不要用审查前结果覆盖修复后状态。

### 反馈：把重复、已确认的失败转成最小规则

单次AI意见先不入规则。确认重复问题后，记录规则owner、适用目录/环境、失败证据、例外、执行器和撤销条件。可程序化的规则进入测试/分析；意图性约束留简短文档；细节案例按需加载。规则过时、噪声高或不再影响决策就删/降级，防止CLAUDE无限膨胀。无后台调度或自动“持续学习”承诺。

## 5. 八问直接答复

| 用户问题 | 本题回答 |
|---|---|
| 1. 最值得采用哪些成熟项目？ | 优先盘点/核验Unity分析器；借鉴feature-dev探索和toolkit按风险审查；Skills只借鉴按需组织。其余依需求而非整套安装 |
| 2. 哪些直接改善Claude代码质量？ | 确定性诊断/测试反馈更可核查；toolkit等提供审查线索。实际改善程度未知，不能由提示定义推导收益 |
| 3. 编码前如何理解架构约束？ | 任务卡＋真实调用链/owner/关键文件＋相似实现＋未知项和批准闸门 |
| 4. 编码中如何保持质量？ | 最小可验证切片、行为契约、局部命名/职责、变更原因驱动抽象；不按行数/模式数量评分 |
| 5. 怎样独立审查且不过度重构？ | 一个风险定向只读角色起步，逐项复核，设计/风格不当硬缺陷；简化另提案，修复后再验 |
| 6. 哪些交给程序？ | 编译、已选格式/诊断、行为回归、显式依赖约束；Unity资产/生命周期/Player/设备按对应环境验证 |
| 7. 如何融入旧成果？ | 指南→编码前选段；案例→风险/测试设计；清单→Review分类；训练→人工修改练习；sources→证据边界，不复制整套常驻 |
| 8. 最小低维护组合？ | 现有Claude Code＋短项目契约/任务卡＋按需旧资料＋已有确定性链＋定向Review＋反馈记录；零新增包也能开始 |

## 6. 何时改变推荐

这是与约束匹配的设计判断，不是普遍最优。若后续授权试点证明：单项插件在相同任务与预算下减少人工返工/漏缺陷且不扩大diff，可保留；若只多输出意见、引入风格噪声或增加权限成本，就不采用。若重复流程无法稳定触发且已有提示确实不足，才比较专用Skill；先测触发，再测任务效果，不能互相替代。

目前证据允许进入**文稿待人工审核**，不允许宣称方案已部署、代码已验证、质量提升或发布就绪。最终核验记录见[review](review.md)。
