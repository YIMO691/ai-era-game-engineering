## 1. 可交给Claude Code的首个实施任务

以下是**未来任务模板，未执行**。使用者须给出授权目录、测试环境、费用及模型处理通道；未明确前仅用已批准材料规划，不读取新源码进入上下文。Claude Code使用远端模型时，读到的源码可能进入发送给模型服务的上下文；不启用CodeRabbit不等于代码不离开本机。若要求任何代码都不出本机，必须先确认满足该要求的执行环境，未确认前不读源码。不要默认现有会话已获新工程数据处理授权。

```text
目标：在 <授权非生产沙盒绝对路径> 验证一个最小AI编码质量闭环。
允许读取：<明确目录与资料>；允许写入：<明确路径>。
允许模型处理的材料/目标服务或部署方式：<明确批准范围>。
禁止向批准模型通道以外的服务发送代码；批准通道也不得接收范围外材料。
禁止：全局Claude设置/Hooks/MCP、新服务、真实业务工程、
自动提交/推送/PR/评论、依赖升级、全仓格式化、删除式Fix All。
模型调用预算/最大尝试：<批准值>；不明则不启动新评测或第三方服务。

1. 只读检查工作区/Git状态，读取目标文件及现有CLAUDE/配置/验证入口。
   不覆盖未提交改动，不读取密钥或无关笔记。
2. 记录Unity/UTF/后端/API/平台/IDE/analyzer真实版本，未知显式列出。
   先核对已有能力，不安装候选。为本次任务输出一页简报和最小diff计划。
3. 拟定一个纯C#或Unity生命周期最小任务及可观察验收。
   把命令表、报告协议、需要审批的写入/执行列出，先取得具体批准。
4. 在批准范围内实现最小切片；若TDD，保留目标行为的真实红→绿记录。
   执行已有获批验证；错误/未执行/空集/skipped不能写成通过。
5. 需要审查时，先一个风险定向只读角色；不再委派、不编辑/提交/评论。
   主线程逐项核对，修改后重新验证最终diff。
6. 交付：简报、实际diff、命令/退出码/报告、发现处置、剩余风险、撤回说明。
   若要补插件或新Skill，先给现有能力不足的证据，另批后才试单项。
```

这不是要求当前会话实施，也不自动授权运行任何示例。批准应针对具体路径/操作/预算，而非一句“采用方案通过”就扩大范围。

## 2. 第一轮只建流程，不建平台

### 步骤A：盘点与任务简报

先读现有文件、Git状态和版本，不扫描整台机器。使用已有架构/测试入口，不先造`agents/skills/rules/hooks`树。若是非Git目录，记录该事实；不为流程完整性自行初始化仓库。

任务卡建议字段：

```text
task_id / 起始快照 / 行为目标 / 非目标 / 允许路径
入口与调用链(file:line) / 状态owner / 资源交接 / 错误与取消
资产与平台影响 / 行为不变项 / 拟改文件
验证层次与已核对命令 / 预期关键测试 / 未知与停止条件
```

按当前风险显式读旧题相关材料；不要把私有Vault路径写到可公开的工程配置。若想改现有CLAUDE，先出增量提案，保留目标原hash与用户改动，批准后再写。

### 步骤B：确定验证入口和失败协议

填写项目自己的命令表，不把占位符当可执行脚本：

| 项目 | 需由沙盒事实填入 | 完成判定 |
|---|---|---|
| 格式/静态规则 | 工具版本、只检查模式、限定文件/规则 | 非零传播、诊断ID/范围明确；不顺手写全仓 |
| 纯逻辑测试 | 真实runner、项目路径、过滤器、结果目录 | 目标断言实际运行；红失败区分环境问题 |
| Unity Editor/PlayMode | 实际Unity/UTF版本文档核对的命令与日志 | 新鲜报告/关键用例/状态/退出码；F2待补 |
| Player/设备 | 后端/平台/构建/场景/设备及批准 | 对应环境行为/性能原始数据；不是普通.NET替代 |
| 架构约束 | 明确source/target/程序集/marker/例外 | 非空与关键类型覆盖，故意违约负例能失败 |

不要为取得一次“绿”而降低验收、吞非零、忽略报告缺失或临时静音未知诊断。既有失败与本次新增失败分开记录，但既有失败也不应被隐去。

### 步骤C：实现→验证→只读审查→最小修复

先实现一个可验证切片；不要把小修扩大为抽象层整理。遇到新依赖、公共协议/序列化/资源策略改变，回到批准点。可执行检查先于AI复述“看起来正确”。审查输入关联最终diff快照、任务契约及验证记录，输出旧清单的三类意见；作者逐项`接受 / 反驳 / 待证 / 范围外`并给依据。

可选Simplifier必须先提案并获批；实际修改后以前结果失效的部分重新运行。再次审查要针对新的diff，不循环刷“零发现”。仍有硬契约缺陷或证据不足时交人工处理，不自动提交。

### 步骤D：记录与撤回

一份任务记录即可，无需数据库。收尾核对最终diff、不相关文件、许可证/敏感内容和未运行项。撤回只恢复本次明确拥有的变更，先比对当前文件，用户已改则停，不做全局卸载/清空/强制reset。结束临时插件会话不会撤销外部副作用。

## 3. 日常四种用法

### 用法一：纯C#小修

“仅修复此输入下的计算错误，读取调用方和现有测试，不改变公开接口。先给失败断言与最小计划，批准后实现，运行该层测试与相关回归。无需多Agent、无需Simplifier。”

目的：建立可核验任务，而不是让模型重写整类。程序通过只支持纯逻辑范围，不外推Unity。

### 用法二：面板启停与异步失效

“读取UI入口、publisher、请求/资源owner；确认订阅有效期。重点核对多次启停、publisher替换、旧请求迟到、失效后释放和线程。用可控顺序测试；另一个只读审查角色仅查这些契约，不做风格重构。”

详见专项适配贯穿例；旧T5/T6是未运行示意，必须补实际夹具。不是把取消等同于任务已经停止。

### 用法三：可选简化

“先说明这个片段具体增加了什么阅读/修改成本；给一个最小备选与不改理由，不改序列化名、事件顺序和资源交接。只提案，不编辑；获批后改并重跑受影响验证。”

目的：避免代码更短但隐含协议更多。原版code-simplifier主动修改且有JS偏置，不直接当只读工具使用（O1）。

### 用法四：架构边界回归

“需求是Domain程序集不能依赖View namespace；先核对现有asmdef/编译约束，列source/target、例外和关键类型。只有现有手段不足才提NetArchTest试点。规则需非空、marker与一个故意违规负例；资产依赖另查。”

目的：把已批准的边界写成测试，不由工具自动发明架构。N1维护成本与宿主未知不能省略。

## 4. 插件与Skill何时进入

只有任务记录反复显示某一缺口时进入单项对照：固定候选/版本、同一任务起点、同样资料/模型/预算，只改变一个因素，保留程序与人工结果。已有普通提示足够就不创建Skill；触发稳定不代表生成质量提高。AI自评、更多发现或更长建议都不是胜出标准。

C1只验证help：`--plugin-dir`是会话加载参数，不是安全沙箱；安装默认scope与marketplace副作用见配置设计。本文不给一键安装/Hook JSON，也不启用CodeRabbit。后者需要单独的数据外发/合同/费用批准；公共仓库可见不自动批准新的第三方处理服务。

## 5. 任务完成记录模板

```text
完成范围：<做了什么，未改什么>
起始与最终快照：<实际引用，不虚构Git提交>
验证：
  - <实际命令、工作目录、工具版本、退出码、结果文件、关键测试与状态>
  - 未执行：<原因与影响>
Review：<输入diff范围、发现及逐项处置；仍为AI判断>
残留：<未解决硬缺陷/设计问题/可选风格>
副作用：<文件/服务/外发/费用，实际无则如实写无>
下一步：<人工确认/补测/停止；不自动发布>
```

合格的“未验证”报告比伪造通过更有价值。不要把命令自然退出、模型说success、heartbeat、零发现、skipped、空测试集或旧XML当验收。
