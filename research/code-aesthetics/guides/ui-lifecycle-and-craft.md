## 一、只有三步，为什么还会错？

设想一个游戏界面：玩家打开角色面板，客户端请求数据，收到结果后刷新显示。

把它写成一句话很简单：**打开 → 请求 → 刷新**。

现在增加两件再普通不过的事：玩家在等待期间关闭面板；玩家又打开了另一个角色的面板。

按时间推演：

| 时刻 | 发生的事 | 必须回答的问题 |
|---|---|---|
| t0 | 面板打开，发出角色A的请求 | 这次请求属于哪个面板实例、哪次打开？ |
| t1 | 玩家关闭面板 | 谁取消或失效这次请求？取消是否保证不会再收到结果？ |
| t2 | 面板再次打开，显示角色B，发出新请求 | 新旧请求如何区分？ |
| t3 | 角色B的数据先返回 | 是否可以更新当前界面？ |
| t4 | 角色A的数据后返回 | 为什么它不能覆盖B？它占用的资源由谁释放？ |

这里的难度不来自“请求”这个函数名太长，而来自**跨时间的关系**：请求归谁、何时有效、谁能更新、谁负责清理。

即使最终实现只有几行，读者仍可能必须在脑中同时追踪这些关系。短，可能只是把复杂度移出了可见代码。

## 二、不是多写几层就能解决

可以想象三个方案：

- **直接版**：把请求、有效性判断与更新放在一个清楚的局部流程中。
- **边界版**：用一个小的生命周期边界管理本次打开的请求和有效性。
- **框架版**：引入通用任务管理器、生命周期注册表、事件路由和多种策略接口。

第二种可能让“谁拥有这次工作”更明确；也可能只是给一次简单调用增加跳转。第三种可能服务多个真实需求；也可能迫使读者阅读十个文件才能回答“关闭后会怎样”。第一种也可能已经足够清晰。

**没有看到需求、约束与任务表现，不能按层数宣布胜负。**

信息隐藏的经典入口是Parnas（Q03）。但引用经典并不等于证明某个接口应该存在。本场景里，更有用的问题是：

> 修改“面板关闭后的行为”时，需要知道多少与此无关的细节？会不会漏改另一个分支？

这是具体任务，不是审美投票。

## 三、把“漂亮”翻译成可以讨论的话

如果审查意见只有“这段代码不优雅”，被审查者很难知道该改什么。

尝试换成：

| 模糊评价 | 可讨论的理由 | 怎么检查 |
|---|---|---|
| 太乱了 | 关闭、重开、旧结果返回分散在三处，没有共享有效性规则 | 逐步推演上表，指出每步由谁处理 |
| 太复杂了 | 理解一次更新必须知道多个无关策略 | 请未参与设计的人定位与修改规则 |
| 太啰嗦了 | 两处有相同语义，但改动时容易漏一处 | 做一个代表性变更，比较遗漏与验证成本 |
| 太抽象了 | 没有当前需求使用扩展点，却增加了调试跳转 | 比较更直接方案；保留确有用途的扩展 |

这不否定美感。美感可能提醒我们哪里别扭，但它需要被翻译成可沟通的理由，再接受行为与任务检验。A01的组织美学研究是这个问题的文献入口；它不是“所有审美分歧都能被任务指标解决”的证明。

## 四、质量内建不是最后多测一遍

继续思想实验：假设新功能很快写完，但每次审查都要重新追踪上述生命周期，而验收材料只覆盖“打开后正常返回”。

再增加生成速度，不会自动补上关闭、重开、乱序结果这些缺口。可能只是让待审工作更多。

精益思想提供的一个研究方向是：在错误进入后续环节前使它可见，并让工作量与验证能力匹配。Toyota TPS与软件精益著作是原始入口（L03、L02），但这里的对应是**本研究的迁移假设**，不是制造业已经证明了这个界面设计。

对这个场景，“质量内建”可以先提出三个候选行动：

1. 在实现之前写出关键时序与必须保持的行为。
2. 在审查中明确有效性与资源所有权，而不仅检查格式。
3. 准备覆盖关闭、重开与乱序结果的独立验收材料。

它们还要接受成本检验。若一个同步、无资源持有的纯数据界面根本没有这些情境，就不应为了套流程引入同等复杂度。

## 五、AI让哪一部分变便宜？

AI可能很快写出直接版、边界版和框架版；这使比较方案更容易，也可能使看似完整的错误方案更多。

请把工作拆开：

**说明正确行为 → 准备上下文 → 生成实现 → 审查与验证 → 集成 → 处理后续变化。**

如果只计“生成实现”的时间，就不能判断端到端是否节约。现有AI研究入口给出了不同情境下不同方向的结果（I01、I02、I04），不能取一个百分比套用到这个界面。

同样，让AI基于自己的实现生成测试，不自动获得独立证据：它可能沿用同一个遗漏的前提。这里是需要检验的机制风险，不是本轮实验结论。更有价值的检查是：验收材料是否来自行为契约，是否覆盖作者没主动考虑的时序。

## 六、什么时候应该停止改进？

假设最小修订已经让规则明确，已有验收证据覆盖当前风险，代表性变更也能正确完成。继续把它升级成全项目通用框架，收益在哪里？

可以问四件事：

- 后面真的还会发生哪类变化？
- 如果不抽象，要多付多少可观察成本？
- 抽象本身要付多少理解、迁移、验证和回归成本？
- 有没有更小、更容易撤回的方案？

技术债与重构资料（Q05、Q06、Q09）是讨论跨期成本的入口，而不是“看起来旧就应偿债”的理由。质量收益的观察模型（Q01）也不能替你支付重构成本，更不能证明投资无限增加仍然划算。

必要的安全、可靠性与合规底线必须满足。满足底线之后的可选改进，则应允许“暂不改”和“做到这里足够好”。

## 七、下次审查可以只问这一句

> **这个改动让谁更容易正确完成什么任务？凭什么相信，代价是什么？**

若答案只有“少了很多行”，继续问行为有没有被删掉。若答案只有“多了几个好看的接口”，继续问边界保护了哪种变化。若答案只有“AI写得很快”，继续问谁完成了验证。

这不是反对简洁、抽象或AI，而是让这些手段回到具体问题。

### 一个小练习（未实施的学习建议）

拿一段你有权使用的代码，不先重构：

1. 写下一个正常情境和两个失败／时序情境。
2. 预测现有行为，标出不知道的部分。
3. 提出保持现状、最小修订和更大改动三种方案。
4. 为每个方案写一句可被推翻的收益预测。
5. 先补证据，再决定是否修改。

不必交出最漂亮的实现。能准确解释为什么这次不重构，也可能是良好的工程判断。
