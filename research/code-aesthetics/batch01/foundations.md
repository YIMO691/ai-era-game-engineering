## 摘要：本批可以建立研究议程，尚不能宣布理论成立

“生产力的进步，不应该成为粗制滥造的借口，而应该成为精益求精的基础”，可以作为一个有解释力的**规范性立场**，但不是能直接由几篇论文证明的经验定律。它包含三个须分别检验的环节：AI是否真的节约端到端成本；组织是否把可支配资源投入质量；这些投入是否在风险与时间尺度内产生净收益。

本批的工作结论是：不宜创立一个以“更漂亮”为统一目标的新编码流派。更有价值的方向，是把**认知与人的理解、审美经验、专业实践、可评价的质量属性、全流程改善和AI成本变化**组织成可反驳的工程判断框架。六部分是本研究的组织方式，不是学界已有“六大学派”。

## 1. 研究设计：先区分问题，再评价证据

### 1.1 核心问题

已有思想能否支持一种工程立场：在满足安全、可靠性与交付约束的前提下，将生产力改善用于降低不必要的理解、变更与验证负担，而不是仅扩大代码产量？

这不是“证明优美代码有价值”的单边论证。竞争解释包括：

- 优美只是熟悉度与团队风格，未改善真实任务。
- 高质量指标是团队能力或项目成熟度的代理，不是收益原因。
- 改善内部结构的收益，低于重构成本、迁移风险及其他机会。
- AI的生成提速被审查、集成、返工抵消。
- 精益指标促进短期工单产量，却削弱探索、学习与长期维护。

### 1.2 方法与覆盖

采用有边界的批判性范围研究：按指定核心文献定点定位，向原始出版社、大学库、标准机构和作者资料追踪，再补充反证研究及中文综述。未进行数据库级穷尽检索、重复独立筛选、质量评分或元分析，不提供伪造的PRISMA流程。

本轮实际使用WebSearch和WebFetch；“优先ACM、IEEE、CNKI”等是来源优先级，不意味着已登录这些数据库。CNKI域名定向搜索未取得目标文章直达详情；《软件学报》官方索引提供了两项中文入口。2013之后的精益综述已检索，但并非大型软件开发同范围的完整更新。无工具横评、代码实验或真实团队干预。

### 1.3 证据不能按一个总等级机械排名

标准适合支持“该标准怎样定义”，不能证明采用后降低缺陷；宣言适合研究共同体价值，不是有效性试验；民族志可以揭示本地实践意义，不等于跨文化普遍规律；随机实验更有利于限定情境中的因果识别，但不自动具有跨任务、跨工具版本的外部效度。研究方法要与问题匹配。

## 2. 为什么追求工程品质：至少有五种不同理由

### 2.1 把工作做好本身就是目的

Sennett《The Craftsman》为工艺的内在动机提供理论入口：工作品质未必只来自金钱回报或外部考核。本轮只定位到出版社书目及p.9的二手引文，未读原书，不能把“人具有把事情做好的冲动”写成被普遍心理实验确认的事实。（A07）

**综合解释**：工程师可能从准确表达、解开问题、掌握材料限制中获得满足；这种动机值得尊重，但不能为无限重构、拒绝合作或忽略用户需求免责。

### 2.2 对使用者与后来维护者负责

**本研究的规范主张**：软件会让他人承担故障、误导、安全和维护成本。品质不只是作者自我表达，还包含对这些后果的责任。一个被作者欣赏的设计，如果把理解成本转嫁给所有后继维护者，就不能仅以“优雅”自辩。

这里的责任不是从ISO标准或某篇审美论文自动推导的道德事实；它是本研究愿意公开接受检验与讨论的价值选择。

### 2.3 在认知能力有限的情况下管理复杂度

Dijkstra的《The Humble Programmer》是认知限制、纪律与程序复杂度的重要经典入口；Parnas则把模块分解与隐藏易变的设计决策联系起来。（Q03、Q04；正文待核）

**综合解释**：当人的注意、记忆与推理能力有限时，好的表达和结构可以帮助局部推理。这比“简短所以美”的解释更强：真正值得降低的是完成任务所需同时考虑的状态、依赖和隐含前提，不仅是屏幕上的行数。

### 2.4 建立共同工作方式与专业身份

Fedorova等人的Yandex研究线索指出，美的理解可能多元，而对丑代码的讨论可能帮助协调本地规范。Sundelin等人的工艺分类则显式包含共享专业文化。（A01、A03）

不能由此宣布团队共识一定正确。共识可能积累有效知识，也可能维持惯例。**规范是否排斥不同经验的人、是否妨碍新解法，是待研究风险，不是本批已证实的结论。**

### 2.5 获得长期经济价值

清晰结构可能减少理解和变更成本；适当验证可能减少返工；技术债把眼前选择与以后成本联系起来。（Q01、Q05—Q09）但这些理由不必与内在动机完全一致。一个设计可以很有美感而不值得继续投资；一个笨拙但可靠、即将退役的模块，可能不应重写。

**阶段结论**：品质动机不只有经济，也不只有审美。研究需要区分动机是否值得尊重、实践是否有效、投入是否适当这三个判断。

## 3. 理论起源：交叉传统，而非单线进化

以下是本批文献入口的年代定位，不是完整思想史：

| 时期／文献 | 主要接口 | 不应推出的结论 |
|---|---|---|
| 1972：Parnas、Dijkstra | 模块化、认知限制、正确性与纪律 | 经典原则自动证明现代框架选择 |
| 1992：Cunningham经验报告 | 技术债隐喻，设计学习与跨期成本 | 所有不整洁代码都必然债务化 |
| 2001：敏捷原则，2003：Poppendieck著作 | 反馈、价值、学习与技术实践的组织 | 敏捷只是更快交付；精益只是裁成本 |
| 2008：Clean Code、The Craftsman；2009工艺宣言 | 实践表达、品质动机、专业共同体价值 | 这些规范性文本构成统一实证理论 |
| 2013：The Lean Gap；2018：Coleman | 检验精益证据基础；区分美学与可读性指标 | 一项综述或指标研究终结争论 |
| 2022：Sundelin等；2024/2025：Fedorova等 | 工艺分类与本地美学实践 | 分类就是通用强制标准 |
| 2023—2026：AI生产力研究与更新 | 成本结构、验证和组织分配的新条件 | 新工具消除了既有软件工程问题 |

敏捷原则正文与XP一手历史材料本轮未完成核验。因此不把“工艺反对敏捷”“工艺等于XP”“某年完整确立某运动”写成已考证历史。更稳妥的**工作性区分**是：软件工程关注系统化建设与评价；敏捷关注面对变化的协作与反馈；XP是一组可具体执行的工程与协作实践传统；软件工艺强调专业责任、技能发展与做工品质。它们可以重叠，关系需进一步以原文和历史材料细化。（A03、A05、A06）

## 4. 代码美学：评价经验不是工程属性的同义词

### 4.1 Beautiful Code的暂定理解

在本研究中，“代码美学”研究人们怎样感知和评价代码的表达、结构和实现方式，包括认为它清晰、简约、协调、贴切或别扭的原因。**这不是统一的好代码评分定义。**

- **简洁**：去除相对于任务目标不必要的负担，不等于字符最少。
- **清晰**：读者能够建立与真实行为相符的模型，不等于“看起来熟悉”。
- **优雅**：以恰当结构组织约束与关系；是评价判断，不能作为免于测试的理由。
- **一致性**：相同语义按相近方式表达，减少无意义猜测；不同语义不应为形式对称被强行统一。
- **对称**：结构关系可以帮助理解，但问题本身不对称时，强制对称会隐藏差异。

以上为工作性概念，不归给某一论文作为公认定义。

### 4.2 Yandex研究：美学也可以是组织实践

A01的Batch01-A历史核验记录称（本轮原文未复核），Fedorova于2014年在Yandex莫斯科总部开展三个月定性田野工作，完成26次开发者深度访谈、4次管理者专家访谈及多日工作观察。最初访谈并非围绕美学设计，研究者是在参与者反复提及 beautiful / ugly 后才加入追问。研究发现组织内没有单一的 beautiful code 理想，但对多种 ugly code 有较共享的识别；作者将“not ugly”解释为该组织中可接受代码的默认类别，不在此断言正式准入规章。该研究解释审美语言如何同时容纳专业差异并推动本地实践一致，不测量缺陷率或维护成本。

可以据此提出问题：当审查者说代码“丑”，是在指出可具体说明的维护障碍，还是在要求新人遵从本地习惯？两者可能同时存在。工程上应把批评翻译成可讨论的理由：哪个状态不清楚、哪个约定被破坏、哪类修改会更危险。**不能把单组织质性材料推广成全球程序员审美规律。**

### 4.3 Coleman：量化不意味着构念被完整捕获

A02的Batch01-A历史核验记录称（本轮原文未复核），研究语料来自GNU Core Utilities的114个程序；过滤后为1,043个单函数C文件、约53,000 LOC。作者比较11个beauty factors与8个readability scores，采用Spearman相关。显著相关的绝对值约为0.05–0.59，没有强相关；作者报告其中位相关平方值为0.0961。

这些数字只描述作者构造的特定代理指标和单一C语料。beauty factor不是程序员主观审美测量；Spearman ρ²是秩相关平方，不能直接解释为原尺度美学指标中由可读性解释的方差比例；即使回归R²也不自动具有因果解释。研究没有真实维护者理解、缺陷定位或修改任务实验。与Buse/Weimer的可读性建模研究入口对照，应进一步区分主观偏好、模型预测、真实任务理解和后续维护结果。（Q11）

### 4.4 炫技与过度设计如何识别

**综合判断规则**：不要仅问“是否很高级”，而问：

1. 这层抽象保护了哪个实际变化点？
2. 它减少了哪些必须同时掌握的信息，又增加了哪些跳转和约定？
3. 新维护者能否在不求助作者时正确完成代表性修改？
4. 删除它会失去什么可观察能力？
5. 相比更直接方案，收益是否足以覆盖理解、调试和运行代价？

答案必须联系具体任务；本批尚未证明一个普适抽象深度阈值。

## 5. 软件工艺：从个人技巧到社会—技术实践

### 5.1 Sundelin分类的价值与边界

A03的Batch01-A作者稿核验记录称（本轮原文未复核），论文使用系统性文献综述与七年Ericsson金融科技产品案例，提出四主题、17原则和47实践。文献部分从980条Google Scholar结果筛选并经四轮snowballing，最终纳入18篇论文和11本书；案例报告按Git Author tag识别155个贡献者身份（自然人去重口径待核），访谈参与者报告为6人。第一作者曾参与该项目开发：

| 主题 | 工作译名 | 本研究关注的问题 |
|---|---|---|
| Value-focused architecture | 价值导向的架构 | 结构如何服务持续价值与变化 |
| Iterative design, development, and verification | 迭代设计、开发与验证 | 如何把设计、构造、测试与改进连成反馈 |
| Shared professional culture | 共享专业文化 | 如何形成责任、学习和可交流的专业判断 |
| Feedback | 反馈 | 如何获得及时且能改变决策的信息 |

这套分类具有较直接的主题相关性，但**“最直接相关”不等于“最强因果证据”**。七年观察不能单独排除人员、产品与组织变动；17/47不是逐项随机验证；书籍、宣言和论文的证据性质不能混同。博士论文收录同一文章不构成独立复制。（A03、A04）

### 5.2 专业判断如何成长：需要研究，而不能只崇拜资历

本批提出的**能力形成假设**：有反馈的真实任务、设计取舍解释、失败复盘、源码比较和反复修改，可能比单纯记忆规则更有助于形成判断。共享文化应把隐含经验外显成可质疑的理由，而不是把个人偏好授予资深者最终解释权。

这一假设尚无本轮教育实验支持。下一批需区分：年资、领域熟悉度、概念知识、任务表现与校准能力，不能把“资深”直接定义为“审美更正确”。

### 5.3 工艺与Clean Code

《Clean Code》是实践著作，不是标准化学术定义，也不是每条规则被独立验证的证据。（Q10）工艺讨论不应退化成SOLID、设计模式和命名规则罗列。某个小函数建议在局部可能改善清晰度，也可能通过过度拆分增加导航成本；需要任务证据而不是书名背书。

## 6. 制造业迁移：迁移问题解决机制，不复制工序外形

### 6.1 纠正一个历史前提

不能在没有历史证据的情况下断言：“制造业先提高生产力，富裕后才追求品质。”减少返工、异常阻断和稳定流程，本身可能影响有效产出；质量与效率既可能互补，也可能因检测、等待和预防投入产生短期张力。**本批只提出联合优化的机制解释，不宣布普遍历史顺序。**（L03—L05）

### 6.2 TPS、TQM与学习循环处于不同层级

- TPS：生产系统；索引中的两支柱是Jidoka和JIT。
- Jidoka：发现异常、停止并处置，以防不合格品继续流转；不是自动化程度越高越好。
- JIT：依据需要和下游节奏拉动；不是把人排满、取消一切缓冲。
- Kaizen：持续改善的取向；本轮未取得独立原典段落，不为其伪造唯一流程或首创年代。
- TQM：全组织的客户与质量取向，不仅是测试／质量部门职责。
- PDSA：预测、实施、研究结果和行动的学习循环；Deming Institute索引强调Study，不宜把Deming直接说成PDCA的发明者。PDCA/PDSA的精确历史仍待原件考证。（L03—L05）

### 6.3 最接近软件开发的参照不只有重复制造

产品开发要产生需求知识、设计方案和新的生产能力；软件开发也不仅是复制既定规格。软件复制／分发成本和软件设计成本是不同对象。降低重复错误的变异，不等于禁止探索的变异。（L02、L06、L09；综合辨析）

因此，试验、备选设计、必要文档和知识储备不能自动被叫作浪费。相反，长期没有验证的决策、未集成的大批变更、等待审查和反复交接，才是值得调查的候选浪费。具体是否浪费，取决于价值、风险与所产生的信息。

### 6.4 条件性迁移

| 原机制 | 软件候选对应 | 必要条件 | 失败信号 |
|---|---|---|---|
| 异常阻断 | 构建／测试／发布门禁 | 有效信号、处置责任、停止权限 | 红灯常态化、误报疲劳、漏检 |
| 拉动与小批次 | 限制待审变更、缩小集成批次 | 可切分工作、下游容量可见 | 提交更多但队列与返工增长 |
| 持续改善 | 小范围重构、复盘后的流程实验 | 基线、反馈、改进预算 | 持续加码、只统计活动次数 |
| 学习循环 | 先预测再比较结果 | 可观察、可撤回、能记录负结果 | 事后讲故事、没有对照 |
| 标准化 | 接口契约、自动格式与明确例外 | 标准服务实际风险且可修订 | 用统一风格压制必要差异 |

这张表是**工程假设矩阵**，不是一手资料直接验证了这些软件效果。完整机制与指标见 [03_概念与理论关系图](concept-map.md)。

## 7. 软件质量：可评价不等于存在无情境总分

### 7.1 什么意义上的“客观”

工作定义：质量属性可以在明确任务、环境、测量方法和容许风险下接受可重复评价。例如规定负载下的时延、故障恢复时间、修改任务的正确完成率。选择哪些属性及权重仍涉及利益相关者价值与风险，不能从“能测”跳到“无价值判断”。

Batch01-A记录ISO/IEC 25010:2023有九项产品质量特性。以下保留前轮术语列表和工作译名；**Batch01-B未直接取得ISO页面或GSO采用版正文，九项条款、采用版身份及官方中文译名均未独立核验**，不能把搜索索引称为确认。（Q02）

| English | 本研究工作译名 |
|---|---|
| Functional suitability | 功能适合性 |
| Performance efficiency | 性能效率 |
| Compatibility | 兼容性 |
| Interaction capability | 交互能力 |
| Reliability | 可靠性 |
| Security | 信息安全性 |
| Maintainability | 可维护性 |
| Flexibility | 灵活性 |
| Safety | 免于危害的安全性／安全保障 |

安全攻击防护（security）与避免对人、财产或环境造成危害（safety）不是一个维度的重复翻译。本列表不构成合规证明。

### 7.2 代码级、架构级与产品级

- **代码级**：局部表达、控制流、状态、依赖和错误处理是否能被理解与验证。
- **架构级**：职责、变化隔离、跨模块契约、部署／故障边界、系统级约束。
- **产品级**：在使用情境中满足功能、性能、可靠性、安全等目标。

这是本研究分析层级，不是ISO原文分层。漂亮的局部代码可能藏在失败架构中；良好架构也不能替代错误路径的正确实现。可演进性关注面对后续需求变化保持适应能力，不能不加说明地与当前可维护性分数合并。

### 7.3 坏味、债务、重构的区别

坏味是值得调查的结构／表达线索，不自动是缺陷判决。技术债强调当前选择与后续成本的关系；并非只有粗制滥造才产生债，也不意味着每笔债都该立即偿还。重构在Fowler定义下是保持可观察行为的结构调整，不等于任意重写，更不是“测试过了就自动证明行为保持”。（Q05、Q06、Q09、C01）

### 7.4 量化的正确角色

本批建议用指标帮助发现问题、比较方案、核查假设，不把指标变成绩效目标的唯一代理。认知复杂度、坏味数、覆盖率、函数长度和美学分数的构念并不相同。一个模型准确预测“看起来可读”，仍可能不能预测人在真实任务中的正确理解。（Q11、A02）

## 8. 品质的经济价值与停止优化

### 8.1 Borg论文支持到哪里

Batch01-A记录Q01将两个公开数据集中的质量、缺陷和开发时间关联组织成回归价值模型，并讨论高质量端的增强收益；Batch01-B未取得原文，不能据摘要索引直接确认。Time-in-Development的单位、起止和模型样本N待核，不等同于员工工时、端到端周期或生命周期成本；79个项目等汇总数不保证每个模型使用相同样本。这仍是值得核查的研究线索，不是当前已证的收益曲线。

但至少有四个不同量：当前质量与结果的关联；把低质量变成高质量的干预效果；实现这次干预所需投入；其他用途的机会成本。论文的模型不能自动填满后面三个量。本轮也未核验样本、指标构造、混杂控制及拟合细节，不能把曲线当通用投资函数。

### 8.2 收益递增与停止条件不矛盾

即使某质量区间的**收益函数**变陡，达到该区间的**成本函数**也可能更陡。另有寿命、变化频率、回归风险及收益实现概率。因此“存在高质量收益”与“有些优化应该停止”可以同时成立。

本研究的**示意决策规则**：在强制安全／合规／可靠性约束已满足后，只有当预期避免的未来损失、变更成本节省和选择价值，大于实施、验证、迁移、回归和机会成本，才继续可选优化。无法可靠估值时，先做小而可逆的实验，不假装有精确ROI。

### 8.3 应考虑重构的情形与应停止的情形

| 值得进一步调查 | 倾向停止／缩小范围 |
|---|---|
| 经常变化且理解困难的热点 | 即将退役且不再改变的稳定模块 |
| 多次故障暴露同一职责／状态边界问题 | 没有可陈述的问题，只是不喜欢风格 |
| 新需求正受现有耦合阻碍 | 主要收益依赖很低概率的想象变化 |
| 能用独立测试和小步切换控制行为风险 | 缺乏验证与回滚能力的大规模重写 |
| 安全／合规约束要求整改 | 指标改善但实际任务与产品属性不改善 |

这是研究建议，不是已经估计的普遍决策阈值。Kaur/Singh的综述索引报告不同属性、学术与工业环境的效果差异，支持反对“重构全面改善所有质量”的简单说法，而不支持“重构一般有害”。（Q08）

## 9. AI改变的是成本结构，不是责任消失

### 9.1 对照而不是选边

下表保留前轮文献记录，不表示Batch01-B读到原文或摘要；I02/I03/I04本轮均不可达，I01未纳入本轮重点复核。来源层级与版本见 [sources](../evidence/sources.md)。

| 研究 | 前轮记录的条件与测量 | 前轮记录的结果（本轮未复核） | 当前解释边界 |
|---|---|---|---|
| Peng等，2023（I01） | 受控JavaScript HTTP服务器任务；当时Copilot | 完成任务“55.8% faster” | 非全部开发流程；不擅自换算吞吐提升 |
| Becker等，2025（I02） | 16名开发者、246个熟悉仓库任务；早期2025工具 | 允许AI的时间效应约+19%，所记95%区间约2%–39% | 人与任务是不同层级；估计和区间方法待核，不等于生产率−19%或质量下降19% |
| Cui等，2026（I04） | 三个企业现场随机实验、4,867名开发者；代码补全助手 | 完成任务数量+26.08%，standard error 10.3% | ITT/IV/LATE、采用、标准化分母、权重及版本待核；权限随机不自动确定所报估计量；不是质量提升 |
| METR，2026更新（I03） | 后续研究方法说明 | 选择与测量问题、设计调整 | 选择方向与幅度待核；不提供可直接替换早期数字的通用净提升率 |

任务、样本、工具、结果尺度和估计对象不同，不能相互抵消或简单平均。保留I04的SE原写法是转录政策，不单凭百分号裁定所有“百分点”释义数学错误；也不能把它解释成26.08%的10.3%。最新工具的能力不能由旧版本结果单独裁定。

### 9.2 可能下降与仍然存在的成本

**机制假设，不是本轮测量**：AI可能降低样板实现、备选方案草拟、测试候选、代码导航与解释的初始成本；仍需支付规格澄清、上下文准备、判断输出正确性、集成、运行、安全审查、回滚和未来维护成本。

AI生成的测试与实现可能共享同一错误假设；这是本研究需要检验的失败机制，不是由上表生产力实验直接证明的结果。因此“AI既写代码又写测试”不能自动当独立验证。架构建议亦需由真实约束和变更任务检验。

### 9.3 人的价值：提出和审查可负责的判断

本研究不预言“人只剩提需求”或“AI永远不能做架构”。较稳妥的工作安排是明确谁负责需求与风险、谁拥有验收证据、谁决定取舍和回滚。AI可参与多种工作，但工具参与不等于责任转移。

### 9.4 从生产力红利到质量红利的三个条件

1. **净节约存在**：计入审查、集成与返工后仍有可支配资源。
2. **组织允许再分配**：不是立即用新增功能和更多在制品吃掉节约。
3. **质量投入有效**：有具体风险／任务目标、独立证据和停止条件。

三者任何一个不成立，核心机制都可能失败。即使AI没有节省资源，某些质量整改仍可能因风险底线而必要；不能把品质责任绑定在AI红利上。

## 10. 最强反方观点与本研究的回应边界

| 反方命题 | 何时可能成立 | 本研究如何接受检验 |
|---|---|---|
| “优美”只是专业群体的口味 | 评分只随熟悉度变化，不能预测任务表现 | 分开测偏好、理解正确率和修改结果 |
| 代码不是艺术品，应该只看用户价值 | 审美活动挤占高价值且有时限的任务 | 要求明确利益相关者、成本与时间尺度 |
| 抽象是未来维护负担，而非资产 | 变化猜错、跳转增多、隐藏约定 | 用未参与设计者完成后续变化任务 |
| 重构是在制造风险 | 无验证、无回滚、低变化模块 | 优先小步、热点、可观测的改进；允许不做 |
| 精益只是管理层压缩成本的语言 | 满负荷、裁缓冲、不允许学习 | 同时看队列、缺陷、负荷与探索机会 |
| AI写得快只会制造更多待审代码 | 下游验证能力固定且缺陷负担增长 | 对比端到端周期和积压，不看生成量 |
| 新理论没有必要 | 既有工程、工艺、质量经济学足以解释 | 接受“代码优美论”只是综合研究议程，而非新学派 |

这些反命题并非都已由本批实证支持；它们是有意保留的竞争解释。框架的价值必须来自更好的判断、可检验的问题与实践收益，而非新名字本身。

## 11. 初步理论架构V0.2.1

详细定义与可证伪假设见 [04_代码优美论初步理论框架](framework.md)。此处只给综合顺序：

1. **认知与程序理解**：读者如何建立程序模型、领域模型，处理可见性、隐藏依赖和认知负担。
2. **价值与审美**：谁的品质、为什么值得追求、审美判断从何而来。
3. **专业工艺**：如何形成并执行有理由的设计、构造与学习实践。
4. **质量工程**：把目标转换为可评价属性和适当证据。
5. **精益改善**：从整个价值流观察反馈、等待、风险与学习。
6. **AI成本结构**：研究工具如何改变各环节成本，以及收益怎样分配。

六部分是相互校正的视角，不是从低到高的成熟度等级。“AI生产力革命”在本版改称“AI成本结构与品质投资接口”，以避免在研究之前预设全面正向的结果。

## 阶段结论

本批没有证明“代码优美论”正确，也没有建立统一美学指标。它完成的是一个受证据可达性限制的研究起点：找到相关思想与原始资料入口，拆开概念、方法与价值主张，校正若干外推风险，并形成可被后续证据修订的框架。

**最值得保留的不是“所有代码都应该更精美”，而是：让每一次品质追求都能说明它服务谁、减少什么负担、凭什么相信、付出什么代价，以及何时应停止。**

### 14.2 认知科学成为理论基础，而不是装饰性附录

本批新增 K01–K03，详见 [08_认知科学与程序理解补充研究](cognition.md)：

- Soloway 与 Ehrlich 的两项程序理解研究表明，熟悉的程序计划和表达惯例会影响读者理解；违反预期惯例即使不导致程序不可运行，也可能增加理解难度。
- Green 的 Cognitive Dimensions 为分析可见性、黏滞性、隐藏依赖、角色表达性和困难心智操作提供概念工具，但它不是代码质量评分量表。
- Pennington的程序模型／领域模型仅为Batch01-A所记二手摘要线索；Batch01-B连该二手正文也未取得，不能将其记为本轮部分已读。Green候选维度的1989归属和K01原表也仍待核。

由此，代码优美的研究不能停留在“看起来漂亮”，还应研究读者能否建立正确的程序模型与领域模型，以及能否正确预测、定位和修改行为。

### 14.3 AI 生产力结论必须保留情境差异

- Cui 等人 2026 年三组现场实验的 INFORMS 官方摘要报告，在特定企业和代码补全工具场景中，完成任务数量估计增加 26.08%（standard error: 10.3%）。本报告不额外将其改写为代码质量提升。
- METR 2025 熟悉仓库实验在 16 名经验开发者、246 项任务中观察到允许 AI 的任务完成时间增加约 19%；METR 2026 更新指出后续研究存在自选择和测量问题。

两者不能简单相互抵消：工具、任务、熟悉度、分配、估计量和结果尺度不同。若METR所报方法与减速结果成立，它可构成“所有软件任务必然提速”的情境性反例；Cui的正向产出结果本身不是反对该普遍命题的负例，也不能用来消除另一情境的减速结果。这里仍是对前轮报告的条件性解释，不是本轮原文认证。

### 14.4 v0.2.1 的工作定义补充

代码优美不仅是视觉或风格上的审美，也可能涉及一种认知协调状态：读者能否在合理成本下看到关键状态、理解依赖、把程序行为映射到领域规则，并在变化时安全地修改系统。这个定义仍是研究假设，必须通过行为等价的理解与修改任务验证。
