## 4. 两项承重理论判断

### 4.1 能否把代码审美作为单独研究的构念？

**可以作为研究问题提出，不能据本次材料宣称已经验证为统计独立变量。**

- **支持方向（证据状态明确）**：A01 的来包解释与搜索索引均指向审美语言在组织协调、身份与社会化中的用途；这足以提供“为什么值得研究”的线索，但本次未直接读到原文。A02 的索引称所用代理指标相关不强，至多提示两套代理不能随意互换。
- **关键区分**：概念上分开定义、测量上有判别效度、统计独立、因果独立，是不同命题。“独立研究”不要求统计独立；构念不同仍可高度相关。反过来，低 Spearman 相关可能源于代理测量不佳、取值范围受限或非单调依赖，不足以证明两个心理构念不同。
- **可操作的下一步**：把直接审美判断（含理由）、可读性判断、真实理解／修改任务分别测量；考察评价者与团队差异，测试收敛／判别效度和可重复性。是否能增加对任务结果的预测，须另行验证。这是审校建议，不是本次完成的实验。
- **反对证据状况**：本次未取得直接反对“审美值得单独研究”的原文证据；也未取得直接支持“美学与维护绩效统计独立”的证据。不得把缺少证据写成反证。

**建议可用句**：“代码审美可以作为与可读性、理解绩效及维护结果分别操作化的候选研究构念；现有材料尚不足以确证其测量结构，更不证明它与这些变量统计独立。”

### 4.2 软件工艺是否已经形成被完整验证的理论？

**本范围不能支持这一结论；也不能反向宣布工艺无效或只是一套口号。**

- 文献综合与案例可支撑术语组织、候选机制、实践分类、情境解释及未来假设；这本身有理论发展价值。
- 四主题／17原则／47实践是分类结果的数量，不是验证通过率。18论文＋11书是材料组成，不是29项独立因果复制；同一文章收录于学位论文不增加独立研究数量。
- 七年是案例时间跨度，不是控制混杂的设计。155 Git 作者身份不等于155受访者、155独立分析单位或155次效果验证；6访谈也不能单凭人数否定质性解释。
- insider身份不是自动失格；需要考察是否提供分析轨迹、反例、异议者、独立编码或研究者反思。但这些措施本次均未读到，不能断言存在或不存在。
- “完整验证”至少应说明要验证什么：分类覆盖、概念区分、机制解释、具体实践效果还是跨团队适用性。不能把“没有逐项RCT”当作唯一评价标准，也不能用一例实践成功替代所有层次验证。
- **反对证据状况**：本次没有取得工艺实践失效的独立对照或复现证据；没有取得足以认定A03完整验证全部理论的证据。
