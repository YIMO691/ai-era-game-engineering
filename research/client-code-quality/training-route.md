# 个人训练路线

目标是形成可解释、可复核的判断，而不是记住“优雅代码”形容词。这是可按个人节奏执行的训练计划，尚未执行，没有学习效果数据。无需另建学习系统、定时任务或新工具。所有练习优先使用独立示例、公开固定源码或用户明确授权材料，不默认访问公司工程。

## 每次练习的最小记录

```text
阅读/修改任务与版本：
开始前的预测：
原始行为与不变量：
我必须理解的状态、依赖与副作用：
候选A / 候选B / 不改：
选择与拒绝理由：
验证方法、实际结果、未运行项：
另一位读者/审阅者的不同意见：
我修改了哪条判断，以及为什么：
```

时间、跳转次数、读者解释错误可以记录为观察，不机械相加成优雅分数；熟悉度、IDE导航、代码长度、领域经验会干扰比较。

## 1．先读懂，不急着“美化”

**任务**：固定源码读 CQ-04 的Queue Dequeue/TryDequeue/MoveNext，先不修改。回答：移除后哪些字段变化？何时清空数组槽位？空队列的两个API契约有何不同？为什么MoveNext注释解释性能理由？

**交付**：一页状态/调用者义务记录，附文件、SHA、行号；列出源码事实、作者注释、个人推论各一项。

**验收**：能从原文指出每条依据；不把注释中的JIT理由外推为Unity目标平台实测；不知道的部分能准确说出还需读哪个边界。AI可核对定位，不能用AI复述代替自己阅读。

## 2．比较两种表达与“不改”

**任务**：用examples中的纯规则/控制流示例，分别写嵌套、卫语句、提取一个稳定规则三种候选。不规定函数行数。让同伴在不知道你的偏好时回答正常/拒绝/边界输入的结果；如果没有同伴，先自己盲隔一段时间复述，但承认它不是独立读者实验。

**交付**：三版本差异、相同输入矩阵、你预计减少/增加的信息与跳转。

**验收**：输出和副作用顺序应符合原定契约；读者能指出第一次写状态的位置。若某候选仅减少行数却增加隐藏依赖，应能拒绝它。没有编译测试就记录“候选尚未验证”。

## 3．先刻画行为，再做小范围重构

**任务**：在独立C#示例中选一个业务规则。先写现状测试：正常、边界、拒绝、重复、异常；实际观察失败/通过状态后再改结构。若是在修bug，将“保持行为的重构”和“改变错误行为的修复”分开。

**交付**：原始/改进diff、测试输入/期望/实际、命令/环境/退出码、未覆盖项和回退方法。

**验收**：除有意修复外输出与可观察副作用保持；出现回归能定位并撤回。不能用“代码更短”代替行为验证，也不能以有限测试通过证明所有行为等价。

## 4．练习Review分级，而不只练找茬

**任务**：使用[清单](code-review-checklist.md)审查同一小段代码，写一条必须修复、一条设计讨论和一条可选偏好。没有真实必须修复缺陷时写“未发现”，不要为凑三条编造。

**交付**：每条给位置、条件、后果、最小建议、验证状态；同时写出至少一个“建议不改”的理由。

**验收**：另一位审阅者能够区分事实与偏好；必须修复可由反例或契约支撑；讨论项有备选和代价。评价重点是误报/证据适配，不是评论数量。

## 5．重组一次跨系统业务主流程

**任务**：用原创场景“点击购买→校验→提交→更新模型→刷新UI→失败提示”画出文字调用序列，然后写最小实现。分别尝试：全塞MonoBehaviour；分出业务规则/服务边界；再增加工厂/策略。比较第三种是否真的有需求支持。

**交付**：状态owner、依赖方向、提交点、事件/异常顺序、三种候选的变更影响。提出一个真实变化，例如增加另一支付来源或断线重试，预测需修改哪些边界。

**验收**：更换View不改核心规则的主张有实际验证；服务失败不留下半完成状态的主张有测试或明确未完成；若重复封装只增加转发层，应删去或选择较小方案。不能为练习虚构线上支付安全保证。

## 6．Unity生命周期与资源责任专项

**任务**：经用户批准后才创建/选择独立最小Unity工程，记录确切Editor、包、平台与后端。覆盖启用/停用/销毁/对象池复用、A/B倒序完成、旧请求迟到、事件重复订阅、producer异常。

**交付**：每个请求/资源的获取、交出、接管、释放记录及异常观察；Prefab/Scene加载和字段迁移验证；实际日志与未运行项。

**验收**：订阅/清理行为与选定生命周期一致；过期结果不提交；未交出资源由producer负责，未接管结果有接收/清理路径；具体资源释放遵守API契约。后台永不返回、应用退出等未覆盖情况必须列出。普通.NET测试不能代替此项。

## 7．最后练习性能与表达的真实权衡

**任务**：先用Profiler定位实际热点，再比较一个可读基线与一个有明确目标的候选，例如已知数组上的聚合。不要先“全面禁用LINQ”。

**控制条件**：目标设备、Unity/包/runtime/backend、构建模式、数据分布/数量、调用频率、初始化和稳态、采样方法、预热、重复次数一致；分别记录CPU耗时、GC.Alloc、峰值/保留内存等与任务有关的指标。

**交付**：原始数据、汇总口径、正确性对照、收益与维护代价；无收益或噪声主导也应保留。CQ-05的runtime实现只能给出假设，不能给Unity收益数字。

**验收**：结果足以回答是否满足已定义预算；候选若无稳定收益或可读性代价不值得，保留基线。不要用一次Editor截图、源码中的new或作者注释替代目标环境结论。

## 回看与固化

完成一次真实任务后才问：我常漏的是什么？是否已有格式化/分析器能处理？某条判断是否反复适用且输入条件稳定？只有存在可复现缺口，才考虑Skill或团队规范，见Skill评估（内部适配提案未纳入公开导出）。

不要求按周打卡或必须完成所有练习才能写业务代码。优先选择当前真实任务最需要的一项，把证据、反例和未完成项记录清楚；代码修改能力、审查能力与教学表达能力分别评价。
