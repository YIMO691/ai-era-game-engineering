# 研究计划

## 问题与裁剪

依据用户提供的研究任务范围（私人任务书不随公开导出提供）。统一主问：在既有 Unity/C# 项目约束下，什么代码质量判断有可追踪依据，如何据此选择小范围改进而不将审美偏好或额外抽象包装为工程必需？

Type=applied。待检验命题：优秀代码以低理解成本表达必要复杂性，并易于验证、修改和维护。竞争解释：局部简短/低复杂度指标已足够；更多抽象天然更好；只要风格一致就足够。研究将用明确反例与源码阅读任务检验这些替代解释，而非先把命题当定律。

按任务书覆盖九个维度与五个层次，围绕同一决策组织，不扩为各引擎/框架百科。不预设某种写法一定GC或更快，不建立“优雅总分”。

## 版本、材料与非目标

Unity 机制参照已有6000.0.85f2固定C# reference记录；新增Graphics/MonoGame/.NET源码分别固定SHA，不将它们的默认分支视为Unity目标版本。没有指定实际项目的包版本、运行时、后端或目标设备；不能据此给生产性能结论。

成熟资料按可读原文选取，不按Star选型：作者公开原文用于定位观点，官方源码用于追踪机制与调用者义务，原创教学示例用于比较候选。经典书籍读不到合法原文时明确标为未完整阅读，不编造章节或作者结论。源码和作者观点不能直接证明人类阅读效率。

非目标：公司工程审计、依赖安装、统一团队编码规范、全量审计所有候选仓库、Unity工程运行、性能基准、购买书籍、立即创建Skill、发布。只读无关私人笔记不在授权范围。

## 证据与分工

主线程：.NET实际源码、现有Unity异步研究可复用部分、综合与六项成果。两个限定独立取证任务：作者原文；Graphics/MonoGame源码。对决定性结论由主线程定点复核。新来源失败保留真实错误，不用摘要代替正文，不绕过安全限制。

支持命题的证据：能明确解释短但隐藏状态/所有权的失败；能展示较长局部实现通过清楚约束减少跨文件理解负担；能界定不值得引接口/抽取函数的情形。修订/否定条件：若改进候选不能减少具体阅读或修改任务成本，或破坏行为/兼容性/性能预算，应拒绝该候选；无读者实验则不得宣称降低认知成本已被实证。
