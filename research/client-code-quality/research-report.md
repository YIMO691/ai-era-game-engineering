# 游戏客户端代码质量与工程审美研究报告

> **状态（只在此处说明一次）**：已读官方 C# 规范、分析器与类库设计原稿，固定版本的 .NET Queue/Select 源码、Graphics RTHandle 关联实现、MonoGame 集合事件实现，并复用前题固定 Unity reference 记录（CQ 编号与读取范围见[来源登记](sources.md)）。四本指定经典未完整阅读：Ousterhout、Fowler、Pragmatic Bookshelf 的合法公开原文候选访问受阻（CQ-09–12），Clean Code 未取得原文（CQ-13），因此本报告不是这些书的已核验综述，也不转述其论证。所有代码未编译、未运行，没有 Unity、Profiler 或读者实验数据。人工研究审核 pending。
>
> **公开区修订（2026-11-15）**：按仓库所有者要求合并重复的边界说明、为每节加上结论句、统一术语，未新增来源或结论；修订前版本见 Git 历史及[导出清单](export-manifest.json)。正文中“〔源码〕”指固定版本静态阅读，其余为本研究的综合判断。

## 结论

**优秀的客户端代码不是最短、模式最多或风格最整齐的代码，而是让必要的行为、状态、依赖与约束能被可靠理解，并在项目环境中可验证、可修改的代码。** 这是工程工作定义；源码分析为它的若干边界提供了实例，但没有把“理解成本最低”证明成普遍定律，更没有建立客观的优雅分数。

更可执行的问法是：**给一个具体的阅读或修改任务，维护者需要知道什么、到哪里找、容易漏什么、改完如何确认没有破坏约束？** 如果改名、拆函数、抽接口不能改善这些任务，或引入了更多接线与隐藏协议，就不能只凭“更干净”认定它更好。

## 1 功能正确，为什么仍然难读

**本节结论：难读来自四类缺口，字数与质量没有单调关系。**

“输出对了”只说明已观察条件下的行为。维护者面对的是尚未执行的条件和未来变化：要恢复隐藏状态、识别副作用、判断异常后哪些操作已经发生。逻辑可以在十个函数里每个都正确，读者却仍不知道哪一步扣款、谁拥有资源、通知看到的是旧集合还是新集合。

MonoGame 集合事件最能说明这一点〔源码，CQ-07〕：插入与单项删除先改集合再通知，`Clear` 却先逐项通知再清空；helper 判空后同步调用，没有为集合增加异常隔离或重入保护。每段都短，系统时序却不能凭名字推断。这支持“局部简洁不足以证明系统协议清楚”，不等于发现了已复现的上游缺陷。

| 缺口 | 表现 |
|---|---|
| 语义缺口 | Process、Get、flag 等名称没有说明行为、单位或失败条件 |
| 位置缺口 | 一条简单主流程要跨多文件或多层寻找；只转发的抽象没有省下知识 |
| 时间缺口 | 状态何时改变、何时通知、旧请求何时失效、资源何时交接没有契约 |
| 验证缺口 | 不能构造反例、定位日志、隔离依赖或运行必要检查，只能相信作者 |

这是本研究的分析分类，不是量化的认知模型。改善这些缺口有时需要更长的名字、显式状态或较多失败分支，有时需要删除多余抽象。

## 2 五个层次：不把“漂亮函数”外推成“好系统”

**本节结论：应逐层解释，而不是用一个总分掩盖短板。**

| 层次 | 核心评价任务 | 能观察或验证什么 | 不能据此推出什么 |
|---|---|---|---|
| 局部表达 | 识别意图，追踪分支与副作用 | 名称与行为是否一致；给定输入的路径；单位与返回契约 | 整体模块边界合理 |
| 模块设计 | 解释状态 owner 与不变量 | 公开 API 能否绕过检查；非法状态能否构造 | 跨系统协作没有时序漏洞 |
| 系统协作 | 追踪调用、消息与资源交接 | 提交与通知时点、依赖方向、失败与生命周期协议 | 目标设备性能达标、未来维护成本已知 |
| 工程维护 | 复现、测试、诊断与回退 | 测试、日志、迁移、变更影响；实际失败定位 | 未覆盖行为也正确；测试多就易维护 |
| 项目适配 | 遵守真实工程约束 | 编译链、序列化、包与 API 兼容、团队风格、设备预算 | 某团队经验就是行业统一标准 |

一个漂亮的 UI 方法若直接调用全局状态并依赖不明的销毁顺序，局部表达合格，系统协作仍有缺口。一个较长的引擎适配函数若清楚隔离了必要的状态机，也可能比到处拆分更合适。

## 3 命名、签名与局部表达

**本节结论：名称应让读者形成可核对的预测。**

名称要回答：读取还是消费、借用还是接管、异步还是立即完成、值以什么单位表示。Queue 的 `Peek` 与 `Dequeue` 区分了保留与移除，`TryDequeue` 与 `Dequeue` 用不同的失败契约服务调用方〔源码，CQ-04〕。这比“所有方法必须短”更接近可执行的质量判断。

- 类型与接口表达角色和能力，不给每个类都加 Manager/Service 和同名 `I` 接口。
- 方法用动词表达动作；副作用不藏在看似查询的名字后面。`Get` 若消费资源，应改名或显著说明。
- 布尔值表达明确命题，如 `isRequestPending`；避免 `Check()` 返回值说不清是有效还是有错；不全面禁用 bool。
- 集合用能说明内容的复数或角色名；需要区分快照与可变视图时，用类型与契约补充。
- Task 异步入口可沿项目的 `Async` 惯例，取消参数表达取消语境；`Async` 后缀不证明线程或生命周期正确，Unity 回调与既有 API 不机械改名。
- 参数说明单位、可变性与合法组合；多个布尔参数可先用命名参数或枚举，不必直接建设 Options 体系。
- 事件名表达已发生的事实或请求意图，并说明同步与否、通知时序与订阅寿命；名字无法单独编码全部协议。

缩写是否合适取决于领域共享知识与作用域。名称越长并不越准确，把每个约束堆进名字会冲淡核心意图。重命名公开 API、序列化字段、反射目标和持久化字段不是纯风格改动。

## 4 函数粒度、控制流与异常

**本节结论：提取函数的价值在于形成可信的知识边界，而不是删掉几行。**

要问：提取后的名字是否描述了稳定概念？调用者是否因此无需理解实现？被隐藏的是细节，还是必须知道的资源与时序责任？CQ-04 把索引回绕放在 `MoveNext`，但没有强行统一 `Dequeue` 与 `TryDequeue` 的差异；CQ-05 的 `Select` 保留了多种输入与优化分支〔源码〕。它们展示的是可成立的取舍，不能转成“永远不要消除重复”或“所有分支都应保留”。

1. 保留主要步骤的同层表达，例如校验 → 提交请求 → 接受结果 → 更新状态 → 通知；不把每个赋值拆成 `StepN`。
2. 将纯规则、I/O 边界、事务、重试与所有权协议按需独立命名。只调用一次不代表不能提取；重复出现也不代表是同一职责。
3. 卫语句能让拒绝条件更明显，但必须保持异常时点、副作用与清理语义；多个 return 不天然优雅，深嵌套也不天然错误。
4. 多阶段状态与合法转移应考虑显式状态机；十个相互影响的布尔值即使名字都好，组合也可能失控。模式匹配可让分类更集中，但要检查分支优先级、遗漏与目标编译链支持。
5. 参数、返回值和异常应让调用方知道如何继续。只在能兑现的边界处理异常，不为“主流程干净”吞掉失败。

判断拆分的单位是具体的阅读或修改任务，而不是 N 行上限。

## 5 类、组件、模块与项目结构

**本节结论：内聚按“为保持哪个不变量而共同变化”来讨论；局部结构必须反映真实的权威与协议。**

字段私有并不足够：如果三个服务都能间接改一份余额而权威归属不明，封装只是表面。公开 API 应限制非法状态进入，而不是为了整齐把所有字段透传出去。

- MonoBehaviour 负责必要的引擎回调、序列化引用与视图适配；可独立计算与验证的规则可放普通 C# 对象。不强制每个组件都配 Presenter/Service/Factory。
- UI 以展示与输入适配为主；网络提交、模型权威、错误与重试协议应有明确 owner。“UI 拆出去了”不代表资源加载与释放有人负责。
- 配置承载稳定的数据差异，并校验版本、引用、默认值与错误处理。把任意行为搬进字符串或反射配置，可能把编译期错误变成运行期错误。
- 组合有助于局部替换能力；继承适合清楚且可替换的共同协议。子类必须记住隐含的 base 调用顺序时应重新审视，但引擎既定的回调边界不能凭口号消除。
- 文件、命名空间与目录帮助寻找代码，不自动隔离依赖；程序集边界有更强的编译约束，但也影响可见性、序列化引用与包依赖，需要在目标工程验证。
- 普通 C# 对象可优先让构造入口建立必要依赖与合法初态；引擎创建或序列化的对象则应按目标 Unity 的创建与回调契约初始化，不机械套用普通对象的构造方式（具体回调时序未验证）。

如果服务定位器把依赖藏起来、每层只转发、事件顺序无人负责，再漂亮的文件排列也没有解决设计问题。

## 6 抽象与必要复杂性

**本节结论：有效抽象提供稳定易用的契约，隐藏调用者无需承担的知识，并真正负责它承诺的责任。**

接口短不代表模块深。如果调用者仍要懂初始化顺序、异常后的半状态和释放策略，复杂性只是被移走了。

**抽象之前的四问**：现在必须隐藏的知识或不变量是什么？哪个真实变化会因此被局部化？调用者省下了什么，又多了多少跳转、配置与调试路径？不抽象、少量重复或普通函数能否以更低成本满足需求？

| 工具 | 值得考虑的条件 | 主要代价或反例 |
|---|---|---|
| 接口 | 限制依赖能力、隔离外部边界、真实替换或测试风险 | 每类一个同名接口只增加导航；只有一种实现不自动否定接口价值 |
| 泛型 | 同一算法或不变量确实跨类型共享 | 约束、特化、错误信息与代码大小更复杂；CQ-05 有 AOT 相关作者注释 |
| 委托 | 小而清楚的可替换行为 | 捕获状态与调用时点变隐式；性能须具体核对 |
| 事件 | 多方通知，且订阅、顺序、错误契约明确 | 隐式调用图、长寿命引用、重入与调试成本 |
| 策略、工厂 | 稳定的变化轴，创建与生命周期规则值得集中 | 尚无变化就预建扩展点，增加配置与组合数量 |
| 装饰器 | 日志、缓存、重试等横切协议可组合且次序清楚 | 重试叠加、异常与取消传播、所有权可能变复杂 |

DRY、YAGNI、KISS 在这里只作为思考提示，不以未读书籍的引文背书：消除同一规则的多处权威；不为猜测的未来付过多现在的成本；不为表面简单而删除业务必需的约束。三者冲突时，列出“不改／局部重复／普通函数／结构化抽象”候选，用真实变化与失败边界比较。

**反例**：两段相似的金额或等级比较，合法零值与变化原因不同，合并成带模式参数的通用 `Check` 可能更难懂；反过来，同一价格协议已在多处同因变更并频繁漂移，继续复制也未必更简单。

## 7 注释、风格与自动检查

**本节结论：注释记录代码无法表达的原因与约束；工具只负责它覆盖的规则。**

代码适合表达动作、类型、单位和可见状态；注释适合记录原因、兼容性、协议、风险、来源与非显然约束。CQ-04 中 `MoveNext` 的注释给出了作者的性能理由〔源码〕，这是有用的上下文，但不能替代当前平台的基准。

- XML 文档优先服务跨模块调用者：返回与失败、线程、可变性、所有权、重复调用与生命周期契约；私有小方法不必逐句复述。
- `TODO`、`FIXME`、`HACK` 应带待办或兼容原因及解除条件。错误的注释比缺注释更危险，应与代码同改。
- 一致性减少团队内重复解释的需要，这是合理的工程目标，但其收益未被量化。CQ-01 明确规范可调整，其教学与新语法目标与运行时热路径不同，不能把官方示例的语法与 LINQ 倾向当成 Unity 项目的硬规则。
- EditorConfig 与格式化适合稳定风格；Roslyn 诊断适合已覆盖的静态模式，诊断级别与版本可配置（CQ-02）。机器不能仅凭命名规则确定业务职责，也不能从某条性能告警证明设备预算被突破。StyleCop 未专门评估，不生成未验证的启用清单。
- 团队现有配置优先；格式化与行为改动尽量分离；抑制规则要写范围与理由。

## 8 Unity 中最容易把“漂亮”误当“安全”的地方

**本节结论：生命周期、异步、资源与序列化的责任必须显式写出，名称与语法不能代替契约。**

### 8.1 生命周期与事件

停用、销毁、关闭业务窗口、归还对象池、同一实例重开不是同一个事件。先选定 owner 与有效期，再决定订阅与退订入口以及请求身份。启用期事件可考虑 `OnEnable`/`OnDisable` 配对；跨停用期仍需业务监听的，应有其他明确 owner（回调顺序未经运行验证）。

订阅处理器要能被正确移除，publisher 替换前要解除原绑定。不要只在 Destroy 写一个退订就认为所有长期 publisher 引用都已处理。CQ-07 也提醒，“移出集合”与“销毁资源”是不同的协议。

### 8.2 异步与资源

前题 CQ-08 区分了执行位置、提交资格与资源交接（详见 [Unity 异步任务生命周期](../unity-task-lifetime/report.md)）。名字带 `Async`、传了 token、await 后判空，都不足以独立证明旧请求不能改新状态。必须问：谁观察异常，谁清理生产者未交出的资源，谁接收迟到结果，何时成功接管。

CQ-06 给出了具体的所有权例子〔源码〕：RenderTexture 的 `Alloc` 入口默认借用，`Release` 有条件地请求销毁。不要把所有资源清理压成一种 `Dispose` 模板；Graphics 主线包 17.7.0 与 6000.0.85f2 的兼容未验证，其实现细节不能外推到所有 Unity 资源。

### 8.3 超时要说清是哪一层停止

接口要区分“调用方不再等待”“已请求生产者取消”“生产者已完成并清理”。超时提示可以先出现，后台工作却未必已停；此时仍要观察异常、拒绝过期提交、接收并清理迟到结果。若要求等清理结束再返回，就不能同时无条件承诺严格的截止时间。这是协议设计分析，没有核验某个超时 API 的实现，也不推荐在目标版本未确定前直接套用某个最新 .NET 等待 API。

### 8.4 序列化与历史约束

重命名序列化字段、改变结构或程序集、修改事件顺序，可能改变代码调用之外的行为。应把数据与资产迁移、加载验证与调用方兼容列入修改任务。

已有框架不只是“服从或推翻”二选一：先在现有边界完成最小清晰的改动；局部问题局部修，结构性问题单独提案讨论迁移成本。不为一个需求顺手建立平行的 DI、事件或资源框架。

### 8.5 迁移到其他语言或引擎：迁移问题，不搬运机制

- **可迁移**：让名称兑现行为、说明状态 owner 与不变量、显式记录提交与通知时点、比较候选与“不改”、在目标环境验证。
- **需要重建映射**：构造与销毁、事件寿命、线程与调度、序列化、引用有效性与资源句柄协议。MonoGame 的集合事件不是 Unity 回调顺序的证据，服务器 .NET 的线程假设也不能移植成客户端保证。
- **不能照搬**：例如把 C++ 作用域析构的经验当成普通 C# 引用离开作用域就会清理，或把托管对象回收当成 Unity 资源已释放。

这是迁移判断的提示，不是对其他语言或引擎源码的审计。

## 9 性能与可读性：成本必须具体化

**本节结论：不能从一个语法名字推出统一成本；先有预算与热点，再谈优化。**

CQ-05 的 `Select` 实际存在按输入类型、空集合、优化开关的分支〔源码〕。它支持“不能从一个语法名字推出统一成本”，既不支持“LINQ 免费”，也不支持“所有 LINQ 都必定产生某个分配量”，更不能直接给出 Unity 中 Count/Where/ToList 的运行数据。

| 写法 | 应核对的具体问题 | 不能直接下的判决 |
|---|---|---|
| LINQ 与迭代器 | 源的静态与动态类型、延迟枚举次数、是否物化、版本实现 | 一律 GC、一律更慢、一律更可读 |
| lambda、闭包、委托 | 是否捕获、何时创建与缓存、持有对象的寿命、调用频率 | 每个 lambda 都有相同堆成本 |
| 值类型与装箱 | 哪个转换或调用路径、泛型约束、运行时与编译优化 | 用结构体或泛型就自动零分配 |
| async 状态机 | 具体 await 路径、同步还是挂起、结果类型、生命周期 | 每次 await 固定产生分配或必回主线程 |
| 复用、缓存、池化 | 初始化与稳态、保留内存、清理、失效、一致性 | 少一点分配就一定有收益 |

顺序是：定义预算与代表负载 → 定位热点 → 保持行为比较候选 → 目标设备测量 → 权衡收益与维护代价。要记录 Editor、包、运行时与后端、构建与平台、输入与频率、预热、重复次数、原始数据与指标口径。CPU 时间、GC.Alloc 和保留内存回答的是不同问题。

如果代码不是热点，或数据无法区分收益与噪声，保留清楚的基线可能更合理。性能关键部分需要复杂实现时，把它限制在清楚的边界内，留下原因、测试与环境记录，不让优化惯例无证据地扩散到所有业务代码。

## 10 可测试、可调试与可维护

**本节结论：可测试性的价值在于更快验证重要假设；维护质量最终要用真实变化检验。**

- 纯规则适合输入/输出测试；I/O 与 Unity 边界需要更具体的失败、顺序、取消、重复与资源归属检查。为了测试新建接口，应说明它隔离了哪类真实风险，而不是机械地把私有方法公开。
- 可调试性要求能恢复一次执行：请求与资源标识、阶段、必要输入、异常与清理。过量的每帧日志、只记录 Message 而丢上下文、吞掉异常后返回成功，都会把局部的“干净”变成维护代价。日志还要控制频率、开销与敏感信息。
- 本研究把重构定义为“行为保持的内部调整”（作者原文 CQ-10/11 未读，不作引文）。行为包括调用方可观察的状态、事件与异常顺序、数据兼容，不只是返回值。刻画测试通过只支持已覆盖的条件。
- 维护质量要通过真实变化检查：新增一条业务规则要改哪里？故障能否复现？回退是否可行？这也受领域经验与团队流程影响，不应把一次顺利修改归因于某种风格。

## 11 哪些可以验证，哪些仍是审美

**本节结论：先分清讨论的是事实、有证据的设计讨论、未实证的假设，还是偏好。**

| 类别 | 示例 | 应如何表达 |
|---|---|---|
| 可核对的事实或硬约束 | 事件在提交前还是后；错误输入路径；目标编译是否成功；资源释放调用次数 | 给版本、代码定位或实际运行结果 |
| 有证据的设计讨论 | 某项变化被边界局部化；为理解副作用需跨七个转发层 | 给具体任务、候选、代价与反例，不自动升级为缺陷 |
| 合理但未实证的假设 | 这个命名或主流程组织可能减少误读 | 说明机制，待独立读者或真实修改检验 |
| 审美偏好 | 同样清楚且兼容时偏好 var、成员顺序、某种表达式 | 标为可选，沿项目约定，不阻塞正确改动 |

审美不是无价值，一致、节奏与局部对称可能帮助阅读，也体现团队的表达习惯。但一旦把“更自然”变成强制要求，就应指出真实任务收益或团队约定，而不是借作者名声或工具分数压平不同意见。

核心命题因此要限定：在满足正确性、安全、数据与项目约束之后，比较理解、修改与验证负担；“尽可能低”不是可全局计算的最小值，也不存在被证明的唯一最优代码。必要复杂性随业务、读者、环境与变化而变化。

## 12 转化为日常方法

1. **写前**：几句话说明意图、状态 owner、主流程、失败与项目约束。
2. **写时**：让名称、类型、顺序兑现这些说明；只在形成真实知识边界时提取，比较“不改”候选。
3. **自查**：沿正常、拒绝、异常、取消、重入或重复、退出路径追一次数据与资源。
4. **审查**：先正确性与硬契约（A 必须修复），再设计讨论（B 需要讨论，须附替代方案与代价），最后可选风格（C）；评论给场景、后果与验证状态，不按审美凑问题。详见[审查清单](code-review-checklist.md)。
5. **修改后**：运行实际需要的测试与设备检查，记录未覆盖项；同步注释与契约；小范围、可回退。
6. **复盘**：用真实任务修正指南；只有反复出现、现有工具没有覆盖的缺口才考虑固化为规则或 Skill。
