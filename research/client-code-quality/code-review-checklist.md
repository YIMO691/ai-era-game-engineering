# 日常编码与 Code Review 清单

只评审本次改动及必要上下文，不顺手改造整个历史项目。清单是提醒漏项的工具，不是“勾完即正确”的认证。规则依据与限制见 [来源](sources.md)、[指南](code-quality-guide.md)。

## 提交者：先给最小背景

- [ ] 这次解决什么问题？哪些行为应保持、哪些有意改变？
- [ ] 列出真实约束：Unity/包版本、运行时/后端、平台、序列化、项目框架与性能预算；未知项写未知。
- [ ] 说明状态owner、外部副作用、失败路径；改了协议就说明调用者义务。
- [ ] 列出实际执行的编译/测试/设备复现，命令、环境、结果；未运行项不要写成“应该通过”。
- [ ] 格式化/机械改名与行为修改尽量分离；说明不可分离的原因。
- [ ] 如果是重构，给行为刻画/前后对照；如果修bug，给能区分旧新实现的失败用例。

## 第一遍：看系统路径，不先挑拼写

沿一次真实请求追踪：入口 → 前置校验 → 读取状态 → 外部依赖 → 提交 → 通知 → 失败/退出清理。

- [ ] 输入来自哪里，结果交给谁？有没有隐藏的静态状态或服务定位器？
- [ ] 哪个步骤不可重入/不可重复？能否从UI事件重复触发？
- [ ] 一个局部改动会不会改变事件顺序、持久化字段、缓存失效或跨模块API？
- [ ] 修改应局部化在哪个责任边界？当前diff是否把无关变更捆进来了？

## A — 必须修复：有实际失败条件或违反硬契约

严重性取决于后果，不取决于是否符合个人喜好。证据不足但潜在影响大的问题先要求补证/阻塞验证，不能编造确定bug。

- [ ] **正确性**：边界、顺序、重复调用、空/缺失输入、溢出/单位；是否存在具体输入得到错误状态/输出？
- [ ] **生命周期**：销毁/停用/场景切换/对象池复用后是否还回写？资格检查能区分同实例新请求吗？
- [ ] **异步**：谁观察Task异常？取消是否被错误吞掉？停止等待后的迟到结果归谁？线程依据是什么？
- [ ] **资源**：谁创建/借用/接管/释放？取消、异常、半接管、重复释放、永不返回都讨论了吗？
- [ ] **事件**：订阅是否可能重复？是否仍被长寿命publisher持有？退订是否使用原处理器/原publisher？
- [ ] **数据完整性**：是否出现部分写入、通知早于提交、存档/序列化迁移缺失、旧缓存覆盖新状态？
- [ ] **安全与隐私**：不信任输入的边界、权限、路径、凭据和日志敏感信息是否受保护？
- [ ] **性能回归**：是否违反已确定预算或有可复现的明显回归？给目标平台、输入、频率与数据。没有测量时将疑点写为待验证，不按语法给性能判决。
- [ ] **验证缺口**：高风险行为修改是否缺少必要复现/测试？缺证据时可暂不合并，但不能说测试已经失败。

## B — 需要讨论：设计与修改成本

- [ ] 名称能否准确预测行为、单位、可变性与副作用？“Get”有没有悄悄移除资源？
- [ ] 函数中的主要动作是否同一抽象层？是否为理解一步操作频繁跳到只转发的函数？
- [ ] 提取函数/类是否隐藏了真正的规则或协议，而不只是把几行搬走？
- [ ] 参数/状态组合中哪些是非法的？是否可以少一点隐式约定？
- [ ] 接口/泛型/策略/工厂/事件的存在依据是什么？能否指向真实变化或依赖隔离？
- [ ] 这些重复代码是在表达同一知识，还是目前偶然相似、未来独立变化？修改理由相同吗？
- [ ] MonoBehaviour中哪些依赖Unity回调/序列化，哪些是普通业务规则？拆分收益是否抵得过接线成本？
- [ ] 错误能否定位到请求/状态转换？日志是否可用而非噪声？
- [ ] 注释有没有给出代码外的约束、原因和版本？会不会与现状矛盾？
- [ ] 需求变更时预计影响哪些模块？这个预测有没有通过真实需求或历史diff验证？

讨论意见应提供替代方案与代价；“感觉不优雅”“不够面向对象”不是充分理由。

## C — 可选风格：不冒充硬性缺陷

- [ ] var/显式类型、成员排列、单行/多行、表达式形式等是否已有团队约定？有则自动化，不逐条争论。
- [ ] 没有约定且两者都清楚时，是否可以保持当前写法？
- [ ] 改名/格式化会不会扩大diff、制造合并冲突或影响序列化？若有影响，就不再是单纯风格建议。
- [ ] 圈复杂度/函数行数/依赖数量是否只是定位线索，而非直接判定错误的阈值？

## 工具负责到哪里

| 工具/手段 | 可以交给它 | 仍由人判断 | 本课题状态 |
|---|---|---|---|
| EditorConfig/格式化 | 项目支持范围内的空格、换行、部分命名/风格配置 | 规则是否适合团队、迁移diff与兼容性 | CQ-01已读；未改真实配置 |
| Roslyn分析器 | 启用规则覆盖的静态模式与诊断 | 真实业务owner/性能预算、诊断是否需要有记录的抑制 | CQ-02已读；未在Unity集成 |
| StyleCop类工具 | 经团队确认且工具支持的风格检查 | 命名是否贴切业务、架构是否合理 | 未安装，未完成本轮专门规则/许可证评估，不给具体启用清单 |
| 编译与测试 | 目标环境下的语法/类型、测试覆盖的行为 | 覆盖缺口、真实设备/时序、用户需求 | 本题示例均未编译/运行 |
| Profiler/设备测试 | 指定环境下的采样与测量 | 因果、代表性、预算与可接受性 | 本轮未运行；不提供收益数字 |

分析器升级可能改变诊断，CQ-02明确有SDK/级别差异。不要直接将`.NET 5+默认启用`套到Unity生成工程；须核对Unity/IDE/CI实际编译链。不要为本清单擅自安装依赖或修改团队配置。

## Review 评论格式

```text
级别：必须修复 / 需要讨论 / 可选风格
位置：文件:行号
观察：可核对的代码或契约
场景：什么输入/顺序/需求会受影响
后果：错状态、泄漏、回归，或额外阅读/修改成本
建议：最小候选；必要时给第二选择与代价
验证：已执行结果 / 建议补充但未运行
```

**必须修复示例（原创假设场景）**：Close后旧请求仍能写入当前View；如果B已取代A，A后完成会覆盖B。建议在owner线程检查请求身份并明确未接管结果清理；请加倒序完成测试。若未复现，就写“静态推断，待复现”，不写“测试失败”。

**讨论示例**：为了确认一次购买是否成功，需要跨七个只转发函数寻找扣款/发货顺序。能否把业务主流程保留在一个入口，把可独立命名的校验规则单独提取？代价是入口会稍长，但提交点更可见。

**可选示例**：这里显式类型和var均能辨认，没有团队规定；我偏好显式类型，但不阻塞本次修改。

## 合并/交付前

- [ ] 关键发现已修复或有明确风险接受者；不能以“审美不同”回避正确性，也不能以“最佳实践”回避设计讨论。
- [ ] 实际测试结果与未运行项已更新；抑制/兼容处理有范围与理由。
- [ ] 文档/注释/契约与代码同改，保留公开接口与数据迁移责任。
- [ ] 后续清理与当前必须修复分开，不凭Review顺手引入全局框架。

本研究清单尚待人工审阅和真实项目练习，不能代替团队合并政策或发布授权。
