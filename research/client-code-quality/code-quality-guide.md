# 客户端代码质量实用指南

目标不是让所有代码“看起来像我写的”，而是让下一位维护者能找对意图、状态、依赖和失败边界，并安全完成修改。本指南是有边界的工程建议，不是行业强制标准，也不是经过读者实验验证的排名。依据与状态共用 [来源登记](sources.md)；机制、反例见 [代码对照案例](unity-csharp-examples.md)。

## 先选对层次

| 层次 | 应回答的最小问题 | 常见误判 |
|---|---|---|
| 局部表达 | 这段在做什么、条件和单位是什么？ | 把改名/换行当成架构改善 |
| 模块设计 | 谁拥有状态，公开什么，隐藏什么？ | 把拆成更多类当成更内聚 |
| 系统协作 | 谁调用谁，何时生效，失败归谁？ | 单个类漂亮就认为跨系统协议正确 |
| 工程维护 | 能定位失败、验证改动并回退吗？ | 测试数量多就认为测试覆盖了风险 |
| 项目适配 | 符合现有序列化、生命周期、API和性能约束吗？ | 从现代.NET拷贝语法/工具配置到Unity |

## 日常判断表

表中的“依据”包含源码事实与综合建议，不代表每条都被实验验证。CQ编号对应来源；综合建议需要在当前项目用具体修改任务检验。

| 特征 | 反模式 | 判断依据/问题 | 改进动作 | 边界与反例 |
|---|---|---|---|---|
| 名称表达角色与行为 | Data/Manager/Process承载所有东西；Get却消费队列 | 读者能否仅据签名预测是否变更状态？CQ-04 的Peek/Dequeue区分保留/移除 | 用动词标记命令，用业务名词标记对象；消费方法与查询分开命名 | 不为所有成员堆所有权后缀；签名不能承载全部契约 |
| 单位与状态明确 | time、value、flag含义随上下文变化 | 秒/毫秒、请求中/已完成是否需要猜？ | `cooldownSeconds`、`isRequestPending`；复杂状态用明确状态类型 | 类型封装可避免单位混用，但少量局部计算不必建领域框架 |
| 返回契约明确 | bool同时表示缺数据、取消、错误 | 调用方是否知道失败后还拥有什么？ | 简单缺失用Try模式；多失败原因用受限结果类型 | 不为每次查询建立十层Result/异常包装；与项目约定一致 |
| 主流程连续 | 每行都跳到只转发的私有函数 | 为完成一次阅读任务要打开多少实现？ | 保留同层业务步骤；提取能独立命名的规则/协议边界 | I/O、事务、重试/资源协议值得独立封装，即使调用只有一次 |
| 提取有信息增益 | CheckA/Step2/DoCore只隐藏语句 | 提取后是否减少必须理解的信息？ | 用稳定业务概念命名；局部顺序高度相关的语句保留相邻 | 不设“超过N行必须拆”的通用阈值；CQ-04/05含必要状态分支 |
| 参数组合可解释 | bool、bool、int顺序容易误用 | 是否存在大量非法组合或难辨调用？ | 命名参数、业务枚举、必要的不可变请求对象 | 单个布尔开关可清楚；小函数不必总改Options |
| 状态有单一权威 | View/Model/Service各存一份isOpen | 失配时听谁的？ | 指定权威状态与派生视图；就近收束状态转换 | 缓存可以存在，但要有版本、失效和一致性契约 |
| 封装保护不变量 | public setter允许绕过检查 | 是否能从公开API制造半完成状态？ | 暴露意图方法/只读快照；集中检查后提交 | 私有字段不自动意味着封装，静态全局仍可能泄漏实现 |
| 接口承载能力边界 | 每个类都加同名I接口 | 谁实际需要替换、隔离或限制访问？ | 围绕外部服务/不稳定依赖设边界，必要时用简单委托 | 一种实现也可能有合理边界；多实现也不自动需要通用工厂 |
| 继承符合替换契约 | 基类模板要求子类按隐含顺序调用base | 调用方能否不识别子类型而安全使用？ | 更明确的组合或封闭继承协议 | 引擎回调继承是既定边界，不必为追求组合重写引擎体系 |
| 分支暴露正常/失败路径 | 深嵌套与双重否定 | 哪些路径无副作用，哪里第一次写状态？ | 卫语句处理拒绝；副作用聚在可见提交区 | 提前return不能越过清理/事件；状态机比十个guard更适合多阶段协议 |
| 条件是可讨论规则 | 长表达式夹带调用、缓存更新 | 条件求值会触发什么？短路是否有意义？ | 提取纯判断/明确命名的规则；把改变状态移出谓词 | 不能为“等价”重排有副作用或异常的表达式 |
| 注释补充代码外信息 | `//加1`、陈旧“无分配”承诺 | 名称和类型不能表达的约束是什么？ | 写原因、协议、来源/版本和修改风险；删除与代码矛盾注释 | 性能原因注释是作者理由，不替代当前设备数据；CQ-04 |
| XML文档服务调用者 | 把每个私有getter写一段英文复述 | 调用者是否需要线程、所有权、失败/单位契约？ | 为公共/跨模块API补必要param/returns/exception/remarks | 不承诺工具无法保证的“线程安全”“永不失败” |
| TODO可追踪 | 永久的`TODO optimize`、无解释HACK | 何时能删、风险是什么、责任归哪？ | 指向问题号/触发条件/兼容原因；定期在相关改动时复查 | 不在代码里写个人敏感信息；不为零风险任务强建流程 |
| 测试切在风险边界 | 为Mock方便复制生产逻辑 | 什么输入或顺序能推翻结论？ | 纯规则测输入输出；边界测失败/顺序/调用次数；重构前先刻画现状 | 纯单元测试不能证明Unity销毁、GPU释放、IL2CPP成本 |
| 调试可追踪 | 每帧海量日志；所有异常只打印Message | 同一请求能否从开始追到失败、清理？ | 标识/阶段/关键输入/完整异常；日志级别/采样和脱敏 | 不把大对象或令牌写日志；日志本身也有性能与隐私成本 |
| 组件是明确适配层 | MonoBehaviour兼管网络、计费、资源、规则 | 何处必须依赖Unity对象/场景？ | 生命周期/序列化/视图绑定留组件；适合独立判断的规则放普通C# | 20行简单组件未必需要Presenter/Service/Factory三件套 |
| 序列化兼容被保护 | 为改名移动字段后只检查编译 | Prefab/Scene/存档的持久化身份是否变化？ | 单独做迁移与加载验证；公开API改名检查调用方 | 不把任何字段重命名自动认作安全重构；本轮未测试具体Unity迁移API |
| 事件有明确寿命 | Start订阅静态事件，停用后仍回调 | 订阅方活多久，发布方活多久？ | 配对选择启用期/对象期/显式会话期，保留可移除的处理器 | OnEnable/OnDisable并非适合所有事件；集合事件须核对变更与通知的先后及异常边界 |
| 异步有提交资格与归属 | await后直接改UI；只传token便称安全 | 谁观察异常、拒绝旧结果、清理未接管资源？ | 请求身份/有效期与producer取消分开，显式交接协议；CQ-08 | 不保证所有await回主线程，不混用Dispose/Release/Destroy |
| 资源API表达ownership | `Set(texture)`隐含复制/借用/接管 | 这次调用到底取得哪种责任？ | 在名称/契约/类型上区分借用、创建、接管、归还；CQ-06 | 不对共享/引用计数句柄套独占释放模型 |
| 风格可自动维护 | Review几十条括号/空格覆盖真实bug | 哪些规则已有确定检查器？ | 按团队EditorConfig/现有分析器处理，格式化与行为改动分离；CQ-01/02 | 不把“现代语法”当兼容性保证；本轮未安装或集成StyleCop |
| 性能结论有口径 | `LINQ一定GC`、`for一定快` | 哪个调用、输入、后端、频率和指标？ | 先定位热点/预算，再控变量测量；CQ-05显示输入类型特化分支 | 源码里出现new不直接等于每次所有平台都分配同样字节 |

## 抽象之前的四问

1. 现在必须隐藏的知识/不变量是什么？不是“以后可能有很多实现”。
2. 哪个真实变化会通过这个边界被局部化？给一个已存在需求或明确外部契约。
3. 调用者省下了哪些信息，又多了多少跳转、配置、初始化和调试路径？
4. 不抽象、少量重复，或者普通函数/委托能否以更低成本满足需求？

接口、泛型、事件、策略、工厂、装饰器都只是候选工具。优先选能明确承担责任的最小结构，既不禁止模式，也不把模式数量当设计质量。

## 冲突时的顺序

先检查行为与项目硬约束，再在满足条件的候选之间比较理解/修改成本。安全与数据正确性不是“代码更简洁”的交换筹码；真正需要权衡的性能/可维护性冲突必须给预算与证据。若两种表达都清楚、风险相同，沿用项目风格，不为个人偏好扩大diff。

“必须改”要附失败场景或已确认契约；“讨论”要附阅读/修改任务及备选；“可选”明确标注偏好。完整清单见 [Review 清单](code-review-checklist.md)。
