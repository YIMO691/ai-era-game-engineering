# AI Code Quality Engineering Protocol（AI-CQEP）

> 公开导出说明（2026-11-12）：以下为原稿研究或通用模板，不是实际配置；历史状态、检查与未运行项不因公开授权而升级。来源与排除边界见 [README](README.md) 和 [导出清单](export-manifest.json)。

**版本：0.2.0 · 按真实研发工作流修订的草案 · 2026-11-06**

> **核心命题：存在可迁移的工程决策顺序，不存在脱离需求、项目与运行环境的万能代码质量解。**
>
> AI-CQEP 用少量约束组织理解、设计、实现、验证、审查和反馈。它旨在减少可避免的工程失误，使任务的依据、修改和证据可以被核查；它不是“照做就一定写出优秀代码”的证明，也不是工具安装方案。

**使用定位：本文是按需查阅的工程判断依据，不是每次任务的执行脚本。** 正常功能开发先把需求拆成有项目依据的方法级方案，经一次整体人工审核，再逐点实现、审查、联调并提测；稳定项目规范由 AI 主动落实，不让用户逐项监督六阶段。

日常入口：[精简工作流](QUICK-REFERENCE.md)。已有规范优先，缺口才用 [项目工程契约模板](PROJECT-CONTRACT-TEMPLATE.md)。如何复用现成项目文档：[采用说明](CLAUDE-ADOPTION.md)。

## 1. 宗旨、适用对象与核心命题

### 1.1 质量目标

高质量代码首先满足真实需求与硬约束，并让维护者能够可靠回答：

- 这段代码为什么存在，承担什么职责？
- 输入如何变成输出，状态和外部世界在哪里改变？
- 谁拥有状态、任务与资源，失败或退出后谁负责？
- 这次修改影响哪些契约，如何发现、验证和回退问题？

命名、函数组织、抽象和注释服务这些任务，不独立构成质量认证。代码短、类少、接口多、覆盖率高或编译通过，都不是整体质量的充分条件。`R1`

本协议适用于修改既有代码、新增功能、缺陷修复、受控重构和性能改进。语言、框架和 Agent 可以不同；具体规则与验证入口由项目提供。探索性原型可以减少交付与兼容义务，但必须明确其非生产状态，不能在被复用时默认升级保证。

### 1.2 通用解存在于哪里

| 判断层次 | 可以通用的内容 | 必须补充的依据 | 最终责任 |
|---|---|---|---|
| 跨项目原则 | 先确认问题；显式责任与副作用；控制额外复杂性；不伪造证据 | 当前任务的实际情况 | Agent 执行，维护者核查 |
| 项目上下文 | 模块职责、依赖方向、接口兼容、团队表达习惯 | 项目契约、实际代码、维护决策 | 项目维护者定义；Agent 不擅自改写 |
| 技术栈机制 | 构造与销毁、线程、取消、资源释放、序列化 | 目标版本文档、实现与环境 | 有能力的工程人员核对，工具按范围验证 |
| 运行事实 | 给定输入是否正确、竞态是否暴露、性能是否达标 | 对应测试、构建、设备或生产观测 | 实际执行链与结果解释者 |
| 业务与价值取舍 | 要什么行为、可接受的风险、成本和时间边界 | 业务目标、法律/安全要求、团队决策 | 获授权的人；Agent 可比较而不代决策 |

因此，“统一协议”统一的是**提问、决策、停止条件与证据责任**，不是统一所有项目的类结构、设计模式和代码风格。

### 1.3 “质量下限”的准确含义

本协议提出的是**条件性的过程保障**：在项目契约可获得、Agent 有能力理解、必要验证可执行、关键决策有人负责的前提下，让无依据实现、隐藏责任、无关重构和虚假通过更难混入交付。

它不建立可计算的代码质量下界。自然语言协议不能强制模型遵守；检查器只检查其覆盖范围；项目契约本身也可能错误。**遵循程度可以核查，质量收益仍须在真实任务中验证。** 当前没有本协议的质量提升、首轮通过率或维护成本实验。`R2`

## 2. 通用原则：八条最小约束

以下八条是协议的常驻核心。后续章节负责解释触发条件，不要求每次任务重述全文。

| ID | 核心约束 | 可观察的执行动作 |
|---|---|---|
| U1 | **目标不明，不臆造行为。** | 明确目标、非目标和可观察验收；关键未知先查证，仍不能消除则提问或停止受影响部分。 |
| U2 | **先读真实上下文，再决定修改。** | 阅读将改内容及必要调用方、数据/状态路径、测试与相似实现；不以目录摘要冒充理解。 |
| U3 | **先确定责任，再选择结构。** | 指明状态权威、外部副作用、资源/任务所有者、失败与退出责任。 |
| U4 | **选择满足当前契约的最简单完整方案。** | 先查复用；新增抽象须解释现在隐藏什么知识、减少什么责任；不为外观整洁扩大修改。 |
| U5 | **保护契约和修改边界。** | 区分有意改变与必须保持的行为；发现范围、权限或契约冲突，回到决策点。 |
| U6 | **用对应证据验证对应主张。** | 按风险执行检查，报告真实状态；修复后更新受影响证据；不将编译、自评或零发现外推。 |
| U7 | **按风险增加独立审查，逐项核对发现。** | 需要时使用未参与实现的审阅者；区分缺陷、设计讨论、风格，不以角色或投票代替证明。 |
| U8 | **只沉淀已确认且可复用的经验。** | 先修具体问题；查现有规则；仅在有复用价值时更新，并保留原因、范围、例外及淘汰条件。 |

**小任务可以压缩记录和阶段展示，但不能压缩事实诚实、授权边界与必要验证。**

## 3. AI 工程能力模型

这里的“能力”是完成一项工程责任的能力，不是一个新 Agent 或 Skill。一个主线程即可承担大部分责任。

| 能力 | 合格输出 | 常见假象 | 主要校验方式 |
|---|---|---|---|
| 问题界定 | 将请求转成输入/状态、预期结果和不变项 | 复述需求后直接编码 | 用户意图与既有契约核对 |
| 上下文定位 | 从入口追到责任边界，指出事实位置和未知 | 列出大量文件，未追实际路径 | 源码、调用方、配置和测试互相对照 |
| 设计判断 | 能解释最小方案及必要取舍，也能选择不改 | 套用固定分层、模式或行数阈值 | 具体阅读/修改任务、备选成本、维护者判断 |
| 实现表达 | 名称、控制流和结构兑现责任与契约 | 局部漂亮但状态、依赖和时序隐藏 | 源码阅读及行为验证 |
| 验证设计与执行 | 选择能推翻错误假设的检查并真实执行 | 写了测试、命令退出，就宣称通过 | 测试目标、报告、终态与最终改动对应 |
| 审查与证伪 | 对发现给条件、路径、后果和证据，能撤回误报 | 用严重性或置信分数替代依据 | 独立读取、运行复现或限定的静态论证 |
| 反馈治理 | 改善重复决策而不是堆积规则 | 每次 Review 自动生成新规范 | 跨任务失败记录、规则执行与噪声观察 |

编译器、分析器和测试并不替代这些能力，而是承担其中可以明确程序化的部分。人类负责关键意图、授权和价值取舍。能力不足或证据缺失时，应缩小承诺，不能靠增加角色名称掩盖缺口。`R2`

## 4. 正常研发工作流、六阶段责任与风险裁剪

### 4.0 日常主线：先形成可审方案，再受控实施

**常规功能开发默认采用：需求文档 → 功能点拆解与项目调查 → 方法级实施方案 → 一次整体人工审核 → 逐功能点实现 → 代码质量审查与功能联调 → 提测。** 六阶段是这条主线的责任框架，不是六次审批、六份报告或固定 Agent 编排。

先分清三类内容：**稳定项目规范由 AI 直接执行；本次实现选择由 AI 调查并提出；业务取舍与整体方案由有权人员审核。** 不把命名、排版、已确定的分层等重新交给人决定，也不因为没有未决业务问题就跳过已约定的编码前方案审核。

- **常规功能开发：** 无论风险等级，先提交可审核方案，得到人工确认后写业务代码。审核的是功能覆盖、范围、方法职责、关键取舍与验收，不是要求人逐行设计。小功能的方案可以很短，但不能只凭标为 L 就越过审核。
- **已审方案续作：** 在批准范围内自主逐点推进，不为每个方法、功能点或阶段重复请求批准。上下文变化时仅补读缺失或改变的事实。
- **边界明确的局部小修：** 项目或用户已授权直接修复时，可用短简报实施；不因此省略源码阅读、自查和针对性验证。只读咨询、纯文档维护按实际任务裁剪，不强加业务功能方案门槛。

这是协议的采用默认，不会自动改写项目现行流程。若项目已有不同的审批约定，应明确本次采用哪种方式；**不得以引入 AI-CQEP 为由擅自增加项目门禁或修改其规则。** 风险增加首先增加调查、验证和审查深度，不自动增加人工审批次数。

### 4.1 风险决定调查与验证深度，不决定是否绕过方案审核

风险取决于后果、影响范围、未知程度和恢复难度，**不按 diff 行数或文件数量计算**。先按 4.0 确定任务方式，再分风险。

| 等级 | 判定条件与例子 | 执行深度 |
|---|---|---|
| L：局部、已知、可逆 | 行为与验收明确；责任边界不变；影响可界定；已有直接验证。例：已定位的纯函数边界修复、确认无持久化影响的局部命名调整 | 已授权小修可合并 P1/P2 为短简报；常规功能仍先审方案；相关检查和代码自查必做，独立审查可不启用。 |
| M：存在重要协作或不确定性 | 局部业务新路径、外部依赖适配、错误处理、事件/异步有效期等；影响可界定但需专门验证 | 方法方案交代协作、失败和验证；检查正常及关键失败路径；按主要风险选择定向独立审查，不固定多角色。 |
| H：高后果、跨契约或难恢复 | 权限、安全、真实资金、不可逆数据、迁移、公共协议、跨模块所有权/并发策略、关键资源寿命、关键性能预算，或影响范围无法界定 | 方案补齐兼容、验证与恢复边界；关键检查及独立审查为完成条件；必要时领域人员参与，不要求逐方法审批。 |

升级规则：出现任一高后果触发项即按 H 处理，不与低风险项平均。未知只影响代码风格时无需升级；未知可能改变正确性、责任或恢复方式时，不能按 L 执行。已被充分理解、隔离且有直接回归证据的生命周期局部修复未必都属于 H，但改变其所有权协议通常属于 H。

不确定时先做**最小只读调查**；仍无法界定影响则保持较高等级。项目指定的人可以裁剪流程，但必须说明理由与剩余缺口；风险接受不使未运行的测试变成通过，也不豁免安全或合规硬要求。

### 4.2 P1：Context Understanding — 需求拆解与上下文理解

**进入条件：** 有任务，读取范围已获授权。

1. 先按可单独描述、可验证的业务结果拆功能点，沿用已有编号；没有编号时可用 F01、F02。每点明确触发条件、正常/适用异常行为、非目标、依赖和验收。**先拆业务，再落方法，不按文件或技术层拼批次。**
2. 按需读取现行项目指令、相关规范、功能资料和实际入口，追到规则、权威状态、副作用、通知/清理及必要调用方。稳定规则已在有效上下文中时不反复读取，不全库扫描。
3. 核对真正相似的实现、版本、资源/任务所有者、兼容与验证入口。知识库是定位资料；源码证明当前实现，不能自动覆盖有效需求。资料冲突分别记录。
4. 区分已核实事实、设计推导和待验证事项；为各功能点选择风险与验证方法。可查事实自行核实，只把查后仍决定业务、重要契约或授权的缺口交人决定。

**产物：** 在原功能说明或任务记录列出功能点、范围、依赖、完成条件和关键事实入口。小修可只写目标/不变项、修改责任、验证方法三句；不新建整套阶段文档。

**退出条件：** 能解释本次关键路径和不变项，功能点有可观察验收；剩余未知不决定接下来设计的正确性或授权。与未知无关的工作可继续，不能把依赖它的方案写成已确定。

### 4.3 P2：Design Judgment — 方法级实施方案与整体审核

**进入条件：** P1 对当前范围足够；不要求理解整个系统。

按“既有责任边界与复用 → 状态权威和不变量 → 主流程与失败收尾 → 必要结构 → 验证和恢复”决定实施方式。新增抽象应说明现有方式的具体缺口；有实际竞争方案时比较主要成本，不强制罗列三个架构。

**产物：可审核的方法级实施方案。** 复用既有分端手册或任务记录，明确标为“拟实施，待审核”，不要写成当前实现。至少能沿下列关系双向追查：

| 功能/验收编号 | 文件、类型与方法落点 | 本次操作和职责 | 实现依据/选择理由 | 验证编号与方式 |
|---|---|---|---|---|
| F01 / A01 | 真实的既有位置；新增方法标“拟新增” | 复用 / 修改 / 新增；承担什么，不承担什么 | 规则/源码位置；为何适用；关键未知 | 输入/状态、预期、自动检查或真实联调 |

预计新增、修改的方法应有清单并关联功能点；纯复用方法标出调用和契约依据，不为复用重写完整手册。**关键入口、规则、状态提交、外部调用、异步与资源交接方法**还须交代：

```text
方法：真实或拟定的类型.方法、参数与返回；对应功能编号。
逻辑：输入/前置条件 → 规则与分支 → 状态/外部副作用 → 结果/通知。
边界：调用关系；失败、重复、重入、取消、关闭/销毁；状态/任务/资源归属。
依据：适用项目规范与当前源码位置；选择理由；必要替代方案及代价。
验证：对应验收、边界和失败路径；检查方式；需要的真实环境与未覆盖项。
```

写到能够审核责任、顺序、配套与验证即可；简单辅助方法可以一行说明，不为凑粒度预造函数，也不提前写所有方法体。复杂度、内存、线程、兼容等在确有触发时具体说明，不机械填满“不适用”。

**依据必须分三类：** 已核实事实说明“现在是什么、来源在哪里”；设计理由说明“因此为何选择此方案、代价是什么”；待验证事项说明“实现后用什么检查确认”。设计合理不等于运行已证实；不要求为每条常规命名或格式重新写论证。

**人工审核与退出条件：** 常规功能提交一次整体方案，待有权人员明确同意该版本和范围后进入 P3。审核看功能是否遗漏或发散、职责/复用是否合适、关键风险是否闭合、验收是否对应需求。已有有效批准不重复审核；仅局部小修等按 4.0 的已授权简化方式推进。批准方案不授权提交、发布、新服务外发或不可逆业务操作。

### 4.4 P3：Quality Implementation — 按功能点贯通实现

**进入条件：** 方案可执行，满足约定的整体审核与修改授权。

- 一次完成一个可验证功能点所需的代码、协议、配置、资源接线、注释与结构整理、针对性验证和文档同步，再进入下一点。不先铺满多个功能点的空结构；公共部分只做当前点必需内容。
- 沿项目风格和既有边界实现，不建立平行框架。主流程连续可读，重要规则、提交和清理可见；实际事务/事件顺序不能为模板改写。
- 缺陷修复尽量先得到能区分旧新行为的失败断言；编译/环境失败不冒充行为红灯。P3 与 P4 逐点交替，不等全部写完才第一次验证。
- **无需重新审核的细节：** 不改变已审行为、契约、职责和风险的局部命名、排版、私有辅助方法组织等，由 AI 自行处理并同步实际方法清单。
- **需要差量审核的变化：** 新增业务范围、改变已审行为/验收、公共接口、模块职责、状态/资源所有权协议，或扩大授权及不可逆影响。只提交变化、依据、影响和验证差量；暂停依赖该变化的动作，不推翻仍有效的整份方案。
- 原方案不成立或硬约束矛盾时先回 P1/P2，不用 TODO、吞错、放宽断言或“顺手优化”绕过范围控制。

**退出条件：** 功能点及必要配套已实现，已完成适用检查和文档更新。逐点保留已实现、已验证、待验证、阻塞状态；单点完成不代表整个功能已联调通过。

### 4.5 P4：Deterministic Verification — 开发验证与功能联调

**进入条件：** 有可检查切片；与 P3 交替，最终再核对完整链路。

1. 从需求/验收编号选择输入、边界、失败与回归检查，不照抄实现作为预期；使用已有适用入口，不为协议完整默认安装工具。
2. 核对执行终态、实际对象和新鲜报告。退出码 0、旧报告、空集或关键用例全跳过不构成行为通过。`R2`
3. 记录受检版本、命令/步骤、工作目录、环境、结果和证据位置；失败区分实现、测试契约、基线与环境，修复后更新受影响证据。
4. 在真实配套可用时按业务入口完成开发联调，核对代码、配置、协议、资源和目标环境实际加载。受控测试、编译与单端成功不能冒充完整联调；必要条件不可得就逐项标待验证。
5. 收尾用原需求反查：每个功能点都有实际结果，每个新增行为有已审依据，跨点组合与回归有覆盖，不仅逐个方法“能跑”。

**退出条件：** 必要检查和开发联调有与最终产物对应的真实结果；必要项失败或未执行则保留阻塞/待验证状态，不宣称完全符合需求。

“确定性”指明确输入与程序规则的执行责任，不保证无环境/调度波动。保留原始失败，不反复重跑直到一次绿色就隐去风险。开发联调不替代 QA 的独立测试。

### 4.6 P5：Quality Review — 代码质量审查与必要的独立审阅

**进入条件：** 有最终改动、必要周边和验证记录。审查发现可使流程回到 P3/P4，不必僵化串行。

**所有实现都要检查两个维度：** 一是命名语义、方法职责、主流程、适度抽象、必要注释、结构排版及项目约定；二是实现与已审需求/方案、错误路径、生命周期、兼容和联调证据是否一致。作者自查必做，但不冒称独立审查；也不把整齐或短小当功能正确。

- L 可不启用额外独立审阅，不省略代码自查与行为验证。
- M 按主要风险选择定向独立审阅；必要时说明现有证据为何足够，而不是以代码少为理由。
- H 默认必须有未参与实现的审阅者；不可得则保留缺口，项目有权人员可显式接受延后，但不能称完整协议验收通过。必要的安全/法规审查不能由 AI 文本豁免。

审阅者可为项目已有人员，不默认新增 Agent、Skill 或外部服务。新的 AI 上下文只是**角色与上下文层面的独立阅读**，不是独立运行证据。提供需求、已审方案、项目约束、最终改动及必要周边，不预置作者结论或答案。

默认只读，发现按第 7 章格式逐项核对。必须修复、设计讨论、可选风格分开；修复后复验并更新文档。审查不授权修改、外发、提交或发布，自然语言“只读”不是安全沙箱。

**退出条件：** 必须修复项已处理，关键补证完成；设计争议有决定，最终证据仍适用。零发现或另一个 Agent 同意不证明无缺陷。

### 4.7 P6：Handoff & Feedback — 提测交接与反馈

**进入条件：** 开发收尾，包括失败、阻塞或决定不改。

常规功能的提测材料复用现有验收记录，给出：**交付版本/范围、功能与验收入口、环境和必要测试数据、实际开发验证/联调结果、回归影响、已知问题/未覆盖项与下一步。** 不在交接中放凭据，也不重新复制全部用例定义。

按第 7.5 节区分开发完成、验收待验证和阻塞。“提测就绪”须满足已约定的开发完成条件；必要联调/审查缺失时不能无条件宣称就绪。确需限范围提前移交，由有权人员接受已列缺口并标为受限提测。QA 的独立测试、产品验收和发布批准是后续不同责任，不由 AI 自行宣布通过。

偶发问题修当前内容；重复或单次严重且已核实、可复用的机制，优先补已有契约、测试或检查器，不新增同义规则。最小记录为 `原因/依据；范围与版本；执行载体；维护角色；例外；解除条件`。

**退出条件：** 实际结果、提测范围及缺口已交接；值得复用的反馈已更新或交维护者决定。没有新知识时不生成复盘文件，也不因收尾自动创建工单、发消息或发布。

## 5. AI 编码决策流程：优先改善首次实现

首次质量主要依靠正确定位、责任判断和及时验证，不靠最后再加几轮“让代码更优雅”。以下为 Agent 的实际决策顺序。

### 5.1 编码前的行动算法

```text
1. 确认目标、授权范围、目标副本、已有修改和数据通道。
   不允许处理的材料不读；需要新权限先确认。
2. 确定任务方式：新功能先形成方案；已审方案续作不重复审核；
   明确授权的局部小修可简化；咨询/文档不套业务开发全流程。
3. 按可验证业务结果拆功能点与验收，查现有规则和真实关键路径。
   可查事实自行核实；业务/契约/授权仍未决则只暂停依赖动作。
4. 按最高后果分 L/M/H，增加相应调查、验证与审查，不增加例行审批。
5. 查复用与责任：语义吻合则调用/扩展原边界；确有缺口才新增结构。
   列清预计新增/修改方法，关键方法交代输入输出、顺序、分支与收尾。
6. 将功能 → 方法 → 事实/选择理由 → 检查/联调关联为可审核方案。
   常规功能等待一次整体人工确认；已有有效批准不再等每点批准。
7. 逐功能点贯通实现、代码整理、针对性验证和文档同步。
   内部可逆细节自行处理；重要行为/契约/范围差量回到方案审核。
8. 反查原需求 → 代码质量审查与完整开发联调 → 修复并更新证据
   → 如实提测交接；QA 独立测试不由开发自查替代。
```

“已授权小修可直接实现”不表示跳过源码阅读、验收或项目规则；“常规功能先审方案”也不表示每个方法都要单独批准。仅新建、隔离、无项目依赖的示例，且用户给出完整契约时，可以不探索既有调用链；仍要核对目标位置、指令与环境。

### 5.2 阅读到什么程度才够

不是“读越多越安全”，而是达到以下停止条件：

- 能从真实入口解释受影响的正常路径和主要失败路径。
- 知道第一次状态/外部副作用发生在哪里，失败后由谁收尾。
- 找到兼容要求与测试入口，或明确关键资料缺失。
- 已知未读范围不会决定本次设计；有依据而不是凭感觉。

沿依赖边扩展阅读：调用者决定输入和使用契约；被调用方决定异常、线程和所有权；持久化/资产决定静态代码看不到的入口。不为完成探索遍历全仓，也不以读完一个类就默认影响已封闭。

### 5.3 复用与新增抽象的闸门

复用前核对：输入/输出、失败语义、状态权威、生命周期、性能与版本是否吻合。只有代码形状相似不算匹配；不能为复用反过来扭曲需求。

新增接口、策略、工厂、通用帮助类、事件层或泛型抽象前，回答：

1. **现在**要隐藏哪项知识、保护哪个不变量或限制哪种依赖？
2. 谁因此不再承担哪些信息/责任？给出具体调用者或变化场景。
3. 现有边界、普通函数或少量局部重复为什么不够？
4. 新增接线、跳转、配置、错误路径、测试和生命周期成本是否值得？

答不出前两项，或全部理由只是“以后可能扩展”“看起来专业”“重复超过几次”，应拒绝本次抽象。单一实现的接口可以隔离外部风险；调用一次的函数可以封装复杂协议。数量不是否决或批准依据。`R1`

若现有模式与明确硬契约冲突，不应复制其缺陷；在最小范围修正，结构迁移另提。沿用项目不意味着继承已确认的错误。

### 5.4 编码中即时判断

| 决策 | 应采取的动作 | 应拒绝的理由 |
|---|---|---|
| 函数要拆吗 | 当一段形成可命名的规则/协议，调用者无需再知其细节，且不会隐藏必须可见的责任时提取；提取后检查主流程是否更易追踪 | “超过 N 行”“每行一个函数”；提取后仍须读全部细节且只增加跳转 |
| 类/模块要拆吗 | 状态权威、变化原因或依赖边界确实不同，拆分后能独立承担契约；核对接线成本 | “一个类方法太多”；把一个不变量分散到多个任意写状态的服务 |
| 要写注释吗 | 补充代码难表达的原因、限制、版本、失败/线程/所有权义务；先改误导名称 | 逐行翻译代码；用长注释为不必要结构辩护；无证据的性能保证 |
| 要重构吗 | 当前任务被阻碍，或已有具体缺陷/维护成本证据；可说明收益、行为不变项、验证与回退 | 顺手美化全仓；仅偏好新语法；无法界定兼容影响 |
| 要做防御检查吗 | 外部输入、可恢复运行失败和明确边界需要检查；内部不变量违约按项目方式显露错误 | 任意判空、catch 全部、静默返回默认值，让错误状态继续传播 |
| 要优化吗 | 先确认硬预算或热点证据，再保持行为比较候选并测量 | 仅凭语法给 GC/速度结论；无预算无热点却引入池化与缓存 |

若判断收益不清楚，默认保留现状或采用较小方案；这不是“永不改设计”，而是要求设计收益承担举证责任。

### 5.5 复杂业务如何保持主流程清楚

先把业务步骤、状态转换与不可逆提交写成短序列，随后让代码映射这条序列。纯规则、I/O 适配和真正复杂的协议可有命名边界；不要把必要时序分散到不明监听者和转发层。

- 多阶段合法状态优先用明确状态与转换表达，不靠互相影响的布尔值猜组合。
- 把“查询/判断”和“提交/通知”的副作用区分清楚；有意混合的 API 必须兑现其名称和契约。
- 不通过吞异常使入口显得顺滑；错误在能恢复、补偿或最终报告的层处理。
- 提交前校验、提交后的通知和失败补偿可能具有领域特定顺序，必须从契约出发。
- 不在持锁、事务或资源交接中随意插入回调；回调可能重入或失败，影响原子性。

代码应让重要责任**容易看见**，而不是让所有复杂性都消失。

### 5.6 不制造任务文档负担

任务事实放当前记录；长期约束放项目契约；稳定设计依据放已有决策记录或就近注释；可确定检查的规则放已有验证链。一个事实只保留一个权威入口，其余引用。

已授权局部小修可只用三句：目标与不变项；修改点与责任；验收方法。常规功能复用已有功能说明、分端手册与验收记录，方法方案只展开本次变化和关键风险，不另建六份报告或固定增加实施文档。稳定规范不逐项抄写和报批；项目事实不足只补当前决策必需信息。

## 6. 代码设计与表达原则

本章将第一轮知识变成选择规则，不重新建立 Clean Code 教材。`R1`

### 6.1 命名、签名与职责

- 名称应让调用者预测行为：查询还是消费、单位是什么、失败如何表达、是否有重要副作用。名称不可能承载全部协议，剩余义务由类型和必要文档补充。
- 职责围绕要保护的不变量和变化原因划分，不按“方法只做一行”划分。
- 不为所有类型自动增加 `Manager/Service/Factory` 或同名接口；也不机械删除已有合理接口。
- 简单预期缺失可用已有 Try/可选值惯例；多种业务结果需可区分。不为统一而把取消、非法输入、缺数据和系统故障都压成一个 `false`。

### 6.2 状态、依赖、副作用与生命周期

- 一份业务事实应有明确权威；副本、缓存和投影必须说明更新与失效规则。单一权威不要求所有数据集中在一个巨型对象。
- 依赖通过项目已有机制明确提供；全局定位器、隐式事件和魔法初始化顺序如果让责任不可见，应指出具体代价，不为教条另造容器。
- 资源协议区分创建、借用、共享、接管、归还与销毁；GC、作用域退出或某个名为 `Release` 的方法不通用于所有资源。
- 异步分别处理执行位置、取消请求、结果有效性、交接与异常观察。取消不证明 producer 已停止；停止等待后可能仍有迟到结果。
- 重试和恢复前考虑外部操作是否已发生；缺少完成记录不证明操作从未执行。非幂等副作用需要查询、幂等标识、补偿或人工处理，不盲目重放。`R2`

### 6.3 抽象、重复与注释

DRY 的操作目标是避免**同一规则的多处权威**，不是消除所有相似字符。独立变化的相似逻辑可以分开；同一协议反复漂移则值得集中。抽象必须真正接管责任，不能只隐藏几行语句却把初始化、错误和清理义务留给所有调用者。

注释优先记录“为什么这样、何时不成立、改动会破坏什么”。可观察行为由代码表达，调用义务可由 API 文档补充。历史兼容说明应包含解除条件或可追踪依据；相关实现改变时同步更新或删除。

### 6.4 性能与可理解性

已批准的硬性能预算是可行方案的约束，不能用“更清晰”豁免。先找到满足正确性、安全、兼容和预算的候选，再比较理解/修改成本。没有预算的优化愿望不能自动覆盖可维护性。

必要复杂优化应局限在明确边界，保留简单行为参考或对照测试、原因和目标环境测量。缓存、池化、增量维护减少某项成本时，增加的失效、复用、保留内存和并发责任也要验证。未测量时只能给机制假设，不写“更快”“零分配”的事实结论。`R1`

## 7. 验证、审查与交付机制

### 7.1 谁能判断什么

| 主张 | 主要证据 | 不能据此推出 |
|---|---|---|
| 符合选定风格/静态规则 | 实际执行的格式器、分析器及其版本/配置 | 名称符合业务、职责合理、无缺陷 |
| 目标输入可编译/类型正确 | 目标编译链与实际构建结果 | 业务正确、资产绑定正确、架构优秀 |
| 某行为成立 | 有效断言、受控输入/顺序、实际测试结果 | 未覆盖行为也正确；mock 等于真实外部系统 |
| 不违反依赖禁令 | 对明确非空对象集的依赖检查，配关键对象和违规负例 | 规则本身合理、全部运行/资产关系已覆盖 |
| 生命周期/资源行为符合约定 | 对应宿主的状态、调用次数、线程和清理检查 | 任意平台、强杀或永不完成路径都安全 |
| 性能满足预算 | 代表负载、目标环境、基线与重复测量 | 所有设备都提升；源码推测等于测量 |
| 结构便于理解与修改 | 具体阅读/修改任务、候选比较、维护者反馈 | 存在客观优雅总分，AI 一致同意就是实证 |
| 产品取舍可接受 | 获授权的人结合业务、安全和成本决定 | Agent 可以替代授权或用测试证明价值选择 |

已知边界可编程时优先程序化；意图、合理边界和可维护性仍需判断。判断也必须具体，不以“最佳实践”免除举证。

### 7.2 最小验证记录

```text
检查目标/对应验收：
受检版本：最终提交，或内容快照/文件集合；不要虚构 Git 提交。
命令或人工操作步骤；工作目录；相关工具/目标环境：
预期对象/关键用例；实际执行对象/数量（若适用）：
退出码与终态；原始报告/日志位置：
结果：通过 / 失败 / 跳过 / 未执行。
原因、未覆盖项与结论边界：
```

状态含义：

- **通过**：检查真实执行，命中预期对象，满足判据；只在检查范围内成立。
- **失败**：实际结果不满足判据；注明是行为、编译、配置还是环境失败。环境失败不证明产品行为失败，但确实没有完成对应验证。
- **跳过**：执行链明确排除了检查或用例；给原因和影响。
- **未执行**：没有启动或无法取得有效结果；中止、超时或报告损坏应保留真实执行状态，并将验收标为未获证实。

“不适用”是检查选择的理由，不是执行结果，不应计作通过。仅建议运行的命令必须标为建议。

最终代码改变后，先前结果是否继续适用需要判断：行为变化重跑受影响行为/构建；注释变化可复用仍适用的行为结果，但要核对注释与实现。记录证据适用范围，不机械要求每个空格重跑全平台，也不默认修复后旧结果全部有效。

既有失败与新增失败分开，保留基线；不能无证据声称“与本次无关”。必要检查受既有失败阻塞时，仍是验证缺口，而不是隐去后算成功。

### 7.3 按风险选择验证，不按工具数量凑齐

- 纯规则缺陷：区分旧新实现的用例、边界、相关回归、目标编译。
- 协作路径：正常、拒绝、异常、重复与关键顺序；外部系统的实际契约验证。
- 异步/资源：可控完成顺序、失效、取消、异常、接管/释放次数与线程；不要只用随机延迟。
- 持久化/公共协议：旧数据/客户端兼容、迁移与恢复，不能只验证新数据。
- 性能：行为对照、预算、目标环境和代表负载，保留原始数据。
- 纯文档/表达调整：结构、链接、事实与影响范围；涉及序列化或反射的“改名”不归入纯表达。

测试断言来源于需求和契约，而非照抄新实现。必要时用旧实现行为对照、已确认反例、独立参考数据或人工验收。作者写的测试有价值，但可能与实现共享误解；AI 自己写、自己通过的测试不等于需求已独立确认。

### 7.4 独立审查发现格式

```text
类别：必须修复的工程缺陷 / 需要讨论的设计问题 / 可选风格建议。
位置：文件:行号，或实际可定位的配置/资产位置。
契约：对应需求、项目规则或明确义务。
条件：具体输入、状态、调用/完成顺序，或具体阅读/修改任务。
路径：从条件到相关代码和副作用的推演。
后果：错误行为/违约，或具体理解、修改成本。
证据：源码事实 / 静态推断 / 运行复现 / 人工确认；剩余未知。
建议：最小修复或备选及代价；验证方法。
```

分级要求：

- **必须修复**需要可核对的失败条件或硬契约违背。严重要害但缺证据时可阻塞并要求补证，不冒称已确认 bug。
- **设计讨论**需要具体维护场景和候选成本，不要求伪造崩溃；一个跨七层转发寻找提交点的阅读任务可以成立。
- **可选风格**说明偏好或尚未成为项目约定的选择。没有错误路径就写“不适用”，不能为满足模板编造后果；不阻塞合格交付。

影响程度与证据强度分开。理论上严重的风险可能尚未核实；已复现的小问题也可能影响有限。

处理结果使用 `接受并修复 / 有依据反驳 / 待补证 / 范围外交接`。必须修复项不能仅以“范围外”结束：若本次引入、恶化或直接影响验收，必须处理或明确阻塞。真正无关的历史问题另行登记，不顺手全库修复。

### 7.5 完成门槛与停止条件

本节的**完成验收**指约定的开发交付范围：目标达到；必要证据与最终产物对应；没有未解决的必须修复项；需要的审查与开发联调已完成；剩余设计取舍已有决定。它不表示 QA 独立测试、产品验收或发布批准已经完成。常规功能据此判断是否提测就绪；必要项缺失只可如实待验证或经有权人员接受缺口后受限提测，不能无条件报就绪。

允许三种交付状态：

1. **已完成并按列明范围验证**：满足上述条件；列出未覆盖但不影响本次验收的边界。
2. **实现已完成，验收待验证/待决定**：代码可供接手，但必要运行、审查或业务选择缺失；不得简称“全部完成”。
3. **阻塞或未完成**：方案无法成立、关键缺陷未解、权限不足或风险不可接受；保留已有结果与可执行下一步。

连续修复仍出现同类问题、原假设反复被推翻、成本超预算或无法取得关键证据时，停止自动迭代，缩范围或交维护者决定。不追求无限轮“审到零发现”。

## 8. 两层结构与项目工程契约

### 8.1 第一层：Universal Engineering Protocol

本协议规定从需求到方案、实施、验证和交接的决策责任，不规定语言语法、固定类模板、测试框架或目录树。八条是 AI 的判断约束，六阶段是责任索引，不要求每任务重读全文或逐项向人汇报；按风险选择深度，按已有授权与有效审核结论推进。

### 8.2 第二层：Project Engineering Contract

项目契约是项目自己定义的可执行边界，不是把协议再复制一次。至少提供**当前任务需要的**：

- 技术栈、版本和构建目标；事实入口与已确认状态。
- 架构/模块边界、允许依赖、状态权威与资源/任务所有者。
- 命名/编码约定及已有配置位置。
- 错误、线程、生命周期、持久化与兼容规则。
- 验证命令/操作、判定方式、环境限制和性能预算。
- 允许读取/修改范围、材料处理通道、需人工决定的操作。

**契约是一组有效约束，不是一份必须新建的文件。** 已有项目指令、规则导航、功能手册与验证入口足够时，直接使用；只有必要事实缺口才用 [模板](PROJECT-CONTRACT-TEMPLATE.md) 的相关部分补充。未知标为未知，示例不变成项目事实，不再维护同义副本。

文档分工也沿项目已有方式：业务说明维护需求/非目标/验收；实现手册承载分端方法方案及实际实现；验证记录维护审查、联调和真实结果。拟方案须标状态，实施后更新为当前事实；审核决定和经过留原任务记录。项目仅需在采用时确认整体方案审核如何衔接，不为每功能固定增加一份新文档。

### 8.3 冲突与优先级

先区分规则性质，再谈优先级：

1. **不可交易的边界**：安全/法律硬要求、数据完整性、事实诚实、授权。不能由“写短一点”或用户未授权的便利目标覆盖。
2. **已批准的需求与项目硬契约**：兼容、模块责任、技术/性能限制。若彼此不可同时满足，报告冲突，由有权人员决定变更；不自行选一个然后声称全满足。
3. **协议默认建议与项目惯例**：在不违反前两项时，具体且适用的项目约定优先于一般表达偏好。
4. **同样合格的候选**：优先清晰、局部、可验证、可恢复的方案；无实质差异沿现有风格。

项目契约可以规定某种性能敏感写法或类组织，不必服从一般审美。但它不能把未运行写成通过、把自查写成独立审查，或把未授权动作变成允许。

| 常见冲突 | 处理规则 |
|---|---|
| 简洁 vs 完整 | 删除无关仪式，不删除必要责任、失败路径和验证。最小完整实现不等于最少 diff 字符。 |
| DRY vs 过早抽象 | 共享同一知识和不变量；偶然相似可重复；抽象需证明当前收益。 |
| 整洁 vs 性能 | 先满足正确性与硬预算，在可行候选中比较理解成本；优化需对应环境证据。 |
| 自动执行 vs 人工控制 | 常规功能先审一次整体方案；已审范围内逐点自主推进，普通内部细节不重审；重要差量、未决业务、越界或难撤销外部动作再确认。 |
| 通用原则 vs 项目特殊约束 | 迁移问题不搬运机制；项目提供具体做法，仍保留责任与证据要求。 |
| 现有风格 vs 已确认缺陷 | 保留无害惯例，不复制违约实现；只修必要范围，迁移另议。 |
| 首次质量 vs 快速迭代 | 前置关键判断和可验证切片，不要求一次预知一切；出现反证及时改方案，而非坚持首稿。 |

“遵循协议”也不授予 Agent 修改规则、测试期望、CI 严重级别、权限配置或发布策略的权力。这些变更必须有需求依据和对应授权。

### 9.3 P1/P2：先把失败条件变成设计输入

必须读取：面板打开/关闭与池归还入口、选择回调、既有加载与句柄、现有任务监督、类似面板和测试、相关资产绑定。

编码前确认四个问题：

1. 业务会话关闭和 Disable/Destroy 的关系是什么？关闭后是否允许后台加载但不得展示？
2. 成功结果交出后谁有且只有谁承担归还责任？接管可能部分成功或抛异常吗？
3. producer 忽略取消、迟到成功、异常或永不完成时分别怎么办？
4. 实际在哪个上下文检查身份、更新视图和归还句柄，是否可能重入？

前两个问题未定，不能直接写“传 token + await 后判空”。单独完成取消参数接入不等于这个任务完成。

本次若改变资源交接协议，按 H；若严格沿既有协议修一处身份检查、影响已隔离且测试充分，可按 M。展示短方案：复用现有句柄和监督机制；会话/请求身份拒绝过期提交；不新增通用加载框架。

### 9.4 P3：实现应兑现的算法，不提供伪装成生产代码的片段

```text
打开：建立新的业务会话身份；每次新选择再建立请求身份。
替换/关闭/归还池：先使旧身份失效，再按现有契约请求取消和解除绑定。
  身份失效必须先于可能触发回调的取消/清理操作。
发起：所有加载任务进入现有监督/异常观察路径。
接收成功：按既有执行上下文要求接收句柄；接收路径先承担其责任。
  若会话已结束或不是当前请求：不展示，按句柄协议归还。
  若仍有效：在串行、无 await、无外部回调的交接段检查并完成接管。
  接管成功后，归还责任属于会话；未接管时仍由接收路径负责。
  旧已展示句柄的替换和归还遵守同一明确协议，不能丢失旧责任。
接收失败：按项目错误/取消契约报告，不能伪装成成功，也不重复吞报。
会话结束：归还已接管句柄；迟到任务仍有观察与接收/归还路径。
```

设计前提必须核对：若接管/视图绑定可能抛异常或部分成功，先定义回滚和责任移交点，不直接使用“接管后设 null”的简化算法；清理失败不能悄悄吞掉或掩盖原故障。若无法串行检查与提交，则需要项目认可的同步协议，而不是再加一次判空。

对永不完成的 producer，本例不承诺接收路径的 finally 一定执行；资源仍由 producer 负责。超时若只结束等待，监督与迟到接收仍不能消失。需要强制终止、进程退出或硬截止清理保证时，属于另一个必须明确的系统契约。`R1`、`R2`

### 9.5 P4：验证矩阵与本轮状态

以下断言是落地时需要执行的设计，**全部未执行**。

| 场景 | 预期可观察结果 | 所需证据 |
|---|---|---|
| 正常选择并完成 | 当前模型展示；责任完整移交；旧展示资源按约定归还 | 可控句柄/计数测试，实际视图绑定 |
| A 后发 B，B 先完成、A 后完成 | 只有 B 展示；A 不覆盖，A 句柄恰当归还 | 可控完成顺序，不用随机延迟碰竞态 |
| 请求中关闭/归还池，再同实例重开 | 旧会话结果不影响新会话；无责任空洞 | 会话代次断言 + 实际 PlayMode/池回归 |
| producer 忽略取消仍成功 | 无旧提交；迟到成功仍有人接收并归还 | producer 可控夹具、归还计数、任务终态 |
| producer 抛异常/返回取消 | 所有任务异常被观察；只按项目策略报告 | 监督路径与错误/取消来源断言 |
| 接管或绑定失败 | 按已定义回滚协议维持有效状态；无重复或遗漏归还 | 故障注入；不能只断言没崩溃 |
| 关闭触发重入/重复关闭 | 旧资格已失效；重复清理遵从句柄契约 | 受控回调与实际生命周期路径 |
| 实际 Unity 对象销毁/停用 | 不访问失效视图；语义符合业务有效期 | 目标 Editor/PlayMode；普通 C# 假对象不足 |
| 序列化资产与平台 | 原 Prefab/Scene 绑定未破坏；适用 Player 场景可用 | 资产加载/回归；相关后端构建运行 |
| 热路径或内存预算受影响 | 指定设备与负载下满足批准预算 | 独立的 CPU/分配/保留内存测量 |

普通 .NET 单元测试、Unity Editor 编译、EditMode、PlayMode、目标 Player/IL2CPP、设备测量分别支持不同层次，不能互相替代。Editor 或 IDE 的分析器诊断也不证明实际 Unity/CI 编译加载了同一规则。`R2`

### 9.6 P5/P6：审查与反馈

定向审查只查关键路径：会话新旧资格、取消与提交分离、资源交接、线程/重入、任务异常观察、资产兼容。发现必须给具体状态与位置，不因为有 token 就判安全，也不因为有状态字段就要求删掉。

若真实任务反复漏掉同实例重开的旧请求，可以更新现有生命周期规则或补测试；没有发生的缺陷不能写成经验。若已有检查已经覆盖，就修检查执行，不再复制成五份提示。

完整案例的合格交付应是“上述具体场景在列明环境已执行，并说明未覆盖范围”；本轮只能交付**契约与验证设计**，不能给代码或生命周期安全认证。

## 10. 典型错误与反模式

| 反模式 | 为什么失败 | 协议纠偏 |
|---|---|---|
| 需求一句话，立即生成整个模块 | 未识别业务分歧、状态与现有边界 | P1 先消除决定行为的未知 |
| 读目录树后宣称理解架构 | 缺少真实调用、数据与副作用路径 | U2，沿关键路径阅读并及时停止 |
| 为 Clean Code 把每句提成方法 | 必要时序藏进跳转，没有知识边界 | 函数提取闸门；允许较长而连续的主流程 |
| 每个类配接口和工厂 | 增加接线而未隔离真实责任 | 新抽象四问；复用既有边界 |
| 没有抽象就是最好 | 无法限制能力或隔离外部不稳定性 | 比较当前风险，不机械反抽象 |
| 主流程干净但 catch 后返回成功 | 掩盖失败与半状态 | 在能恢复或最终报告的层处理错误 |
| 为了绿灯删断言、调阈值、抑制未知诊断 | 改变验收而非修实现 | 验收变更单独说明依据和授权 |
| 编译过了，宣布架构优秀 | 将一个证据层外推到设计层 | 主张—证据逐项对应 |
| 作者自查或 Agent 投票等于独立验证 | 共享误解与锚定仍在 | 区分角色独立、证据来源与实际运行 |
| 自动简化后直接交付 | 修改使原验证和 Review 覆盖失效 | 看最终 diff，重跑受影响验证 |
| 为局部小修固定六份文档和全员审查 | 流程成本压过收益，鼓励形式化填表 | 风险裁剪；阶段是决策，不是六个文件 |
| 所有 Review 意见沉淀为规则 | 误报、偏好与过时假设永久累积 | U8，核验、合并、注明例外并淘汰 |
| 使用远端模型却承诺代码全不出本机 | 混淆运行位置与数据处理通道 | 先确认获准材料和服务/部署边界 |
| 会话恢复后重放非幂等操作 | 操作可能已经发生，记录却未完成 | 先确认外部状态，不从缺日志推出未执行 |

## 11. 能力边界与有效性评估

### 11.1 协议不能保证什么

- 不能保证需求正确、项目契约完备，或 Agent 真正理解了所有隐含事实。
- 不能保证首次实现无缺陷，不能保证没有竞态、安全漏洞、性能问题或未来维护困难。
- 不能通过有限测试证明全行为等价；也不替代高保证领域需要的形式化、专业安全/合规审查与认证。
- 不能仅凭静态阅读证明设备性能、平台兼容、真实生命周期或分布式外部系统行为。
- 不能提供天然权限隔离、离线保密、自动回滚或 exactly-once；自然语言规则不是执行器和沙箱。
- 不能替有权人员选择业务目标、接受关键风险、授权外发或批准发布。
- 不能从一两个示例推断跨语言、跨项目的收益，更不能将 AI 审查同意当真实维护效果。

最危险的失败不是公开承认未知，而是把“流程走完”当成“质量已经证明”。

### 11.2 如何检验是否真的改善首次质量

这是建议的后续评估，不是本轮已运行实验；不需要新平台。

1. 在授权项目选有代表性的 L/M/H 任务，提前确认验收、任务边界和成本预算，保留无法执行、失败与“不改”的任务。
2. 记录**首个完整实现快照**：按预定范围实现完、尚未接受独立审查修复的版本。P3 期间的切片测试/改正要如实计入，不把多轮返工重新命名为首次。
3. 对照同类任务的既有做法与采用协议后的结果；尽量保持上下文、模型、工具与预算可比，不把同时换模型或加审查角色的效果全部归于协议。
4. 观察：首个快照的契约违背、关键遗漏、无关改动、需返工的设计、必要验证是否真实执行，以及总完成时间/费用和人工返工。统计口径事先确定，不用意见数量、代码长度或模式数量代替。
5. 用预先定义的测试/反例和维护者阅读或修改任务判断；条件允许隐藏版本来源，减少偏好。小样本只支持局部采用判断。
6. 若收益不明显、文档负担增加或仍反复漏同类约束，先简化/修订协议与项目契约；不默认添加更多 Agent、Skill 或 Hook。

即使结果改善，也只能在任务和环境边界内表述。当前协议是依据前两轮材料提出的工程设计，不是已获得经验有效性认证的标准。

## 12. 实际使用示例

下列为行动推演，没有执行项目代码或测试。

### 12.1 L：纯规则边界修复

请求：“修复折扣计算在数量为 0 时错误扣费；不改变公开 API。”

- **P1/P2 合并：** 读计算函数、调用方和测试；确认 0 的业务语义，列必须保持的价格/舍入规则。若这些已明确，无需再问能否开始。
- **P3：** 增加区分旧新行为的断言；条件允许先运行见目标失败，再最小修复。不创建定价策略工厂。
- **P4：** 运行目标测试、相关边界/回归和适用编译。只有实际通过才能报告通过。
- **P5/P6：** 无公共协议与新副作用，可不启用独立审查；说明依据。没有可复用的新教训就不改长期规则。

三句简报和一份真实检查结果即可，不要求六份阶段报告。

### 12.2 M：新增一个外部查询适配

请求：“支持按订单号读取配送状态；遵循现有集成方式。”

- 先读已有外部适配、调用者、鉴权与错误/超时契约；不要凭接口名字假定重试安全或响应字段稳定。
- 确认此操作无写副作用、无新增权限或敏感数据要求后可按 M；若涉及授权扩大或敏感信息则升级。
- F01 为“按订单号查询状态”，成功、找不到、超时、非法响应和取消属于其验收场景，不先按客户端/接口/测试文件拆成半成品。
- 方法方案列现有查询入口与错误处理的复用位置，拟新增 `QueryStatusAsync(orderId, cancellation) → DeliveryResult` 作为本教学例的适配边界；说明输入校验由谁负责、如何映射结果/错误、超时和取消的真实契约、是否改变调用方。此签名是教学拟案，不冒充项目已存在 API，也不为每个分支另造函数。
- 依据引用实际找到的适配与错误契约；理由是保持现有调用/错误模型并只补外部字段映射；待验证项对应上述验收场景。**人工整体审核后再实现**，不因已判 M 就自行跳过审核。
- 契约测试验证实际边界；纯 mock 通过不当作供应商契约已核实。定向审查错误分类、数据泄漏和调用方行为，不重做整个集成层。
- 外部环境不可访问时交付“实现完成、集成待验证”，列提测缺口，不写“功能已上线可用”；即使开发联调完成，也不替 QA 宣布通过。

### 12.3 H：存档结构迁移

请求：“合并存档字段并清理旧代码。”

- 先确定旧格式、版本判别、原子写入、备份/恢复和不支持数据的处理；缺这些信息不直接删除旧路径。
- 展示迁移方案与恢复边界，取得破坏兼容或数据处理的相应批准；“清理”不自动授权不可逆迁移。
- 用代表性旧数据、损坏数据、重复迁移、写失败/中断和恢复路径验证；独立审查迁移与数据完整性。
- 核心验证缺失则阻塞发布建议。即使可以回滚程序，也不能假定新格式数据可随之回滚。

这一流程不依赖 Unity，适用于服务、桌面应用和其他持久化系统。

### 12.4 性能改进：先决定是否值得改

请求：“把这段 LINQ 全部改成循环，减少 GC。”

先确认这是硬约束还是未经测量的优化假设。查具体调用、输入、频率和目标环境；无热点/预算证据时先建议保持现状或测量，不先全量改写。若确定热点，比较等价候选、实际测量并记录维护代价。没有稳定收益就允许不采用候选；这不是任务失败，而是有效工程结论。
