# Unity 场景退出后，谁拒绝旧 Task 结果并释放资源？

> **研究边界**
> 本文是源码支持的机制分析与设计提案，不是已运行验证的 Unity 方案。目标 Unity 6000.0.85f2 / System.Threading.Tasks.Task / MonoBehaviour 主线程入口。已读固定 C# reference；Unity/.NET 官方网页正文访问受阻，未完成独立契约交叉核验，未安装运行目标 Editor。Task 上下文捕获、取消协议与原生销毁时序仍有证据缺口。所有来源 ID、定位和访问状态见 [共用来源](sources.md)。

## 结论：责任应在协议中，不应从“场景已退出”推出来

对于场景局部的异步结果，建议由**业务 owner 决定结果现在是否仍有提交资格**；由**调用方与 producer 的交接协议决定每一个结果由谁释放**。取消用于请求减少不再需要的工作，但不能在缺少底层契约时，被当成“已停止、不会返回资源、无需清理”的证明。

这是一项有条件的设计判断，而不是 Unity 官方替你完成的通用机制：已读取消入口只看到 CTS.Cancel，主线程队列只处理 callback/state，卸载绑定将工作交给原生实现，没有在这些已读范围中出现任意用户 Task 的 owner/结果释放协议（ER-20261105-unity-task-01、02、04）。**“没有在这里看到”不等于完整引擎或某个第三方 API 一定不提供这些能力。**采用前必须核对具体 producer 的成功、取消、异常与资源交接契约。

## 三个问题不能合并成一个 await

设一个界面请求加载场景相关数据：

1. 请求 A 启动，携带当时的 owner 与请求代次。
2. 用户离开界面，或同一对象发起请求 B。
3. A 产生结果，等待接收或提交。
4. 接收路径恢复执行。

这里至少存在三种不同判断：

| 判断 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 执行位置 | 当前线程能否调用目标 Unity API？ | 不能证明 A 仍是当前请求 |
| 提交资格 | owner 尚接受结果，且 A 没被替代吗？ | 不能证明没人需要释放 A 的结果 |
| 资源归属 | 资源此刻归 producer、接收路径还是 owner？ | 不能证明 owner 仍存活 |

即使对象没有被销毁，请求 B 也能令 A 失效。这是仅判 Unity 对象不为空的反例，不依赖“退出场景后必然某个帧回调”的时序假设。即使 A 已经失效，它的结果也可能仍需要清理；“不提交”与“不负责”不是同义词。

## 源码建立了哪些边界

### 取消入口是一个信号入口

ER-20261105-unity-task-01 的 getter 在对象失效时有异常分支，token source 懒创建，RaiseCancellation 调用 Cancel。这支持：需要此 token 的路径应在对象仍有效时取得它，不要等迟到回调才首次访问失效 MonoBehaviour 的 getter。

它不展示原生何时调用 RaiseCancellation，也不展示任意 producer 如何处理 token。因此本文不指定它与 OnDestroy 的精确先后，不宣称它覆盖业务“开始退出”到原生销毁之间的所有窗口。若业务在切换动作开始时就不再接受结果，应由业务退出入口立即撤销提交资格，不能等未核验的销毁信号时点。

### 同步上下文是调度机制，不是场景 owner

ER-20261105-unity-task-02 显示：Post 将 callback/state 加入队列；Exec 取出并调用；初始化设置 UnitySynchronizationContext；WorkRequest 保存 callback、state、wait handle，而没有业务 owner 字段。

可得的综合推论是：**即便某 continuation 已投递到此主线程队列，仍需另行判断业务有效性。**不能反向推成所有 Task await 必经此队列。是否捕获上下文、同步完成、后台入口、ConfigureAwait(false) 与实际运行时语义，必须另查契约和目标环境。本文不以未读官方网页填补这些条件（05、10 未核验）。

内部 ExecutePendingTasks 存在超时循环，不代表应用退出时任意任务都能被无限等待或必然清理。本文不提供进程终止/强杀后的 finally 保证。

### Unity 对象有效性不等于请求身份

ER-20261105-unity-task-03 的 CompareBaseObjects 会区分托管引用与原生对象存活，不能用 CLR 引用还在就证明 Unity 对象可用。但反过来，Unity 对象仍有效也不能证明它仍展示请求 A：对象池复用、重复打开、同一界面切换目标都能改变业务身份。

因此，适用时要检查一个由 owner 管理的请求代次或唯一请求标识。对于“关闭后重新打开但复用同一实例”的情形，单一 alive 布尔值不足以区别两次会话。标识应在发新请求、退出或复用时更新；唯一性范围和溢出策略由具体工程确定，不把一个裸 int 宣称成无限期身份保证。

### 场景卸载在这里跨过原生边界

ER-20261105-unity-task-04 展示包装与 extern 绑定，不展示完整原生卸载过程。Object.Destroy 也是原生绑定（03）。本轮不能据此确认卸载的所有销毁时点、资源类型的释放方式或任意 Task 的取消行为。

这影响建议的措辞：不是“场景卸载永远不会释放资源”，而是“**不能只凭已读绑定假定场景卸载已替你的异步结果履行具体资源 API 的释放责任**”。持久化 owner、共享缓存和引用计数句柄都需要各自契约，不能混用 IDisposable、Object.Destroy、Release 作为同义词。

## 一个可审查的交接协议

下面是本研究提出的协议模型，不是源码事实。适用前提是：一个结果拥有单一释放责任；接收、资格检查和提交在 owner 规定的同一线程串行执行；检查到接管之间无 await、无可重入回调；释放 API 的线程与异常契约已明确。

- producer 返回前：producer 负责取消/异常时其内部已分配但未交出的资源。调用方看不到的资源，调用方无法补救。
- 成功返回后、接管前：接收路径临时持有结果。不管取消、过期或提交前异常，都必须走释放路径。
- 接管成功后：owner 负责最终释放。接收路径清空临时引用，避免 finally 二次释放。
- 接管失败：协议必须明确保持原归属；不能出现“已经存到 owner 后又抛异常，调用方却以为没接管”。

资格检查至少包含业务有效期与请求身份；token 状态只能是其中一个输入。退出先撤销资格/更新身份，再请求取消，以免取消回调重入时旧请求仍被视为有效。具体 Cancel 回调异常、嵌套调用与线程切换不在这个简化模型内，生产实现必须另行设计。

若 producer 不返回但一直占用资源，下面的 finally 也不能凭空运行；需要上层服务管理超时、未完成工作与生命周期。若 producer 在消费者提前返回后才完成，则必须另有路径接收并清理迟到结果。不要把“停止等待”实现成“无人负责后续结果”。

### 接收算法（C# 形态的示意，未编译/未运行）

```csharp
// 外部契约均需实现与验证；这不是可直接粘贴的 Unity 脚本。
async Task ReceiveAsync(RequestId id, CancellationToken token)
{
    OwnedResult pending = null;
    try
    {
        pending = await ProduceAsync(token);
        // 前提：此处已处于 owner 线程，ProduceAsync 成功返回非 null。
        if (token.IsCancellationRequested || !IsCurrent(id))
            return;

        AdoptWithoutCallbacks(pending);
        // 契约：Adopt 成功才转移责任；若抛异常则不得已接管。
        pending = null;
    }
    finally
    {
        pending?.Dispose();
    }
}
```

`RequestId`、`OwnedResult`、producer、IsCurrent、Adopt 均是待实现的项目契约，不是 Unity API。这里不吸收取消异常，取消与其他异常继续传播，由调用方观察 Task 并按具体 producer 契约归因；只检查本 token 已取消并不能证明异常来自该 token。Dispose 假定在当前线程合法且不会掩盖原异常；若不成立，需专用清理和异常合并方案。

这段算法**不负责**证明 await 后线程、实现业务退出入口、清理 owner 已接管的结果或保证运行时一定执行 finally。它展示的是责任转移点。不能删掉这些前提后称“通用安全模板”。

## 方案比较与选择依据

| 方案 | 成本/优势 | 漏洞与适用边界 | 本题判断 |
|---|---|---|---|
| await 后只判对象有效 | 简单；可拒绝某些已销毁对象访问 | 对象仍活而请求已替代时无效；未说明资源释放 | 仅适合作为一项 guard，不是完整协议 |
| 只传 destroy token | 能表达 owner 销毁相关的停止意愿；接入成本较低 | 原生触发时点和 producer 响应仍需核验；同实例新请求未必销毁；没规定结果交接 | 不能独立作为完成证明 |
| 业务有效期/请求身份 + 取消 + 明确交接 | 同时回答结果资格与释放责任；能讨论迟到成功路径 | 引入身份与状态管理；要求线程、重入和资源契约；可能重复底层库保障 | 本研究有条件推荐，需补证和运行验证 |
| 将工作交给跨场景服务 | 长任务不必随界面消失；统一管理结果/缓存 | 服务仍要处理订阅失效、资源预算和消费者交接；不是“永久 owner”即可免清理 | 当工作本身跨场景有价值时更合适 |

如果目标 API 已提供完整的结构化 owner、取消和释放契约，应直接复用，减少额外状态。若结果是纯托管不可变值而无独立释放责任，可以简化资源交接部分，但仍不能省略是否允许回写的判断。若结果是共享/引用计数资源，本模型的独占 Dispose 必须换成对应的引用获取/归还协议。

## 失败路径与后续验证设计（本轮未执行）

| 条件 | 应保持的不变量 | 可能推翻/修订设计的观察 |
|---|---|---|
| 正常成功且当前请求有效 | 只接管一次，最终只释放一次 | 接管失败后 owner 和 finally 同时释放 |
| 退出后迟到成功 | 不提交；接收者清理未接管结果 | 没有 continuation 接收结果或释放线程非法 |
| 同一对象 A/B 请求倒序完成 | A 不覆盖 B | alive/token 都正常但 A 仍通过资格检查 |
| producer 内部取消/异常 | producer 清理未交出资源；异常可观察 | 内部分配资源从未交出却无人释放 |
| 检查后发生重入 | 不出现资格检查与提交断裂 | Adopt 回调触发退出后仍提交，需修改交接设计 |
| owner 已接管后退出 | owner 清理已接管结果 | 调用方与 owner 责任重叠或皆未释放 |

后续由用户决定是否在独立最小 Unity 工程执行。应记录 Editor 补丁、runtime/backend、平台、线程 ID、请求 ID、业务失效时点、token 状态、结果交出/接管/释放事件与异常；逐条复现实例，保留原始日志。计数和顺序才是证据，不用一次“没报错”代替所有权验证。本轮没有这些日志、计数或运行结论。

## 当前能决定什么，不能决定什么

可据现有分析决定：审查异步代码时分别追问线程、提交资格、资源归属；不因写了取消或 await 就默认生命周期问题已解决。可据固定源码决定：提前取得需要的 destroy token，不把主线程队列当业务 owner。

还不能决定：目标工程中哪套 API 的精确退出顺序、实际 Task continuation 的线程保证、某资源的具体释放方法、性能收益以及该示意代码可直接上线。补充官方契约后应同步复查本文与 Blog；完成运行验证前维持 draft-with-evidence-gaps。下一步是人工审核与补证决策，不自动发布。
