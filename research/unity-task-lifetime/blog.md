# await 回来了，但这个结果还属于当前界面吗？

你打开角色预览界面，开始加载 A 的数据。等待时又选中了 B，B 的结果先回来，界面显示正确。过一会儿，A 才完成，把界面改回了 A。

这里不需要对象销毁，也不需要线程报错。界面活着，代码也可能就在主线程执行；错的是**旧请求仍被允许提交**。

现在再加一步：加载结果持有一个需要释放的资源。如果你发现 A 过期后直接 return，界面可能不再错，但资源是否有人归还？修好回写，不等于修好所有权。

> **先说明这篇文章的证据边界**
> 这是设计教学草稿，不是已实测教程。分析目标为 Unity 6000.0.85f2、System.Threading.Tasks.Task、MonoBehaviour 主线程入口。已读对应固定 C# reference；Unity/.NET 官方文档正文访问受阻，Task 调度/取消和原生销毁的契约仍需补证；没有编译示例、运行 Editor 或测量性能。共用 [来源登记](sources.md)，完整分析见 [研究报告](report.md)。

## 把异步结果当成一件需要签收的包裹

先用一个不完整、但便于思考的类比：

- **投递地点**：包裹送到正确窗口，类似代码在允许的线程执行。
- **收件资格**：这个窗口现在还要这批货吗？类似当前请求身份和业务有效期。
- **保管责任**：没有签收或拒收时，谁把包裹退回？类似资源释放。

地点正确，不代表订单仍有效；订单作废，也不代表包裹能凭空消失。

这个类比只解释责任分工，不代表真实异步 API 自动提供拒收/退货机制。代码里必须有人实现它。

## 第一层：主线程只回答“在哪里执行”

固定版本 UnitySynchronizationContext 源码能看到 Post 入队，Exec 取出 callback 执行，初始化设置同步上下文（ER-20261105-unity-task-02）。队列条目里没有你的“角色 A 请求还有效吗”这一业务判断。

所以，**即便某段接收代码通过这个上下文在主线程执行，它仍可能处理过期结果。**

注意“即便”两个字。本文没有证据把所有 Task await 的恢复路径都保证为主线程；后台入口、上下文捕获与 ConfigureAwait(false) 需要另查契约并在目标环境核对。不要把 await 当作切回主线程指令，也不要把它当成 owner 存活证明。

## 第二层：对象还在，不代表这次请求还有效

Unity Object 的有效性判断并非仅看托管引用（ER-20261105-unity-task-03）。但即使你正确判断了 Unity 对象是否有效，也没解决开头的 A/B 问题：同一个界面对象可以接连承载不同请求。

一个常见的设计是由界面 owner 管理“当前请求标识”：

1. 发起 A 时，记住 A 的标识。
2. 发起 B 或退出界面时，更新当前标识并撤销旧提交资格。
3. A 回来时，对照它带回的标识。
4. 不匹配就不接管结果，但仍履行未接管结果的清理责任。

这叫**结果失效**：不是声称后台工作已停止，而是明确它的结果不再有权改变当前状态。关闭后重开同一对象也应产生新身份；一个先 false 后 true 的 alive 标记未必能识别旧会话。

## 第三层：取消、拒收和释放是三件事

你可能会问：传 destroyCancellationToken 不就好了吗？

固定源码能确认 getter 懒创建 token source，失效对象首次访问有异常路径，RaiseCancellation 调用 Cancel（ER-20261105-unity-task-01）。因此，若需要这个 token，应在对象仍有效时取得，不能等旧回调来了才去失效对象上取。

但这段源码没有说明你的 producer 如何处理取消，也没有展示所有资源的释放协议。**在没有具体契约时，不能从“请求取消”跳到“保证不再产生结果，所以我不用清理”。**同一界面请求 B 替代 A，也未必发生对象销毁。

为了看清区别，可以假设一个 producer 没有及时停止，最后仍成功返回结果。这个假设是协议要覆盖的失败场景，不是本轮观察到的 Unity 行为：

- 取消信号用于请求停止。
- 资格检查决定还收不收。
- 交接协议决定不收时谁释放，收下后又由谁释放。

如果业务在“开始退出”那一刻就不再接受结果，应在业务退出入口先使旧请求失效，再请求取消；不要依赖本轮尚未核验的原生销毁信号时序。

## 把交接点写出来，才能看见遗漏

下面不是完整 Unity 脚本，而是**未编译、未运行的 C# 形态示意**。外部类型和函数都是项目需自行实现的契约，不是 Unity API。

```csharp
async Task ReceiveAsync(RequestId id, CancellationToken token)
{
    OwnedResult pending = null;
    try
    {
        pending = await ProduceAsync(token);
        // 前提：这里已经在 owner 线程；成功结果非 null。
        if (token.IsCancellationRequested || !IsCurrent(id))
            return;

        AdoptWithoutCallbacks(pending);
        pending = null; // 接管成功，释放责任才转给 owner。
    }
    finally
    {
        pending?.Dispose(); // 未接管的结果仍由接收路径负责。
    }
}
```

读这段代码时，先别盯着 API，按三个路径走一遍：

- **A 迟到**：资格不匹配，return 仍经过 finally，未接管结果被清理。
- **A 有效**：owner 接管成功，临时引用清空，finally 不再释放它；owner 以后负责释放。
- **接管前异常**：临时结果还在，走 finally；异常向上传播，由调用方观察和处理。

这只是设计推演，不是测试结果。真实使用前至少补齐这些约束：

- await 后在哪个线程不能靠注释保证；必须核对契约与目标环境。示意没有实现线程切换。
- 检查到接管之间不能 await 或调用会重入退出逻辑的回调。
- Adopt 必须是成功才转移责任；不能已经存进 owner 后再抛异常，让 finally 又释放一次。
- Dispose 必须符合具体资源的线程和异常规则。Object.Destroy、Release、Dispose 不是可互换名称。
- producer 未交出的内部资源由 producer 清理；若它永远不返回，这段 finally 并不能替它清理。
- 调用方必须观察 Task 的异常。这里没有吸收取消异常，取消也会向上传播；不要把它变成无人观察的 fire-and-forget。

如果你为了“快速取消”让接收路径提前不再等待，还必须安排谁接收以后完成的结果。否则包裹仍在路上，窗口却撤了。

## 什么时候不该照搬这套结构

如果结果只是没有独立清理责任的不可变托管值，资源交接可以简化，但旧请求回写仍可能出错。

如果工作本来就应跨场景继续，例如可复用的数据缓存，更合理的 owner 可能是长期服务；界面只是订阅者。界面退出后撤销订阅资格，服务继续管理任务和资源。这也不表示永久持有所有结果，应有缓存和释放策略。

如果 API 已经提供完整的 owner/取消/释放契约，优先读清并复用，不要再叠加一套相互冲突的状态。共享或引用计数资源也不能套“唯一 owner 调 Dispose”的模型。

本轮读到的场景卸载文件主要是包装与原生绑定（ER-20261105-unity-task-04），不能据此承诺“卸载后资源必然全清”，也不能反向断言“卸载永远不清资源”。需要回到具体资源 API。

## 回到开头，你会问哪三个问题？

下次看到一个 await 后更新界面的函数，先问：

1. **执行位置**：这行 Unity API 调用的线程依据是什么？
2. **提交资格**：对象仍活之外，这是不是当前那次请求？
3. **释放责任**：取消、迟到、异常、接管成功，各是谁负责？

可以用 A/B 倒序完成、退出后迟到、接管前异常三个场景手动推演。推演发现的漏洞应进入后续测试，但推演本身不算测试通过。

这篇文章想教的不是多加一个 token 或一个 if，而是：**调度有调度的契约，业务有效期有业务的契约，资源交接有交接的契约。写清三个契约，比看到 await 就放心更可靠。**当前仍需补官方正文、独立 Unity 验证与人工审核，不能直接当生产教程发布。
