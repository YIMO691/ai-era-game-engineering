# Unity异步任务生命周期：精编版

> **状态（一次说明，正文不再重复）**：本精编版整理自[Unity异步任务生命周期](../unity-task-lifetime/README.md)专题（原稿2026-11-05，draft-with-evidence-gaps，人工pending）。分析对象是Unity 6000.0.85f2的固定C# reference源码；Unity与.NET官方网页正文访问失败；Task调度与取消、原生销毁时序仍有证据缺口；示意代码未编译、未运行；没有Editor、设备或读者实验数据。本精编版继承这些状态。观点标签含义见[精编版目录](README.md)。

## 一句话

**场景局部的异步结果，应当由业务owner决定它现在是否仍有资格提交，由调用方与生产者之间的交接协议决定每个结果由谁释放；取消只是请求减少工作，不能被当成“已停止、不会返回资源、无需清理”的证明。**

## 核心问题

用户离开界面、或同一界面发起了新请求之后，旧的异步请求才返回。**谁来拒绝这个旧结果？如果它持有需要释放的资源，谁来释放？**

这是本仓库路线图的首个候选研究问题。

## 观点体系

### 观点一：一个await背后有三个独立的问题 〔源码＋逻辑〕

| 判断 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 执行位置 | 当前线程能否调用目标Unity API？ | 不能证明这仍是当前请求 |
| 提交资格 | owner还接受这个结果吗？它没有被替代吗？ | 不能证明没人需要释放这个结果 |
| 资源归属 | 资源此刻归生产者、接收路径还是owner？ | 不能证明owner仍存活 |

**关键反例**：对象没有被销毁，但同一对象发起的请求B已经使请求A失效。这个反例不依赖任何“退出场景后必然发生某个回调”的时序假设，所以“对象有效就可以写”不成立。

**关键原则**：即使A已经失效，它的结果也可能仍需要清理。**“不提交”与“不负责”不是同义词。**

*一个帮助记忆的类比*：异步结果像一件需要签收的包裹。投递地点（线程）对了，不代表订单仍有效（提交资格）；订单作废了，也不代表包裹能凭空消失（资源归属）。这个类比只解释责任分工，不代表真实API自动提供拒收或退货机制。

### 观点二：固定源码建立了四条边界 〔源码，静态，未运行〕

1. **取消入口只是一个信号入口。** MonoBehaviour的销毁取消token是懒创建的，对象失效时访问有异常分支，触发时调用Cancel。可推出：需要这个token的路径应在对象仍有效时取得它。源码没有展示原生何时触发取消，也没有展示任意生产者如何响应取消。
2. **同步上下文是调度机制，不是业务owner。** 主线程队列的工作项只保存回调、状态和等待句柄，没有业务owner字段。可推出：即使某个continuation已经投递到主线程，仍需另行判断业务有效性。但不能反过来推出“所有await都一定回到主线程”。
3. **Unity对象有效性不等于请求身份。** 对象比较会区分托管引用与原生对象是否存活；但对象池复用、重复打开、同一界面切换目标都会改变业务身份，而对象依然有效。
4. **场景卸载跨过了原生边界。** 静态阅读只看到包装与原生绑定，看不到完整的卸载过程。因此不能凭此假定场景卸载已经替你的异步结果完成了具体资源的释放；也不能反过来断言“卸载永远不释放”。

“没有在这里看到”不等于完整引擎或第三方API一定不提供这些能力，采用前要核对具体生产者的契约。

### 观点三：提交资格应由业务owner管理的请求身份判断 〔推论〕

- 由owner管理一个请求代次或唯一标识。发起新请求、退出界面、归还对象池、同一实例重开时更新它。
- 单一的alive布尔值区分不了“关闭后重新打开同一实例”的两次会话。
- 标识的唯一性范围与溢出策略由具体工程确定，不能把一个裸int宣称为无限期身份保证。
- 如果业务在“开始退出”的那一刻就不再接受结果，应在业务退出入口立即撤销资格，不等未经核验的销毁信号。
- **先撤销资格，再请求取消**：取消回调可能重入，若此时旧请求仍被视为有效，就可能被提交。

### 观点四：资源交接协议 〔本研究提出的设计，非源码事实〕

适用前提：一个结果有单一的释放责任；接收、资格检查与提交在owner规定的同一线程串行执行；检查与接管之间没有await、没有可重入回调；释放API的线程与异常契约已明确。

| 阶段 | 责任方 |
|---|---|
| 生产者返回前 | 生产者负责其内部已分配、尚未交出的资源（调用方看不到的，调用方无法补救） |
| 成功返回后、接管前 | 接收路径临时持有；不论取消、过期还是提交前异常，都走释放路径 |
| 接管成功后 | owner负责最终释放；接收路径清空临时引用，避免重复释放 |
| 接管失败 | 保持原归属；不能出现“已存进owner又抛异常，调用方以为没接管” |

两条容易被忽略的延伸：

- 生产者永远不返回时，接收路径的finally也不会运行；需要上层服务管理超时与生命周期。
- 调用方提前停止等待时，必须另有路径接收并清理迟到的结果。**不要把“停止等待”实现成“无人负责后续结果”。**

接收算法的示意代码见原文。它展示的是责任转移点，不是可直接粘贴的Unity脚本；它不负责证明await后的线程、实现业务退出入口或保证运行时一定执行finally。

### 观点五：四种方案的取舍 〔推论〕

| 方案 | 优势 | 漏洞 | 判断 |
|---|---|---|---|
| await后只判对象有效 | 简单，能拒绝某些已销毁对象的访问 | 对象仍活而请求已被替代时无效；没说明资源释放 | 只能作为一项检查，不是完整协议 |
| 只传销毁token | 能表达owner销毁时的停止意愿 | 触发时机和生产者响应需核验；同实例新请求未必销毁；没规定交接 | 不能独立作为完成证明 |
| 请求身份＋取消＋明确交接 | 同时回答提交资格与释放责任，能处理迟到成功 | 引入身份与状态管理；要求线程、重入与资源契约 | 有条件推荐，需补证和运行验证 |
| 交给跨场景服务 | 长任务不随界面消失；统一管理结果与缓存 | 服务仍要处理订阅失效、资源预算与消费者交接 | 当工作本身跨场景有价值时更合适 |

**何时不要照搬**：结果是无独立释放责任的不可变托管值时，可以简化交接，但仍要判断是否允许回写；目标API已提供完整的owner、取消与释放契约时，直接复用；共享或引用计数资源要换成对应的获取/归还协议；`IDisposable`、`Object.Destroy`、`Release`不是同义词。

### 观点六：验证要看计数和顺序，不看“没报错” 〔验证设计，未执行〕

| 条件 | 应保持的不变量 | 会推翻设计的观察 |
|---|---|---|
| 正常成功且当前请求有效 | 只接管一次，最终只释放一次 | 接管失败后owner和finally同时释放 |
| 退出后迟到成功 | 不提交；接收者清理未接管结果 | 没有continuation接收结果，或释放线程非法 |
| 同一对象A/B请求倒序完成 | A不覆盖B | alive和token都正常但A仍通过资格检查 |
| 生产者内部取消或异常 | 生产者清理未交出资源；异常可观察 | 内部资源从未交出却无人释放 |
| 检查后发生重入 | 资格检查与提交不断裂 | 接管回调触发退出后仍提交 |
| owner已接管后退出 | owner清理已接管结果 | 调用方与owner责任重叠或都未释放 |

建议在独立的最小Unity工程中执行，记录Editor补丁、运行时与后端、平台、线程ID、请求ID、业务失效时点、token状态，以及结果交出、接管、释放事件与异常，保留原始日志。

## 现在能决定什么，不能决定什么

**能决定**：审查异步代码时分别追问线程、提交资格、资源归属；不因为写了取消或await就认为生命周期问题已解决；提前取得需要的销毁token；不把主线程队列当业务owner。

**还不能决定**：目标工程中某套API的精确退出顺序、Task continuation的实际线程保证、某资源的具体释放方法、性能影响，以及示意代码能否直接上线。

## 下次看到“await后更新界面”时问的三个问题

1. **执行位置**：这行Unity API调用的线程依据是什么？
2. **提交资格**：对象仍活之外，这是不是当前那次请求？
3. **资源归属**：如果不收这个结果，谁来释放它？收下后又归谁？
