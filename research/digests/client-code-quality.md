# 游戏客户端代码质量：精编版

> **状态（一次说明，正文不再重复）**：本精编版整理自[客户端代码质量](../client-code-quality/README.md)专题（原稿2026-11-05，awaiting_review，人工pending）。专题的证据来自官方C#规范与分析器原稿、固定版本的.NET Queue/Select源码、Unity Graphics RTHandle和MonoGame集合事件实现；四本指定经典均未完整阅读；所有示例未编译、未运行，没有Unity、Profiler或读者实验数据。本精编版继承这些状态。观点标签含义见[精编版目录](README.md)。

## 一句话

**优秀的客户端代码不是最短、模式最多或风格最整齐的代码，而是让必要的行为、状态、依赖与约束能被可靠理解，并在项目环境中可验证、可修改的代码。**

## 核心问题

“功能正确”之后，代码还有什么好坏之分？如何把“这段代码不好”从个人品味变成可以讨论、可以检验的工程判断？在Unity/C#中，哪些地方最容易把“漂亮”误当“安全”？

## 观点体系

### 观点一：判断质量的单位是具体的阅读或修改任务 〔工作定义〕

更可执行的问法是：**给一个具体的阅读或修改任务，维护者需要知道什么、到哪里找、容易漏什么、改完如何确认没有破坏约束？** 如果改名、拆函数、抽接口不能改善这些任务，或者引入了更多接线和隐藏协议，就不能只凭“更干净”认定它更好。

本专题明确：这是工作定义，不是被证明的“理解成本最低”定律，也不存在客观的优雅分数。

### 观点二：功能正确却难读，是因为四类缺口 〔分析分类〕

“输出对了”只说明已观察条件下的行为。维护者面对的是尚未执行的条件和未来变化：

| 缺口 | 表现 |
|---|---|
| 语义缺口 | Process、Get、flag等名称没有说明行为、单位或失败条件 |
| 位置缺口 | 一条简单主流程要跨多文件寻找；只转发的抽象没有省下知识 |
| 时间缺口 | 状态何时改变、何时通知、旧请求何时失效、资源何时交接没有契约 |
| 验证缺口 | 无法构造反例、定位日志、隔离依赖或运行必要检查，只能相信作者 |

改善这些缺口有时需要更长的名字、显式状态或更多失败分支，有时需要删除多余抽象。所以字数与质量没有单调关系。

*源码例证*：MonoGame的集合在插入和单项删除时先改集合再通知，Clear却先逐项通知再清空；每个方法都很短，系统时序却不能从名字推断。这支持“局部简洁不足以证明系统协议清楚”，不等于发现了已复现的上游缺陷。〔源码，静态〕

### 观点三：五个层次，不把“漂亮函数”外推成“好系统” 〔分析框架〕

| 层次 | 核心问题 | 不能据此推出 |
|---|---|---|
| 局部表达 | 名称与行为一致吗？给定输入走哪条路径？ | 模块边界合理 |
| 模块设计 | 谁拥有状态？公开API能否绕过检查？ | 跨系统协作没有时序漏洞 |
| 系统协作 | 提交与通知何时发生？失败与生命周期协议是什么？ | 目标设备性能达标 |
| 工程维护 | 能复现、测试、诊断和回退吗？ | 未覆盖的行为也正确 |
| 项目适配 | 符合编译链、序列化、API兼容、团队风格与设备预算吗？ | 某团队经验就是行业标准 |

一个漂亮的UI方法若依赖全局状态和不明的销毁顺序，局部表达合格，系统协作仍有缺口。一个较长的引擎适配函数若清楚隔离了必要的状态机，可能比到处拆分更合适。应逐层解释，而不是给一个总分掩盖短板。

### 观点四：名称要让读者能做出可核对的预测 〔源码＋推论〕

名称应当回答：读取还是消费，借用还是接管，异步还是立即完成，值的单位是什么。.NET Queue的`Peek`与`Dequeue`区分了保留与移除，`TryDequeue`与`Dequeue`用不同的失败契约服务不同调用方。〔源码，静态〕

- 方法用动词表达动作；副作用不能藏在看似查询的名字后面。
- 布尔值表达明确命题，例如`isRequestPending`。
- 多个布尔参数可以先用命名参数或枚举，不必直接建设Options体系。
- `Async`后缀不证明线程或生命周期正确；Unity回调和既有API不应机械改名。
- 重命名公开API、序列化字段或反射目标不是纯风格改动。

### 观点五：函数提取的价值是形成可信的知识边界 〔推论〕

提取后的名字是否描述一个稳定概念？调用者是否因此无需理解实现？被隐藏的是细节，还是必须知道的资源与时序责任？

- 保留主要步骤的同层表达（校验→提交→接受结果→更新状态→通知），不把每个赋值拆成`StepN`。
- 只调用一次不代表不能提取；重复出现也不代表是同一职责。
- 多阶段状态应考虑显式状态机；十个相互影响的布尔值即使名字都好，组合也可能失控。
- 只在能兑现的边界处理异常，不为“主流程干净”吞掉失败。

### 观点六：抽象是否有效，看它是否真正承担了它承诺的责任 〔推论〕

**抽象之前的四问**：现在必须隐藏的知识或不变量是什么？哪个真实变化会因此被局部化？调用者省下了什么，又多了多少跳转、配置和调试路径？不抽象、少量重复或普通函数能否以更低成本满足需求？

| 工具 | 值得考虑的条件 | 主要代价 |
|---|---|---|
| 接口 | 限制依赖能力、隔离外部边界、真实替换 | 每类一个同名接口只增加导航 |
| 泛型 | 同一算法或不变量确实跨类型共享 | 约束、错误信息、代码大小更复杂 |
| 事件 | 多方通知且订阅、顺序、错误契约明确 | 隐式调用图、长寿命引用、重入 |
| 策略、工厂 | 稳定的变化轴，创建规则值得集中 | 尚无变化就预建扩展点 |

*反例*：两个相似的金额比较，合法零值和变化原因不同，合并成带模式参数的通用`Check`反而更难懂；但同一价格协议已在多处同因漂移，继续复制也未必更简单。

### 观点七：Unity中最容易把“漂亮”误当“安全”的四个地方 〔源码＋推论〕

1. **生命周期与事件**：停用、销毁、关闭业务窗口、归还对象池、同一实例重开是不同的事件。先选owner和有效期，再决定订阅/退订入口与请求身份。
2. **异步与资源**：名字带Async、传了token、await后判空，都不足以证明旧请求不能改新状态。Graphics的RenderTexture分配入口默认借用，Release有条件地请求销毁，说明不能把所有资源清理压成一种Dispose模板。〔源码，静态，该包版本与目标Unity版本的兼容未验证〕
3. **超时**：要区分“调用方不再等待”“已请求生产者取消”“生产者已完成并清理”。超时提示可以先出现，后台工作却未必已停。
4. **序列化与历史约束**：重命名序列化字段、改变程序集或事件顺序，可能改变代码调用之外的行为，应把资产迁移与加载验证列入任务。

### 观点八：性能与可读性的冲突必须具体化 〔源码＋推论〕

.NET的`Select`实际存在按输入类型、空集合、优化开关的多种分支。〔源码，静态〕它支持“不能从一个语法名字推出统一成本”，既不支持“LINQ免费”，也不支持“所有LINQ都必定分配”。

顺序应是：定义预算与代表负载 → 定位热点 → 保持行为比较候选 → 目标设备测量 → 权衡收益与维护代价。CPU时间、GC.Alloc和保留内存回答的是不同问题。不在热点上的代码，保留清楚的基线可能更合理。

### 观点九：区分可验证的事实、有证据的讨论、合理的假设和审美偏好 〔分类框架〕

| 类别 | 示例 | 怎么表达 |
|---|---|---|
| 可核对的事实或硬约束 | 事件在提交前还是后；资源释放调用次数 | 给版本、代码位置或运行结果 |
| 有证据的设计讨论 | 为理解副作用需跨七个转发层 | 给具体任务、候选、代价与反例 |
| 合理但未实证的假设 | 这个命名可能减少误读 | 说明机制，待真实修改检验 |
| 审美偏好 | var、成员顺序、表达式形式 | 标为可选，沿团队约定，不阻塞正确改动 |

审美不是无价值，一致和局部对称可能帮助阅读。但一旦把“更自然”变成强制要求，就应当指出真实任务收益或团队约定。

### 观点十：审查按A/B/C三档分开 〔实践工具〕

- **A 必须修复**：有实际失败条件或违反硬契约（正确性、生命周期、异步、资源、事件、数据完整性、安全、已确认的性能回归、高风险验证缺口）。证据不足但影响大时，先要求补证，不编造确定缺陷。
- **B 需要讨论**：设计与修改成本。必须给出替代方案与代价，“不够面向对象”不是理由。
- **C 可选风格**：不冒充硬性缺陷；已有约定的就交给自动化。

第一遍先沿一次真实请求追踪系统路径（入口→校验→读状态→外部依赖→提交→通知→失败与退出清理），再看拼写和格式。

## 日常方法（六步）

1. **写前**：几句话说明意图、状态owner、主流程、失败与项目约束。
2. **写时**：让名称、类型、顺序兑现这些说明；比较“不改”候选。
3. **自查**：沿正常、拒绝、异常、取消、重入、退出路径追一次数据与资源。
4. **审查**：先正确性与硬契约，再设计讨论，最后可选风格。
5. **修改后**：运行实际需要的测试与设备检查，记录未覆盖项。
6. **复盘**：用真实任务修正指南；只有反复出现且工具没有覆盖的缺口才固化成规则。
