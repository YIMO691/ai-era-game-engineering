# AI时代的工程质量：精编版

> **状态（一次说明，正文不再重复）**：本精编版合并整理[AI代码质量工作流](../ai-code-quality-workflow/README.md)与[AI-CQEP](../ai-cqep/README.md)两个专题。前者是对现有工具链的静态源码研究与采用设计（awaiting_review，人工pending，候选工具未安装、未运行）；后者是在前者基础上提出的工程协议草案0.2.0（课题阶段unknown，原稿自述awaiting_review）。两者都没有质量提升、首轮通过率或维护成本的实验数据。本精编版继承这些状态。观点标签含义见[精编版目录](README.md)。

## 一句话

**最值得采用的不是一个“好代码生成器”，而是把项目约束、最小修改、可执行检查、定向审查和规则反馈接成一条可追溯的工作链；存在可迁移的工程决策顺序，但不存在脱离需求、项目与运行环境的万能代码质量解。**

## 核心问题

当AI编码工具可以读仓库、改多个文件、跑测试、自我审查时：

1. 现有的插件、Skill、分析器和审查服务，各自真正能负责什么，不能证明什么？
2. 在不安装全套工具、不换平台的前提下，怎样的最小工作方式能让AI的第一次实现就更可靠？
3. 人应当在哪一点介入，介入多少次，才能既保持控制又不被流程拖垮？

## 观点体系

### 观点一：不同层次的工具负责不同的事，混称“自动质量系统”会把建议当成证明 〔静态源码研究〕

| 层次 | 能做什么 | 不能做什么 |
|---|---|---|
| 知识文档（项目说明、规则） | 影响模型的输入 | 强制模型遵守 |
| Skill / Agent | 组织调用顺序 | 证明输出正确 |
| 分析器、格式器 | 执行指定的语法或语义规则 | 判断业务意图与职责是否合理 |
| 测试 | 在具体环境下验证样例 | 证明未覆盖的行为也正确 |
| 人 | 意图、取舍、授权与风险接受 | 替代运行证据 |

对候选工具的固定版本源码阅读支持了这一区分。几个代表性发现：

- **官方code-review**：实际命令定义排除了依赖特定输入或状态的问题，且不运行linter。这恰好与Unity停用、销毁、迟到回调这类高风险缺陷不匹配。〔源码，静态〕
- **ECC的quality-gate**：没有`.cs`分支，dispatcher归一化退出码为0，因此不是本题需要的阻断式门禁。〔源码，静态；不能推断ECC所有hook都不阻断〕
- **Roslynator的unused修复**：会真正删除节点，但无法证明scene、prefab或反射的可达性。〔源码，静态〕
- **Microsoft.Unity.Analyzers**：最贴近Unity场景的确定性候选，但同样不证明业务意图或资产实际引用。〔源码，静态〕
- **CodeRabbit**：开源的是Skill，审查本身经认证把diff发到外部服务；“开源Skill”不等于“离线开源审查”。〔源码，静态〕

### 观点二：最小低维护组合，零新增包也能开始 〔采用设计，未试点〕

**现有AI编码工具 + 一份短项目契约或任务卡 + 按需读取既有资料 + 已有的编译、测试、格式与Unity分析器 + 风险定向的只读审查 + 一份反馈记录。**

不需要新的Agent运行时、数据库、Hook或专用Skill。候选工具按三层处理：优先复用（已有的分析器）；有明确收益假设时单项试点（例如pr-review-toolkit的代码/测试专项阅读、Roslynator白名单诊断）；本轮不引入（整套ECC、OpenHands平台、外部审查服务）。

改变推荐的条件也写清了：若授权试点证明某单项插件在相同任务与预算下减少人工返工或漏缺陷，且不扩大diff，就保留；若只多输出意见、引入风格噪声或增加权限成本，就不采用。

### 观点三：一条可追溯的工作链 〔综合推论〕

| 阶段 | 要做什么 | 典型的假完成 |
|---|---|---|
| 编码前 | 写任务卡：目标与非目标、允许修改范围、入口与调用链、状态owner、资源交接、错误与取消约定、影响的资产与平台、验证方法与未知项；AI读真实文件并复述不可改变的契约 | 读了目录树就说理解了架构 |
| 编码中 | 先完成一个可验证的最小切片；行为修改与风格清理分开；新增依赖、公开API、序列化字段、程序集方向或所有权策略时重新确认 | “顺手”重构扩大了范围 |
| 验证 | 把能确定的判断交给程序；记录命令、版本、退出码、实际执行的测试集合和未运行项 | 空测试集、全部跳过或旧报告被当成通过 |
| 审查与修复 | 审阅者先只读diff、必要周边与验证记录；发现写成“具体输入/状态→路径→后果→位置→最小修复→验证方式” | 多个AI投票一致被当成独立验证 |
| 反馈 | 只把重复出现、已确认的失败变成最小规则，写明owner、适用范围、例外与撤销条件 | 每次审查意见都沉淀为规则，规则无限膨胀 |

### 观点四：人只审一次整体方案，之后逐点自主推进 〔协议提案〕

AI-CQEP把日常主线压缩为：**需求 → 有项目依据的方法级方案 → 一次整体人工审核 → 逐功能点实现 → 代码审查与联调 → 提测。**

这条主线的关键设计是**人介入的位置与次数**：

- 常规功能无论风险高低，都先形成方案并经一次整体审核。理由是：在“人审核、AI实施”的分工中，方案审核是人保持控制的唯一闸门。
- 审核通过后，在批准范围内逐点自主完成，不为每个方法重复审批。
- 只有改变业务范围、公共接口、模块职责、所有权协议，或扩大授权时，才提交“差量”重新审核。
- 稳定的项目规范（命名、注释、排版）由AI主动执行，不让人逐项监督。

方案的最小形态是一条关联链：功能/验收编号 → 文件、类型、方法 → 复用/修改/新增及职责 → 规范和源码依据 → 检查方式与未覆盖项。关键方法再补参数、主流程、分支、副作用、失败/取消/退出与资源归属。

### 观点五：八条常驻约束 〔协议提案〕

| ID | 约束 | 可观察的动作 |
|---|---|---|
| U1 | 目标不明，不臆造行为 | 明确目标、非目标、可观察验收；仍不明就提问或停止受影响部分 |
| U2 | 先读真实上下文，再决定修改 | 读将改内容、调用方、数据路径、测试与相似实现 |
| U3 | 先确定责任，再选择结构 | 指明状态权威、副作用、资源/任务所有者、失败与退出责任 |
| U4 | 选择满足当前契约的最简单完整方案 | 先查复用；新增抽象须说明现在隐藏什么知识 |
| U5 | 保护契约和修改边界 | 区分有意改变与必须保持的行为 |
| U6 | 用对应证据验证对应主张 | 按风险执行检查，报告真实状态 |
| U7 | 按风险增加独立审查，逐项核对发现 | 区分缺陷、设计讨论、风格；不以投票代替证明 |
| U8 | 只沉淀已确认且可复用的经验 | 保留原因、范围、例外及淘汰条件 |

**小任务可以压缩记录，但不能压缩事实诚实、授权边界与必要验证。**

### 观点六：通用的是决策顺序，具体规则属于项目 〔协议提案〕

AI-CQEP分两层：第一层是通用协议（提问、决策、停止条件与证据责任）；第二层是项目工程契约（技术栈与版本、模块边界与依赖方向、状态与资源owner、命名约定、错误/线程/生命周期规则、验证入口、性能预算、权限边界）。

**契约是一组有效约束，不是一份必须新建的文件。** 已有项目说明足够时直接使用，只在缺口处用模板补充。

冲突时先分性质再谈优先级：不可交易的边界（安全、法律、数据完整性、事实诚实、授权）＞ 已批准需求与项目硬契约 ＞ 项目惯例 ＞ 一般表达偏好。项目契约可以规定性能敏感写法或特定类组织，但不能把未运行写成通过、把自查写成独立审查。

### 观点七：首次质量靠定位、责任和及时验证，不靠事后“再优雅一点” 〔协议提案〕

AI-CQEP把编码中的即时判断写成可执行的规则：

- **阅读够了的标准**：能从真实入口解释受影响的正常路径和主要失败路径；知道第一次状态变更发生在哪里、失败后谁收尾；找到兼容要求与测试入口；已知未读部分不决定本次设计。
- **新增抽象的四问**：现在要隐藏哪项知识？谁因此不再承担什么？现有边界或局部重复为什么不够？新增的接线、跳转、测试与生命周期成本值得吗？答不出前两问就拒绝本次抽象。
- **判断不清时的默认值**：收益不清楚时默认保留现状或采用较小方案。这不是“永不改设计”，而是要求设计收益承担举证责任。

### 观点八：风险决定调查与验证深度，不决定是否跳过方案审核 〔协议提案〕

| 风险 | 触发 | 动作 |
|---|---|---|
| L | 局部、已知、可逆，责任与兼容不变 | 相关检查与自查 |
| M | 重要协作、错误路径、异步或事件有效期 | 查明协作与失败责任，定向独立审阅 |
| H | 安全、资金、不可逆数据、迁移、公共协议、所有权或并发策略、关键资源寿命 | 补兼容、验证与恢复边界，独立审查 |

按最高后果，不按行数。风险升级不自动增加审批轮次，也不默认新增Agent或Skill。与工程判断Tier的对照见[术语与分级对照](../../docs/glossary.md)。

### 观点九：交付状态只有三种，不能含糊 〔协议提案〕

1. **已完成并按列明范围验证**：目标达到，必要证据与最终产物对应，没有未解决的必须修复项。
2. **实现已完成，验收待验证或待决定**：代码可接手，但必要运行、审查或业务选择缺失；不得简称“全部完成”。
3. **阻塞或未完成**：说明已做什么、影响和最小下一步。

“提测就绪”不等于QA通过、产品验收或发布许可。连续修复仍出现同类问题、成本超预算或无法取得关键证据时，停止自动迭代，交维护者决定，不追求无限轮“审到零发现”。

## 协议不能保证什么

AI-CQEP明确列出：它不能保证需求正确、契约完备、首次实现无缺陷；不能通过有限测试证明全行为等价；不能仅凭静态阅读证明设备性能与平台兼容；不能提供权限隔离、离线保密、自动回滚；不能替有权人员接受风险或批准发布。“最危险的失败不是公开承认未知，而是把‘流程走完’当成‘质量已经证明’。”

## 如何检验它是否真的有用（设计，未执行）

在授权项目中选代表性的L/M/H任务，记录“首个完整实现快照”（尚未接受独立审查修复的版本），对照既有做法观察契约违背、关键遗漏、无关改动、需返工的设计、必要验证是否真实执行，以及总时间和人工返工。统计口径事先确定；若收益不明显或文档负担增加，先简化协议，不默认添加更多Agent或Hook。
