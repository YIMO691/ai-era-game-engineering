- **需要作出的判断**：能否把“AI 使某道题更快”推广成“熟悉真实仓库的维护工作更快、更可靠，且不损害学习”？如果不能，应分别衡量哪些成本、质量与判断责任？

### ER-20261106-ai-03 — Peng 等：GitHub Copilot 受控编程题

- **标题/作者/年**：*The Impact of AI on Developer Productivity: Evidence from GitHub Copilot*；Sida Peng、Eirini Kalliamvakou、Peter Cihon、Mert Demirer；2023。
- **URL/DOI/版本**：[原文 HTML v1](https://arxiv.org/html/2302.06590v1)；[书目页](https://arxiv.org/abs/2302.06590)；DOI [10.48550/arXiv.2302.06590](https://doi.org/10.48550/arXiv.2302.06590)。HTML 明示 **v1，2023-02-13**。只核此版本，不声称与后续版本逐字一致。
- **方法**：实验发生于 **2022-05-15 至 2022-06-20**，不是 2023 年工具的现场实验。Upwork 招募职业程序员；166 个邀请、95 个接受，随机 **45 人处理、50 人对照**。处理组获得 Copilot 及一分钟介绍；两组均可用互联网/Stack Overflow。统一任务为 JavaScript HTTP server。
- **测量边界**：GitHub Classroom 从个人仓库创建时间计到第一次提交通过 **12 项可见但不能修改的测试**。这是经过时间，不是精确的键盘操作时间、价值产出或端到端团队维护周期。标准化骨架项目不同于长期熟悉仓库的复杂维护。
- **核验数字**：正文报告两组各 35 人完成任务及问卷，时间结果明确**条件于完成任务**：处理组均值 **71.17 分钟**，对照 **160.89 分钟**；报告完成时间减少 **55.8%，95% CI [21%, 89%]，t 检验 p=0.0017**。四个超过 300 分钟的异常值都在对照组，作者称剔除后结论仍稳健，本轮未重算。

| 工具 | 文件查看、搜索、编辑、shell/测试、错误反馈、输出截断/上下文保留 | 论文摘要索引只指向 ACI 方向；具体命令、窗口、限制和权限未核 |
| 修改 | 编辑失败、语法/lint 错误时是否回滚，如何防止改错文件/越界 | 只能列作要查的契约；没有核实某版一定存在 lint gate 或原子回滚 |
| 测试 | agent 可以运行哪些仓库测试；评估阶段用什么隐藏 test patch；失败如何判定 | 04 的 F2P/P2P 是索引线索，具体评分、跳过测试及安装失败处理待源码核查 |
| 提交 | patch 怎样提取，是否去除测试更改，空补丁/预算耗尽如何处理 | 待核；没有本轮补丁、轨迹或测试日志 |
| 人工 | 谁审查语义、安全、兼容性、文档和维护负担 | benchmark 通过不自动免除人工责任；这是本研究的判断边界，不是测量结果 |

**研究者建议的安全练习边界，非原项目已验证事实**：若未来另获运行授权，只用公开、可丢弃的任务环境；不挂载私人仓库与凭据；明确网络、命令、时间和费用权限；将推理时可见测试与最终评估材料分离；记录全部干预与失败。当前任务没有该运行授权，也未执行这些步骤。

### 4.3 论文设计理由与替代方案——哪些尚未核

- **可定位的原始方向**：05 的题目与摘要索引把 ACI 作为贡献对象，不是只给模型一个“修复 issue”的提示。
- **待原文/消融验证的理由**：受控的文件视图是否减少上下文噪声；搜索摘要是否帮助缩小位置；结构化编辑与反馈是否降低交互失误；历史保留/压缩是否影响后续判断。**本轮没有读到支持这些机制的原表格与消融，不能写“论文已证明每项机制有效”。**
- **不能混淆**：界面便于模型使用，不等于权限已安全隔离；syntax/lint 通过，不等于语义正确；测试通过，不等于维护者合并；修复有限 issue，不等于自主维护整个产品。

下列是分析用替代方案，不声称论文全都实验比较过：

| 方案 | 潜在收益 | 代价/要验证的反例 |
|---|---|---|
| 人主导 IDE + 补全/聊天 | 人保留仓库定位与决策；易按需使用 | 人的提示、审查与整合时间可能抵消生成速度；不能只数接受的代码 |
| 通用 shell agent | 灵活、工具契约较少、可复用已有命令 | 输出冗长、编辑错误、权限范围及上下文成本；更灵活不保证更有效 |
| 检索后直接生成 patch | 流程简化，减少交互轮次 | 定位或假设错时缺少执行反馈；检索质量、人工修补可能成为隐含成本 |
| 专用 ACI / harness | 显式组织查看/编辑/反馈与停止条件 | 维护工具契约、支持语言/平台、窗口与截断损失、接口偏置；需同模型同预算比较 |

### 4.4 成本、观察结果及适用边界

- **本轮实际成本数据**：没有项目运行、API 调用账单、token 记录、容器运行时间或人工审核计时；不能编造美元/任务、分钟/任务或成功数。原论文成本表未读，均值、上限与当前价格均未知。
- **应比较的成本项**：输入/输出与反复历史的 token；失败/重试和超时；仓库安装与隔离环境；外部测试；人工定位、审查、返工；工具维护及错误接受的机会成本。只比单次模型费用会漏项。
- **本轮观察**：原文/源码读取失败；没有生成补丁，没有执行测试，没有验证案例轨迹。05 的历史 12.5%/87.7% 仅为待核索引，不作为此案例的复现结果或当前成功率。
- **未来可证伪比较**：同一模型快照、任务集合、budget、重试政策与可见信息，比较专用 ACI 与通用 shell；记录所有实例而非只挑成功轨迹；分别报告功能测试、安全/维护审查和人工干预。如果提升只在换更强模型、放宽预算或人工修补后出现，就不能归因于 ACI。
- **适用边界**：真实开源 issue 比孤立函数题更接近仓库工作，但有限测试与历史 PR 仍不等于完整需求、长期维护、部署或学习。不能从 Python benchmark 推导 Unity/C# 引擎生命周期、平台限制或团队交付收益。

### 4.5 学习者判断练习（题设，不是实际运行记录）

1. **只有补丁通过测试，能合并吗？** 假设 agent 留下了通过记录，请分别列出已证明的行为、未覆盖的需求/回归/安全风险，以及必须由维护者确认的事项。不要回答“AI 比人可靠”这种超出证据的问题。
2. **谁真正省了时间？** 假设生成很快但人需要定位、复查、改测和返工，应从哪一个起点计时？并行 agent 的等待时间如何计入个人投入、日历时间和总资源？用 02 的计时问题检验方案。
3. **判断 harness 还是模型的贡献**：两组成绩不同时，先核对模型、任务分母、权限、预算、重试、可见测试与人工干预是否相同。设计能推翻“全由 ACI 带来”的对照，而不是只展示成功截图。
4. **离开工具还能解释吗？** 在看生成补丁前先写故障假设、行为不变量与最小反例；看后解释每个改动为何必要，再设计一个未见过的边界测试。该练习是教学提案，未经过真实学习效果验收。
5. **找出证据越界**：分别判断“更快完成题目”“修复了此 issue 的测试”“维护更省钱”“学会了调试”“多年后技能没有下降”需要什么不同证据。08 的非软件机制、09 的短期新库测验、11 的初学者任务均不能直接完成最后一项证明。
