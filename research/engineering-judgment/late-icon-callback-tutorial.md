# 图标已经换了，旧请求为什么还在写

> **公开导出注（2026-11-12）**：以下研究状态、访问和审查记录属于原 2026-11-06 草案；本次只作本地白名单导出。公开授权不等于人工研究审核、实验通过或生产验收。私有状态描述是历史记录；模板及操作文本仅作资料，不在本次执行。转换与排除见 [导出清单](export-manifest.json)。


> **warning** — 文章身份与限制
> 下面的背包格子是**教学题设，不是真实公司事故**；没有执行代码或测试。后文对 UniTask 2.5.10、NGO 1.9.1 的窄观察来自已读固定源码，不能扩展成所有版本/API 的保证。本文所属研究仍有认知论文和四个其他案例的一手证据缺口；训练法是提案，没有学习效果数据，也没有真人教学验收。

## 1. 先不要改代码

假设你接到这样一个 bug：背包滚动得快时，格子偶尔显示成上一个物品的图标。复现不稳定，日志没有异常。

最容易想到的修复是“回调里判空”。再进一层，是“关闭时取消请求”。这两种都可能是措施，但我们还不知道它们是否解决这道题。

先看一段**构造的时序**：

| 时刻 | 格子当前绑定 | 正在发生什么 |
|---|---|---|
| t1 | 物品 A | 请求 A 图标 |
| t2 | 未绑定 | 格子回收，但 Unity 对象没销毁 |
| t3 | 物品 B | 同一个格子借出给 B，请求 B |
| t4 | 物品 B | B 返回，显示 B |
| t5 | 物品 B | A 晚返回，旧回调开始 |

在 t5 判“对象是否为空”，答案是不为空。对象甚至正在正常工作。真正过期的不是对象，而是**旧请求对它的写入资格**。

因此第一个有用问题不是“该加什么 API”，而是：

> 这次结果属于哪次展示？谁能证明当前格子仍然需要它？

这句话把我们从局部代码外观，带到了状态、时间和所有权。

## 2. 画三条寿命，而不是只画一个类

这道题至少有三条不同的寿命：

1. **Unity 对象**：创建到销毁，中间可能多次启停/回池。
2. **展示绑定**：这一次借出展示 A，结束后可能展示 B。
3. **加载操作与结果**：请求可能晚于绑定结束；结果还有自己的持有/释放契约。

三者未必同起同终。

如果把对象当成唯一寿命，就容易写出“对象还在，所以还能写”。如果把取消当成统一终点，又可能误以为“等不到结果，所以也无需清理”。但底层操作是否中止、结果是否仍产生、谁释放，必须查真实 API，不能凭 token 名字推断。

把问题记成表，比开始就引入一套新服务更有用：

| 要回答的事 | 在项目中查哪里 |
|---|---|
| 谁使旧展示失效？ | Bind/Unbind、回池、关闭和重开入口 |
| 谁持有本次身份？ | 绑定上下文、请求记录或框架已有机制 |
| 谁能取消？取消到底做什么？ | 目标包版本的契约与实际调用链 |
| 晚到成功结果怎样处理？ | 资源 owner、句柄转移/释放路径 |
| 失败/取消后谁清理？ | 成功、失败、取消三个分支及 finally |

“代次”是一次绑定的身份，不必一定是某种整数实现；项目如果已经有正确契约，就不需要再造一个 token 框架。

## 3. 先提出两个真可能的原因

只根据画面串图，我们仍不能确定旧回调就是根因。

- H1：旧结果写入新绑定。
- H2：资源 key 或配置本来就映射错。
- H3：共享资源过早释放，之后拿到了错误/无效状态。

下一步应该是一次能分清这些原因的检查：记录或可控观察**请求身份、绑定身份、key、完成顺序与当前 owner**。如果 key 一开始就错，修 generation 可能只让错误更稳定；如果旧结果从未写入，不能因为故事顺耳就认定 H1。

这就是判断训练的一小步：**先写预测，再看结果**。否则修完后很容易把任何变化都解释成“我一开始就知道”。

本题没有实际日志，所以我们现在只能提出检查，不能宣布定位成功。

## 4. 一个真实源码提醒：取消返回对了，还没说清回收

在 UniTask 2.5.10 的一个限定路径里，`SuppressCancellationThrow` 能在取消时给出 bool 结果；但包装的 canceled 分支不调用底层 `source.GetResult`。而所研究 `DelayPromise` 的一条清理/尝试回池路径放在 GetResult 的 finally 中。于是**表达结果正确，不自动等于底层消费/回收协议相同**。

这条观察只针对固定源码和明确路径：创建时未取消、DeltaTime Delay、正常推进的 PlayerLoop、单次消费。即时取消还有另外的归池条件，不能混成一件事。来源 `ER-20261106-game-04/05/07/08`，完整分析见 [工程判断案例库 — C1. UniTask：取消何时生效，与池化归还是否同一件事](case-library.md)。

我们没有运行内存实验，所以不能把它改写成“已经测到永久泄漏”；也不能据此禁用全项目所有 suppress。更不能在已消费后再 await 一遍“补清理”，因为单次消费约束仍然重要。

它对图标题真正有价值的启发是：

> 改写异常/状态的包装层，可能也改变带副作用的消费路径。读代码要追到消费和清理，而不只看返回值。

注意，这不是说教学图标加载一定用了 UniTask Delay，更不是说它有同一个 bug。我们迁移的是检查问题，不是硬套结论。

## 5. 另一段真实源码：收到通知，不代表能立刻复用

在 NGO 1.9.1 的指定动态对象路径中，`OnNetworkDespawn` 被通知后，旧网络流程还要处理消息、spawn 状态与 registry 等。若业务在通知里就把实例发布到空闲池，并允许同步借出，旧流程未必已经结束。

有注册 handler 时，正常 `Despawn(true)` 还能由 handler 把物理释放变成停用归池；名字里的 destroy 并不总等于 Unity `Destroy`。false 在 authority 和远端也并非简单对称。来源 `ER-20261106-game-15`～`20`；范围和反例见 [工程判断案例库 — C2. NGO：网络身份注销与物理归池不能混为一谈](case-library.md)。

对图标题的迁移仍然是有限的：**逻辑终止、通知、旧访问者脱离、物理复用要分开证明。**这不表示两个项目共享同一种缺陷，也不意味着所有对象池都要照搬 NGO。

## 6. 回到题目：现在才比较修复

在已经由项目证据支持 H1、资源 owner 契约也查清的前提下，可以比较：

| 方案 | 可能适合 | 需要承担的代价 |
|---|---|---|
| 沿用现服务，绑定身份校验并处置晚到结果 | 问题局限该复用路径 | 新旧绑定、失败与释放分支必须完整 |
| 在旧加载 API 后加小适配层，逐迁调用方 | 同一问题多次出现，确有共同契约 | 适配层 owner、双轨与退出条件 |
| 替换全资源系统 | 现机制无法满足硬约束且有授权/迁移能力 | 最大回归与发布半径，不是默认答案 |

这时“不重构整个框架”不是懒，而是一个有理由的决定：当前目标和证据可能只需要局部修复。如果后续证实许多调用方反复违反相同契约，才有更多理由讨论共享边界。

反过来，永远复制补丁也不是美德。选哪一个，取决于共同变化原因、风险、验证能力，不是“抽象越多越高级”。

## 7. 什么才算修好了？

“我滚了几次没错”是观察，但不是足够强的全部验收。

为这个题设设计的候选测试可以是：

- A 请求未完→复用 B→B 完成→A 完成：最后只能是 B。
- 关闭→重开同一物品：旧代结果也不能随意取得新代写入权。
- 失败/取消/晚到成功：结果与句柄的归属符合实际 API，不能双释放或漏释放。
- 多次绑定同 key：不能因为 key 相同就把不同生命周期混为一谈。
- 重要旧行为仍成立：资源缓存、业务状态、必要重放没有被修复意外破坏。

这些是**测试设计，尚未实现/运行**。最终 oracle 应从需求与资源契约独立确定，而不是由实现作者或同一个 AI 根据新代码反推“正确结果”。

连现有测试也要看断言。NGO 的一个已读关服测试，在 server shutdown 后仍等待先前的 client 标记；这不足以独立证明 server 回调，但也不证明产品没有回调。`ER-20261106-game-23`。测试名好看，不代表测试问了正确问题。

## 8. AI 在这里应该做什么？

让 AI 帮忙找 Bind/Unbind、追句柄、列三个备选原因、生成乱序测试候选，都可能有价值。先给路径、版本和修改边界，要求每个结论带证据；不要把公司私有代码/凭据未经授权上传。

人至少保留四件事：

1. 这次到底改什么、不改什么？
2. 哪个 owner/不变量不能破坏？
3. 哪个反例会证明修复错了？
4. 实际跑了什么、什么没跑，谁能批准交付？

AI 一起写实现和测试，可能让两者一起误解需求。换一个模型挑错能补充视角，却不是自动独立 oracle。

已读的 Peng 等编程题研究支持某类任务可以节时，但没有研究代码质量；METR 2026 跟进又显示真实工作的选择/计时/产物问题。`ER-20261106-ai-02/03`。所以别用“生成很快”证明这个修复正确，也别凭本题证明 AI 一定让人退化。长期职业能力影响仍是本研究的证据缺口。

## 9. 把这一次变成下一次能用的经验

别只记“格子要加 token”。记一条带边界的规则：

> 当可复用展示的绑定寿命短于异步操作时，对象存在不足以证明写入资格。应关联本次展示身份，并按实际 API 约定处理晚到结果；如果框架已有可靠的资格/owner 契约，优先沿用。下一次在不同模块先预测旧结果是否仍可能影响新代，再用证据检验。

然后做两个变式：

- 表面不同、机制相近：搜索结果面板切换查询后旧响应晚到。
- 表面相似、机制不同：格子始终绑定同一物品，但配置 key 本来就错。

能区分它们，比复述原故事更接近我们要观察的迁移。**这是待验证练习设计，不是已证实的培训疗效。**

## 10. 今天真正值得带走的四问

**改什么？为何在这里？可能坏什么？怎样知道没坏？**

低风险任务把四问写清就可以，不必每次写一整篇架构论证。碰到共享资源、网络、持久化、经济与发布，再升级分析与审查。
