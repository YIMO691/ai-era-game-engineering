# 成熟项目源码阅读与设计还原手册

> **公开导出注（2026-11-12）**：以下研究状态、访问和审查记录属于原 2026-11-06 草案；本次只作本地白名单导出。公开授权不等于人工研究审核、实验通过或生产验收。私有状态描述是历史记录；模板及操作文本仅作资料，不在本次执行。转换与排除见 [导出清单](export-manifest.json)。

> **note** — 目标与边界
> 阅读的终点不是“我能解释每个类”，而是“我能预测一次相关修改的后果，并说明预测依据和失效条件”。以下 M3 为研究综合模型；认知/程序理解文献存在正文读取缺口，不能宣称本方法已经被实验验证。

## 1. M3：代码事实如何转成判断规则

**任务问题 → 版本化事实 → 行为/所有权模型 → 意图证据 → 替代与反事实 → 条件规则 → 新任务预测 → 验证与更新。**

- 输入：一个具体工程问题、固定项目版本、可访问的代码/测试/文档/历史。
- 输出：一条能被新案例检验的条件规则，而非“学到了单例/状态机/观察者”。
- 中间可回退：测试与源码不一致就修改行为模型；找不到历史动机就停在“研究者推断”，不补小说。
- 适用：维护型任务、模块比较、设计审查、疑难诊断。
- 局限：黑盒原生实现、闭源依赖、生成代码、动态内容与部署行为可能超出可见源码；静态理解不能替代运行。

## 2. 陌生项目的探索顺序

### 第 0 步：先写要回答的决策

错误问题：“这个优秀框架怎么写的？”

可研究问题：“面板关闭后仍返回的资源请求，谁持有结果，谁有权丢弃或释放？如果面板复用，旧回调如何不污染新状态？”

先写一条预测和一个未知，避免事后把找到的所有机制都说成学习目标。

### 第 1 步：确认运行与版本，不先读工具库

- Editor、包版本、编译后端、平台、启动场景、构建入口、测试命令、生成步骤。
- 记录 tag/commit、工作树是否有改动。浮动 `main/master` 只代表访问时状态。
- 不擅自运行陌生仓库脚本。克隆/归档隔离，静态阅读优先；需要执行先检查命令与授权。

### 第 2 步：用一条纵向功能线建“薄地图”

按入口（用户/生命周期/网络）→协调模块→状态所有者→外部边界→表现→退出追踪。优先找核心行为与责任，不按文件夹逐层背诵。

地图只需回答：

| 视角 | 记录内容 | 可检验问题 |
|---|---|---|
| 结构 | 模块、接口、依赖方向、owner | 哪个依赖方向实际不允许反转？ |
| 数据 | 来源、校验、转换、缓存、落点 | 谁是权威？什么时候失效？ |
| 状态 | 状态集合、合法转换、重复/乱序输入 | 不可能状态如何被阻止？ |
| 生命周期 | 创建、启用、订阅、异步、回收、销毁 | 哪个时间点后回调已无权写？ |
| 运行 | 线程/PlayerLoop、网络、内容、构建 | Editor 成功是否代表目标设备？ |

### 第 3 步：深挖一个风险最大的交叉点

例如资源返回碰到 UI 复用、网络重连碰到本地预测、配置更新碰到旧客户端。此时再读基础设施实现，问题会比“从底向上通读”具体。

### 第 4 步：补横向比较

找到相邻调用方和一条不同路径：同 API 是否不同 owner？取消是否只停止等待，还是也停止底层操作？资源释放是句柄、实例还是共享依赖？不要仅因函数同名就假定契约一致。

### 第 5 步：用测试/运行挑战地图

先预测再观察：输入、执行顺序、最终状态、释放次数/引用归属。不能只看“没有报错”；也不能把正好经过的路径当覆盖所有组合。

## 3. 入口与调用链追踪记录

每个节点至少写：`文件@版本:符号 → 输入/输出 → 副作用 → owner → 证据类型`。

不要只记录 A 调 B：真正关键的边可能是事件订阅、序列化引用、反射注册、资源 key、配置映射或网络消息。静态查找找不到，不等于没有调用方。

给每条边分级：

- **已确认**：固定版本源码直接调用/注册，或对应运行观测。
- **推断**：动态注册约定提示存在，但尚未追到实际实例。
- **未知**：需生成文件、服务器行为、原生引擎或内容构建才确定。

每次记录完整路径只为能审查，不为制造“我看了很多代码”的活动量。

## 4. 数据、状态与生命周期要联合看

一个常见陷阱：数据流正确，时间上的写入资格却错误。

教学例（不是任何框架的 API 契约）：

1. 展示物品 A，启动请求 A；
2. 格子回收并复用为物品 B；
3. B 已显示，A 晚返回；
4. A 回调发现对象仍存在，于是把 A 图标写到 B。

“判空”和“对象未销毁”都不足以判断当前请求是否仍拥有写入权。应追踪**请求身份、展示代次、结果所有权、取消/完成竞态**。具体解决可能是代次校验、取消、绑定 token、统一加载服务或组合；必须依据项目原有契约选择，不能直接套框架习惯。

对任一异步点问：

- 等待者、操作、结果分别由谁拥有？
- 取消什么时候可见？底层是否支持中断？晚到结果怎么办？
- 成功、失败、取消、关闭、重开、回收之间哪些可以交错？
- 清理会不会双重执行？池化后旧状态是否仍可访问？
- 哪些回调会跨线程/跨 PlayerLoop 阶段？

相关冻结源码案例见 [工程判断案例库 — C1. UniTask：取消何时生效，与池化归还是否同一件事](case-library.md)。

## 5. 设计意图：四种不同的问题

| 想知道的事 | 足够的证据 | 不足的证据 |
|---|---|---|
| 当前实现做什么 | 固定源码、契约、测试/观测 | 项目介绍、方法名 |
| 当前实现保证什么 | 明确契约+异常/边界测试 | 一次成功运行 |
| 当时为何选择 | 同期 ADR/RFC/PR/维护者讨论 | 从当前结构反推作者动机 |
| 现在是否仍合适 | 当前约束+替代成本+验证 | 当年决定正确、项目很有名 |

### 还原顺序

1. 查测试与公开契约，确定当前行为；
2. 看相关提交 diff，区分引入行为和后续修补；
3. 查 commit 引用的 Issue/PR，注意讨论时间与实际合并差异；
4. 查同期设计提案的目标、非目标、替代和兼容承诺；
5. 无明确理由时，写“现结构与 X 约束一致，可能的解释是 Y，尚无作者意图证据”。

**提交说明也不是最终真相**：计划可能改变，评论可能过时，测试可能漏例。结论必须标时间与范围。

### 四类来源不能相互替代

- 有意设计：有明确约束与决策记录。
- 历史遗留：历史材料说明旧契约延续，或存在未完成迁移。
- 偶然形成：目前缺少稳定设计证据；不能凭“不喜欢”认定偶然。
- 不得已妥协：有成本/平台/兼容约束记录；不能替作者找借口。

## 6. 替代方案与反事实

反事实不是“换一种设计模式”，而是移除一个机制后，推演哪条不变量首先失效。

例：移除网络对象处理器映射，只在本地用 Unity 对象池。需要分别追踪 host/server/client 的创建、消息、网络 ID、despawn、回池以及再次 spawn。若只证明本地复用成功，尚未证明网络生命周期一致。

每个替代至少回答：

1. 满足同一目标吗？还是悄悄降低功能？
2. 哪些工作转给调用方/工具/运行时？
3. 引入什么失败或维护成本？
4. 哪个可执行测试能区分它与现方案？
5. 什么项目条件变化会让替代更好？

没有公开备选讨论时，统一写**“研究者提出的备选，不是作者明确拒绝的方案”**。

## 7. 跨项目比较：只比较同一工程问题

适合比较：资源/句柄所有权；取消及时性；网络对象生命周期；迁移适配；测试 oracle。

不适合比较：一方做底层库、一方做业务框架，却用“谁抽象多/跑分高”直接排名。

| 对齐项 | 项目 A | 项目 B |
|---|---|---|
| 任务与调用方 | 同类等待/资源/状态问题？ | 是否相同？ |
| 权威与 owner | 谁能修改、取消、释放？ | 差异理由？ |
| 环境 | 线程、帧循环、平台、版本 | 哪些不可比？ |
| 失败语义 | 取消、超时、丢弃、重试 | 是否等价？ |
| 代价 | 分配、注册、同步、复杂度 | 有无测量？ |
| 迁移条件 | 哪些事实支持选 A？ | 哪些条件转而支持 B？ |

用案例 C1、C2 练习“业务 owner 生命周期与基础设施生命周期是否一致”，但它们并不提供相同 API，因此不能直接性能对比。用 SQLite 与 Kubernetes 比较故障/迁移验证，只能迁移**证据设计逻辑**，不能迁移它们整套组织流程。

## 8. 从案例沉淀条件规则

不合格：“异步都要取消”“所有资源都用对象池”“大项目都用接口”。

合格模板：

> 当【环境/任务】且【关键约束】时，采用【策略】可能优于【替代】，因为【机制】；依据是【固定源码/实验/历史】，代价是【成本】；若【边界变化】则需重新判断。下一次用【新任务预测】检验。

示例规则（研究建议）：**当可复用 UI 的绑定寿命短于加载操作时，仅检查对象存在不足以保证写入资格；应显式关联当前展示身份，并定义晚到结果处置。**这不是说每次都要发明新 token 服务，而是先检查现有框架是否已提供该契约。

## 9. 完整案例记录结构

1. 项目与 tag/SHA、读取日期、许可证；
2. 具体问题与研究前预测；
3. 文件/符号/模块边界与真实调用线；
4. 当前行为事实；
5. 意图证据及可信度；
6. 至少一个真实可行替代；
7. 选择理由（作者陈述与研究者解释分开）；
8. 收益与代价（没有基准就不写“更快”）；
9. 适用条件/失效边界；
10. 可迁移经验与不可照搬部分；
11. 未解问题；
12. 独立判断练习、oracle、验证结果与更新。

## 10. 训练与评价

### 训练 A：隐藏实现

只给接口、需求和边界，让学习者画状态/所有权并预测；保存预测后，再逐步开放源码、测试、PR。记录哪条证据改变了判断，而不是看完答案后复述。若已读主报告、Blog 或案例解析，原题只作示范；独立评价改用未见变式，不把有提示复述计入无提示基线。

### 训练 B：解释竞争

对同一抽象提出两个解释，如“降低分配”与“保留兼容性”；分别寻找能区分它们的历史或实现证据。未分出高下就标未知。

### 训练 C：带条件迁移

把一个网络对象案例转为 UI 资源复用问题，指出哪些语义可以借鉴、哪些不成立。不能只换命名就叫迁移。

### 评分锚点（0–3，研究设计）

- **事实准确**：是否固定版本、具体符号、分清静态与运行。
- **模型完整**：是否包含异常/取消/owner 和重要非代码边。
- **理由克制**：是否把作者意图和研究者解释分开。
- **权衡与迁移**：是否有可行替代、成本和失效条件。
- **独立预测**：新题出现时能否先给可反驳判断。

0=无证据或明显错；1=在指导下局部成立；2=独立且基本完整；3=能处理边界并据反证更新。**这是训练 rubric，不是经验证的能力量表。**晋级需多个新任务和独立审阅，不能按阅读页数或 GitHub star 数评分。
